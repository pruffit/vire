# VireMusic — инженерный цикл (оверлей над Superpowers)

Superpowers задаёт **КАК** (дисциплина фаз). Этот скилл вкручивает **ЧТО ИМЕННО**
для VireMusic: артефакты, гейты, роутинг моделей и review-чеклист из накопленного фидбэка.
Не дублирует Superpowers — подключает его на каждой фазе.

## Автономность — по умолчанию ДЕЙСТВУЙ, не спрашивай

Прогоняй весь цикл от Requirements до Ship **без остановок на согласование**. Между
фазами не отчитывайся и не жди «добро» — переходи сам. Отчёт — в конце, с готовым
результатом и предложением правок, а не вопросом «можно ли продолжить».

**Решай сам (НЕ спрашивать):** триаж, какие файлы, root-cause и подход к фиксу, какой
моделью гнать сабагента, поднимать ли агентов и сколько, источники ресёрча, детали
реализации, как верифицировать, уборка лесов. Это инженерные решения — твои.

**Спрашивай ТОЛЬКО когда** (одним батчем, не по одному):
1. Продуктовая/требовательная развилка, меняющая ЧТО строим, и её нельзя закрыть из
   кода/доков/разумного дефолта (фаза Requirements — один раз).
2. Необратимое/наружу: деплой, удаление данных, push/force-push, смена прод-конфига.
3. Явная развилка без разумного дефолта, где цена ошибки высока.

Сомневаешься «спросить или решить»? → реши, сделай, покажи результат, предложи откатить.
«Спрошу на всякий случай» после каждого шага = плохой воркфлоу. Не делай так.

## Триаж (первое решение)

- **Тривиалка** (опечатка, переименование, правка копирайта, одно-строчный фикс) → быстрый путь: правка → гейты → коммит. Цикл не разворачивать.
- **Иначе** (фича, смена поведения, рефактор >1 файла, нетривиальный баг) → полный цикл ниже. «Это же просто» — красный флаг, см. таблицу.

## Цикл и привязка фаз

| Фаза | Skill (Superpowers) | VireMusic-инъекция | Артефакт | Модель |
|---|---|---|---|---|
| Requirements/Design | `superpowers:brainstorming` | дёрнуть `vire-architecture` (слои/FSD) до дизайна; продумать **мобилку** и **переиспользование** уже здесь | spec в `docs/superpowers/specs/` | Opus (главная сессия) |
| План | `superpowers:writing-plans` | точные пути; что переиспользуем из `packages/ui` и `apps/web/components`; какой слой; какие тесты | план в `docs/superpowers/plans/` | Opus |
| Implementation | `superpowers:subagent-driven-development` + `superpowers:test-driven-development` | сабагентам — ссылки на `vire-architecture/media/queues`, не инлайнить файлы | код + тесты | **Sonnet** (Haiku — тривиал/поиск/маппинг) |
| Debug (если всплыл) | `superpowers:systematic-debugging` | gotchas VireMusic (см. ниже) | — | Opus |
| Review | `superpowers:requesting-code-review` | **VireMusic-чеклист** (ниже) обязателен | вердикт | Sonnet (Opus если спорно) |
| Testing/Verify | `superpowers:verification-before-completion` | прогон ВСЕХ гейтов (ниже), Iron Law | зелёные гейты | механика |
| Ship | `superpowers:finishing-a-development-branch` | версия в 2 местах, lockfile, doc фичи | коммит/PR | — |

Артефакты (спека, план, фичедок, ledger) пиши по размеру задачи: покрой суть — решения,
пути, риски — без филлер-секций и повторных резюме. Длинная спека ≠ хорошая спека.

Полный контекст задаче задавай сразу: одна развёрнутая постановка на входе даёт лучший
результат, чем то же самое, размазанное по десятку уточняющих реплик.

## Оркестрация: главная сессия НЕ исполняет

Главная сессия (Opus) — оркестратор: триаж, дизайн, план, маршрутизация. **Реализацию и
широкий ресёрч отдавай сабагентам** (`Agent` tool, поле `model`) со свежим контекстом —
это и бережёт твой контекст от деградации, и режет расход (дешёвые модели на механику).

Антипаттерн с одной стороны: прогнать весь цикл инлайн в главной Opus-сессии. Ловишь себя
на ручной реализации/массовом ресёрче в главной сессии — сигнал делегировать.

Антипаттерн с другой: сабагент ради сабагента. Делегирование множит стоимость и время —
каждый агент заново набирает контекст, заново исследует, отчитывается, а ты потом читаешь
отчёт. Поэтому:

- **Делегируй:** крупные, реально независимые и параллелизуемые треки — широкий
  многофайловый ресёрч, независимые срезы реализации по готовому плану.
- **Не делегируй:** то, что закрывается парой чтений/правок или одним grep'ом; проверку или
  перепроверку собственной работы (верификация живёт в главном цикле — гейты ниже).
  Поиск уходит агенту (Haiku), когда это широкий маппинг по репо, а не один известный файл.
- Хватает одного агента — бери одного, не троих. Счётчик параллельных держи низким;
  дробить одну умеренную задачу на параллельных агентов не надо.
- Бриф сабагенту пиши точным с первого раза (запуск → ожидание → перебриф — потраченный
  прогон). Делегировал — доверяй результату: не переделывай и не перевыводи его выводы.

**Роутинг моделей** (выбирай по характеру работы, НЕ по умолчанию Opus):

- **Opus** — суждение: Requirements, Design, план, нетривиальный дебаг, арбитраж спорного ревью.
- **Sonnet** — механика по готовому плану: реализация, ревью, рутинные тесты, самокритика.
- **Haiku** — структурный труд: поиск по коду, маппинг файлов, тривиальные правки.

Принцип: план уже содержит рассуждение — исполнение это имплементация. Не жги Opus на пошаговое.

**Параллель:** если треков действительно несколько и они независимы (разные баги, ресёрч из
разных источников, фикс + тесты к другому модулю) — запускай их одним сообщением, а не
цепочкой. Два и больше агентов из главной сессии — сначала спроси у Danya «параллельно или
последовательно?» (лимит подписки: при параллели всё сгорает недоделанным). Вложенных
агентов это не касается.

## Самокритика — один прогон, по критерию

Держи ровно один независимый «прожарочный» прогон на срез — **сабагентом** (Sonnet,
свежий контекст), когда цена промаха реальна: срез программы, UI-проход, авторизация/
приватность/деньги, миграция БД, диф больше пары файлов. Задача агенту — сломать диф по
VireMusic-чеклисту (ниже) и gotchas: мобилка, дубли, утечки, layout-shell, краевые случаи.

На узкой правке (один файл, локальный фикс) отдельный агент не нужен — чеклист прогоняешь
сам, доказательство даёт verify-контракт ниже. Не поднимай агента, чтобы перепроверить
агента: нашёл проблемы → чини и прогоняй прожарку ещё раз только если фикс сам был крупным.

**Просьба ревьюеру/критику — на полноту, не на «только важное».** Формулируй так: «выкладывай
все находки, включая неуверенные и мелкие, с уровнем уверенности и серьёзностью; фильтрацию
сделаю отдельно». Инструкции вида «сообщай только критичное / будь консервативен» модель
исполняет буквально и молча роняет реальные баги.

## VireMusic review-чеклист (закрывает реальные промахи)

Прогоняй перед тем как сказать «готово». Каждая мысль слева = СТОП, ты рационализируешь:

| Мысль-самооправдание | Реальность |
|---|---|
| «десктоп готов» | Проверил **мобильную вёрстку**? Узкий вьюпорт, горизонтальный скролл таблиц, сайдбар→топбар. |
| «напишу компонент» | Сначала поиск готового в `packages/ui` и `apps/web/components`. Не плодить дубли — выноси общее. |
| «быстро добавлю стили» | `min-h-screen`/`h-screen` на странице/лейауте ЗАПРЕЩЕНЫ (ломают app-shell). Высоту даёт скролл-область. |
| «вынесу в useEffect/новый стейт» | Утечки, лишние ререндеры/реконсиляция, мемоизация, кеш — следи по умолчанию. |
| «поясню комментом» | Минимум комментов. Только неочевидное «почему», не «что». |
| «дизайн потом» | Принципы Impeccable применяются по умолчанию; при UI — `audit:design` обязателен. |

## VireMusic gotchas (помнить в дебаге/реализации)

- Не интерполируй JS-`Date` в raw-`sql` Drizzle — считай дату в SQL (`now() - interval '7 days'`).
- Не интерполируй колонку в `sql` внутри `.select()` — ссылайся литералом на внешнюю таблицу.
- Роль/имя/аватар кладутся в JWT при логине — после смены нужен релогин.
- Трекам нельзя ставить READY руками — без воркера нет HLS (маркер `!hls`).

## Verify-контракт (Iron Law: нет «готово» без свежего прогона)

Никаких claim'ов «работает/готово» без вывода этих команд в текущем сообщении:

```bash
pnpm --filter @vire/web typecheck
pnpm --filter @vire/web lint
pnpm --filter @vire/web check:routes
pnpm --filter @vire/web test
pnpm --filter @vire/web audit:design   # если трогали UI
pnpm --filter @vire/web build
```
