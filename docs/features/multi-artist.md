# Несколько артистов на один аккаунт (и наоборот)

Связь user ↔ artist_profile — многие-ко-многим:
- **Несколько артистов на аккаунт** — один человек управляет несколькими карточками
  (переключатель «активного» артиста в дашборде).
- **Несколько аккаунтов на артиста** — на одну карточку можно дать доступ нескольким
  аккаунтам (со-владение командой). Список доступа — таблица `artist_members`.

## Несколько аккаунтов на одного артиста (`artist_members`)

- **Модель v1 — равные co-owner:** все участники имеют полный доступ к дашборду
  артиста (релизы, треки, профиль, смартлинки). Права по ролям не разводятся.
- **Роль хранится** (`OWNER` | `MEMBER`): `OWNER` — создатель карточки, его нельзя
  снять (профиль не должен остаться без владельца). `MEMBER` — добавленный аккаунт.
- **Добавляет админ** в бэкоффисе `/admin/artists` → кнопка «Участники» (поповер):
  список доступа + добавить по email существующего аккаунта + снять (кроме OWNER).
  Self-service/инвайты — на будущее.
- **`artist_profiles.user_id`** остаётся указателем на владельца (для отображения,
  нотификаций); **контроль доступа к дашборду** идёт через `artist_members`.
- **Доступ:** добавленный аккаунт видит карточку в переключателе артистов и работает
  с ней как со своей (через тот же `active-artist` резолвинг).

### Где код (аккаунты на артиста)
- **Схема/миграция:** `packages/db/src/schema/artists.ts` (`artist_members`),
  миграция `0024` (+ бэкфил: текущий `user_id` каждого профиля → OWNER-строка).
- **Доступ:** `packages/db/src/repositories/artist.ts` — `findByUserId`,
  `findAllByUserId`, `findByIdForUser` джойнят через `artist_members`.
- **Создание:** `createArtistForUser` пишет OWNER-членство в транзакции.
- **Админ-управление:** `packages/db/src/queries/admin-artists.ts`
  (`listArtistMembers`/`addArtistMember`/`removeArtistMember`), server actions в
  `app/admin/actions.ts`, UI `app/admin/artists/members-manager.tsx`.

---

Один пользователь может управлять несколькими карточками артиста. В дашборде —
переключатель «активного» артиста; все операции скоупятся на выбранного.

## Что делает
- **Создаёт только админ** (`/admin/users` → «Создать артиста»): можно привязать
  несколько артистов к одному email (slug глобально уникален). Self-service нет.
- **Активный артист** хранится в cookie `vire_active_artist`. Дашборд, профиль,
  релизы, треки, посты, live — всё работает в контексте активного артиста.
- **Переключатель** в шапке дашборда (показывается при >1 артисте) — меняет cookie
  и перезагружает данные.
- **Безопасность владения:** активным может стать только артист, принадлежащий
  пользователю (проверка `findByIdForUser`); подмена cookie невозможна — при
  «чужом» id helper падает на дефолтного (первого) артиста.

## Где код
- **Резолвинг:** `apps/web/lib/active-artist.ts`
  - `getActiveArtist(userId, req)` — для route handlers (cookie из `Request`);
  - `getActiveArtistForPage(userId)` — для серверных компонентов (next/headers);
  - `resolveActiveArtist(userId, id?)` — общая логика (id → проверка владения,
    иначе дефолт `findByUserId`);
  - `listUserArtists(userId)` — все артисты пользователя.
- **Гейт «свой трек»:** `apps/web/lib/require-owned-track.ts` — `requireOwnedTrack(req, id)`
  собирает всю цепочку артист-периметра (авторизован → активный артист → трек существует →
  релиз принадлежит этому артисту) и возвращает результат-значение, как `require-access.ts`.
  Роуты `dashboard/tracks/[id]/*` идут через него, а не повторяют проверку каждый у себя.
- **Переключение:** `app/api/v1/dashboard/active-artist/route.ts` (POST, ставит cookie),
  UI — `app/dashboard/artist-switcher.tsx`.
- **Репозиторий:** `packages/db/src/repositories/artist.ts` — `findAllByUserId`,
  `findByIdForUser`, `findByUserId` (теперь с детерминированным порядком по createdAt).
- **Создание:** `packages/db/src/queries/admin-artists.ts` `createArtistForUser` — снят блок
  «уже есть профиль»; промоушен до ARTIST по-прежнему только для LISTENER.
- Все dashboard-роуты/страницы резолвят артиста через `active-artist` вместо
  прямого `findByUserId`.

## Env
- Не требуется.

## Ограничения / на будущее
- Создание доп. артистов — только админ (по решению). Self-service с лимитом —
  на будущее, если понадобится.
- Активный артист — общий для всех вкладок (cookie), без per-tab контекста.
- Редактировать ресурсы можно только у активного артиста — чтобы тронуть другого,
  нужно переключиться (намеренно: исключает случайные кросс-правки).
- Удаление/деактивация артиста с переносом владения релизами — отдельная задача.
