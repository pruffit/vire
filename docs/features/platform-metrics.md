# История метрик платформы

Ежедневный снапшот ключевых показателей платформы в Postgres — история переживает
удаления (unlike/unfollow/удаление плейлиста стирают строки в живых таблицах) и
возможную будущую чистку `play_events`.

## Что делает

- Каждую ночь в 00:10 МСК воркер считает «вчера» и пишет одну строку снапшота:
  тоталы (пользователи/артисты/опубликованные релизы/готовые треки/лайки/подписки/
  плейлисты/посты) на конец дня + прослушивания и уникальные слушатели за сам день.
- `/admin/analytics` показывает секцию «История платформы» — графики роста
  пользователей/лайков/подписок за 30/90/180 дней (табы `?days=`).

## Где код

- **Данные:** `packages/db/src/schema/analytics.ts` — таблица `platform_metrics_daily`
  (`day` — PK date; остальные — int, default 0). Миграция `0036_lame_magus.sql`
  включает бэкфил истории до первого прогона джобы.
- **Запросы:** `packages/db/src/queries/metrics.ts` — `snapshotPlatformMetricsDaily(day)`
  (идемпотентный `INSERT … ON CONFLICT (day) DO UPDATE`), `getPlatformMetricsHistory(days)`.
- **Джоба:** `apps/worker/src/workers/metrics.worker.ts` + очередь `QUEUE_METRICS`
  (`packages/core/src/jobs.ts`), крон-шедулер в `apps/worker/src/index.ts`
  (`upsertJobScheduler('metrics-daily', { pattern: '10 0 * * *', tz: 'Europe/Moscow' })`).
  Дата «вчера по МСК» — чистая функция `yesterdayMsk` (`apps/worker/src/lib/msk-date.ts`),
  не зависит от TZ хоста (только UTC-геттеры + фиксированный +3, МСК без DST).
- **UI:** `apps/web/app/admin/analytics/page.tsx` — `PlatformHistory`/`GrowthChart`.

## Погрешность бэкфила

Миграция восстанавливает историю по `created_at` (а для релизов — по `published_at`,
для готовых треков — по текущему статусу `READY` + `updated_at`, точной истории смены
статусов нет). Это **приближение**:
- удалённые лайки/подписки/плейлисты/посты не восстановить — их «вычитание» из истории
  не отражено, ряд может казаться немного выше, чем было на самом деле в моменте;
- трек, который был READY и позже заблокирован, выпадает из всей исторической кривой
  (не только с текущего дня) — используется текущий статус, не исторический;
- релиз, опубликованный и затем архивированный, наоборот — учтён на всех днях после
  `published_at`, так как `published_at` не сбрасывается при архивации.

После первого ночного прогона джобы новые дни считаются точно на момент снапшота —
погрешность касается только бэкфилленной части истории.

## Ограничения / на будущее

- Графики роста в UI — только `users`/`likesTotal`/`followsTotal`; остальные поля
  таблицы (`artists`, `releasesPublished`, `tracksReady`, `plays`, `listeners`,
  `playlistsTotal`, `postsTotal`) собираются и хранятся, но пока не визуализированы.
- Снапшот считает по всей платформе, без разбивки по артисту/жанру.
