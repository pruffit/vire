# Токены устройств (Bearer)

Аутентификация для нативных клиентов: приложение получает пару токенов и ходит с
`Authorization: Bearer`. Веб продолжает жить на cookie-сессии Auth.js — путь не тронут.

## Что делает

- `POST /api/v1/auth/devices` — обмен **доказанной cookie-сессии** на пару токенов.
  Вызов с Bearer отвергается (403): новое устройство заводится только из браузера, поэтому
  второй поверхности проверки пароля не появляется.
- `POST /api/v1/auth/refresh` — обмен refresh на новую пару с ротацией.
- `GET /api/v1/auth/devices` — список своих активных устройств, текущее помечено `current`.
- `DELETE /api/v1/auth/devices/{deviceId}` — отзыв; чужое устройство не отзывается и его
  существование не подтверждается (тот же ответ, что для несуществующего).
- Любой роут `app/api/**` принимает Bearer автоматически: актор берётся через `getCaller()`,
  и потребителям неизвестно, чем доказана личность (барьер `check:caller`).

## Модель токенов

| | Access | Refresh |
|---|---|---|
| Формат | `base64url(payload).HMAC-SHA256` | 32 случайных байта, base64url |
| Живёт | 15 минут | 30 суток |
| Хранится в БД | нет | только sha256-хэш |
| Содержит | `sub`, `role`, `did`, `iat`, `exp` | ничего (непрозрачный) |

Подпись — секретом `LINK_SIGNING_SECRET` (фолбэк `AUTH_SECRET`). Секрета нет → Bearer не
принимается вовсе.

## Что защищено и как

- **Подмена роли в теле токена** ломает подпись; сравнение подписи — в постоянном времени.
- **Ротация**: старый refresh недействителен сразу после обмена.
- **Повторное использование** refresh отозванного устройства трактуется как утечка и отзывает
  **все** устройства владельца.
- **Понижение прав доезжает**: роль перечитывается из БД на каждой ротации, а не берётся из
  старого токена. Исчезнувший владелец обрывает доступ.
- **Отзыв действует не позже 30 секунд** — TTL кэша состояния устройства; на самом отзыве и
  на неудачном refresh кэш сбрасывается явно, то есть обычно мгновенно.
- **Rate limit**: 10 регистраций/час, 30 обменов/час на клиента.
- Ответы с токенами — `Cache-Control: no-store`; наружу не уходят ни хэш refresh, ни его срок.

## Env

`LINK_SIGNING_SECRET` (или `AUTH_SECRET`) — подпись access-токенов. Отдельного секрета
не требуется, но ротация независимо от Auth.js возможна через `LINK_SIGNING_SECRET`.

## Проверено

Юнит-тесты (подпись/срок/подмена/ротация/reuse/отзыв — 21 тест в core, 14 на `getCaller`,
11 на роутах) и прогон на живой базе: пара выдаётся, refresh в БД лежит хэшем, ротация меняет
токен, старый refresh отвергается, после отзыва обмен невозможен.

## Ограничения / на будущее

- **Первый вход мобильного клиента идёт через веб-сессию**: приложение открывает браузер,
  логинится, вызывает `POST /v1/auth/devices`. Отдельного device-code flow нет — он нужен для
  устройств без браузера (ТВ), а таких клиентов не планируется.
- Access не отзывается точечно: отзыв устройства действует через кэш состояния (≤30 с) —
  компромисс между «одна лишняя выборка на запрос» и «мгновенным» отзывом.
- `lastUsedAt` обновляется на ротации, а не на каждом запросе: иначе каждый запрос с Bearer
  превращался бы в запись в БД.
- Экрана управления устройствами в UI нет — только API; появится вместе с мобильным клиентом.
