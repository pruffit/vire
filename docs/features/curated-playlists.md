# Подборки на главной (редакционные + личные)

Секция «Подборки» на главной = **две группы по 4 карточки**:
- **Общие** — одинаковы для всех, обновляются раз в сутки в 00:00 (МСК).
- **Личные** — генерятся под каждого юзера по его вкусу, обновляются раз в 4 часа.
  Гостю/новому юзеру без сигнала личную половину закрывает фолбэк на популярное —
  сетка всегда полная.

Не путать с пользовательскими плейлистами (`docs/features/interactions.md`) — те
создаёт сам слушатель.

## Что делает

### Общие (shared)
- `Сейчас набирает` (TRENDING) — топ прослушиваний за 7 дней.
- `Свежее` (FRESH) — последние опубликованные треки.
- `Возвращаются снова` (RELISTEN) — треки, к которым **один и тот же** слушатель
  вернулся минимум в 2 разных дня за 30 дней. Возвраты считаются по слушателю
  (`COALESCE(user_id::text, session_id)` — аноним учитывается, не только
  залогиненные), а на трек берётся **число вернувшихся слушателей**, по нему и
  сортировка. Это не «сколько всего разных дней трек играли» (популярный трек,
  который каждый день слушают *разные* люди, порог не проходит).
- Топ-настроения (MOOD) — **только 3 самых наполненных** (раньше генерились все
  18; лишние mood-подборки удаляются при каждом прогоне); топ-3 считается по числу
  **видимых** треков настроения; треки внутри — по силе совпадения и популярности
  за 30 дней + свежести (`selectCandidatesByTaste`, ниже).
- **Видимость**: все источники (TRENDING/FRESH/RELISTEN/MOOD/филлер) фильтруются
  единым `visibleTrackWhere` (`wave.ts`) — READY + публичный релиз + активный артист
  (`is_active`). Скрытый/заблокированный артист или трек в подборку не попадёт.
- Показ: приоритет TRENDING → FRESH → MOOD → RELISTEN, берём 4.
- **Всегда полные + разнообразие по артистам**: пороги (`MIN_TRACKS`) проверяются
  по подлинным совпадениям, после чего `composePlaylist` (`editorial-policy.ts`)
  собирает финальный список до 25 треков. Политика (чистая функция, юнит-тесты):
  подлинные совпадения идут первыми, но артист сверх `MAX_PER_ARTIST` (3)
  **откладывается** в хвост, а не выбрасывается — так свежий альбом на 12 треков не
  занимает пол-FRESH подряд. Порядок приоритета: (1) genuine с cap, (2) отложенный
  хвост genuine (cap снят — подлинное всегда важнее филлера), (3) пул вне занятого с
  cap, (4) пул вне занятого без cap, (5) занятый пул. Cap — мягкий: на тонком
  каталоге (мало артистов) он физически недостижим и корректно уступает, лишь бы
  карточка была полной. Пул филлера (`getFillerPool` — видимые треки по популярности
  за 30 дней, при равенстве свежие, до 500) считается один раз на прогон; общий для
  прогона набор занятого филлера не даёт хвостам TRENDING/FRESH/RELISTEN/MOOD сойтись
  к одному топу (переиспользование — только когда незанятый пул исчерпан).

### Личные (personal)
- Сигнал: единый профиль вкуса `getTasteProfile` — лайки ∪ прослушивания за 90 дней →
  топ-5 настроений и топ-5 жанров этих треков (`packages/db/src/queries/taste.ts`).
- Генерим до 4: «Для тебя» (микс по топ-настроениям **и** топ-жанрам, трек попадает,
  если совпал хотя бы один mood ИЛИ жанр) + mood-подборки под вкус, каждая без
  пересечения с уже собранными (exclusion set внутри одного прогона).
- **Дедуп с общими MOOD-подборками**: перед генерацией личных mood-подборок читаем
  настроения текущих общих MOOD-подборок (обратный маппинг заголовка через
  `MOOD_LABELS`) и пропускаем их — `pickPersonalMoods` (`editorial-policy.ts`) берёт
  следующие по значимости настроения из профиля вкуса. Иначе на главной одно и то же
  настроение показывается дважды («Для дороги» и «Для дороги — для тебя»).
- **Порог размера**: ни микс «Для тебя», ни mood-подборка не создаются, если
  подлинных совпадений меньше `MIN_PERSONAL_PLAYLIST_TRACKS` (5, `editorial-policy.ts`);
  для mood-подборок порог считается **до** фильтра эксклюзией — то, что часть
  треков настроения уже разобрал микс «Для тебя», не отменяет вкусового сигнала.
  Прошедшие порог добиваются `composePlaylist` до 25 из общего пула прогона (тот же
  artist-cap `MAX_PER_ARTIST`, что и у общих); филлер избегает уже собранных карточек
  юзера (exclusion set), переиспользует их только при исчерпании пула. Если даже так
  не набралось 25 (каталог меньше лимита) — подборка **не публикуется**: лучше меньше
  карточек, но все полные.
- Нет сигнала (< 3 уникальных лайкнутых/прослушанных треков за 90 дней, порог
  проверяется отдельно до вызова `getTasteProfile`) → личные подборки удаляются.
- **Ранжирование по силе совпадения**: треки внутри подборки сортируются сначала по
  `matchScore`, затем по популярности за 30 дней (`popularityScoreSql`), затем по
  свежести релиза. `matchScore = (совпал mood ? 1) + (совпал жанр ? 1) + (артист из
  топ-любимых профиля вкуса ? 2)` — так трек любимого артиста, совпавший и по
  настроению, и по жанру, поднимается наверх, а не тонет под глобальным топом. Раньше
  ранжирование шло только по популярности, а `topArtistIds` профиля не использовался.
  Выбор по mood/genre/affinity для микса и mood-подборок — одна функция
  (`selectCandidatesByTaste(moods, genres, affinityArtistIds)`, `editorial.ts`): для
  «Для тебя» передаём `(topMoods, topGenres, topArtistIds)`, для личных mood-подборок
  `([mood], [], topArtistIds)`, для общих MOOD `([mood], [], [])` (affinity нет —
  порядок остаётся популярностным). Веса CASE — `sql`-литералы (bind-параметры в CASE
  Postgres типизирует криво).
- Хранятся как `playlists` с `kind='PERSONAL'`, `target_user_id=<юзер>`, `is_curated=true`.
  В личный список юзера не попадают (там фильтр по `owner_user_id`).

## Где код
- **Генерация:** `packages/db/src/queries/editorial.ts`
  (`generateSharedPlaylists`, `generatePersonalPlaylists`,
  `generatePersonalPlaylistsForAllUsers`, `generateAllEditorialPlaylists`).
- **Политика (чистые функции, юнит-тесты):** `packages/db/src/queries/editorial-policy.ts`
  (`composePlaylist`, `MAX_PER_ARTIST`, `PlaylistCandidate`,
  `MIN_PERSONAL_PLAYLIST_TRACKS`, `hasEnoughTracksForPersonalPlaylist`, `pickPersonalMoods`) —
  без БД, `pnpm --filter @vire/db test`. `composePlaylist` работает с
  `PlaylistCandidate = { trackId, artistId }` (artistId нужен для artist-cap); все
  SQL-источники editorial возвращают этот тип.
- **Запросы для главной:** `packages/db/src/queries/playlist-editorial.ts`
  (`getEditorialPlaylists` — общие, `getPersonalPlaylists`, `getPopularPlaylists` — фолбэк).
  Коллаж обложек и досчёт трек-каунта — общие с пользовательскими плейлистами,
  живут в `packages/db/src/queries/playlist-meta.ts`.
- **Расписание:** воркер `apps/worker/src/workers/editorial.worker.ts` + планировщики
  в `apps/worker/src/index.ts` (`upsertJobScheduler`: `shared-daily` cron `0 0 * * *`,
  `personal-4h` cron `0 */4 * * *`, tz `Europe/Moscow`).
- **Ручной прогон:** `/admin` → «Обновить подборки» → `POST /api/v1/admin/editorial`
  (`generateAllEditorialPlaylists` — общие + личные).
- **UI:** `apps/web/app/[locale]/(listener)/(home)/page.tsx` (секция «Подборки»), `components/editorial-playlist-card.tsx`.
- **Схема:** `playlists.kind` enum (+`PERSONAL`), `playlists.target_user_id`
  (миграция `0017`).

## Ограничения / на будущее
- Личные пересобираются целиком (delete + insert), а не диффом — проще, при росте
  числа юзеров можно оптимизировать.
- Персонализация учитывает и настроения, и жанры (`track_genres`) — общий
  профиль вкуса `getTasteProfile`, тот же, что использует волна (см. [wave](wave.md)).
  Профиль материализован в таблице `taste_profiles` (point-lookup по PK), пересчёт —
  первым шагом `generatePersonalPlaylistsForAllUsers` (до самой генерации подборок,
  тем же прогоном); поверх — L1 TTL-кэш на 60с на процесс (`createTtlCache`, потолок
  500 записей, `packages/db/src/queries/taste.ts`), `clearTasteProfileCache()` для
  тестов. Живой расчёт (3 group-by) — только фолбэк для юзера без материализованной
  строки.
- Личные подборки `visibility=PUBLIC` (доступны по прямой ссылке) — id не
  раскрывается, но строгой приватности нет.
- Планировщик — per-process; при нескольких репликах воркера `upsertJobScheduler`
  идемпотентен (один scheduler по id), дублей джобов не будет.
