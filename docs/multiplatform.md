# Мультиплатформенность — стратегия клиентов

**Статус:** предложение (Phase 1) · **Основание:** `architecture-audit.md`, `architecture.md`

---

## 1. Что общее, что платформенное

Требование задания — **не делать один визуальный UI на все платформы**. Оно верное:
приложение, одинаково выглядящее в iOS и на вебе, выглядит чужим в обоих.

| Общее (пишется один раз) | Платформенное (своё на каждой) |
|---|---|
| Доменные контракты (`@vire/api-contracts`) | Рендерер и вёрстка |
| HTTP API | Навигация и переходы |
| Бизнес-правила (`@vire/core`) | Жесты, анимации, нативные контролы |
| Дизайн-токены (JSON) | Аудио-движок |
| SDUI-схема и состав блоков | Хранилище и офлайн |
| Ядро плеера (очередь, транспорт) | Пуш-уведомления, системная интеграция |

Граница проходит по одному признаку: **правило — общее, ощущение — платформенное.**

## 2. Целевой набор клиентов

Четыре клиента, все подтверждены как цель:

| Клиент | Статус | Роль |
|---|---|---|
| **Web (Next.js)** | в проде | Основной, источник требований |
| **PWA** | в проде с v1.45.0 | Не отдельный клиент, а свойство веба: установка, офлайн-медиатека, экран «Скачанное». Остаётся как базовый уровень и точка входа без установки |
| **Mobile (iOS/Android)** | строим | Фоновое воспроизведение, пуши, офлайн — на iOS PWA этого не даёт |
| **Desktop (Windows/macOS)** | **строим** | Полноценное приложение: медиа-клавиши ОС, глобальные горячие клавиши, системный трей, мини-плеер поверх окон, автозапуск, локальные файлы, дистрибуция вне браузера |

Срез 0 сделан (16.08.2026): `apps/desktop` — минимальная Tauri v2 оболочка вокруг
веб-фронта, без нового UI и без нативных фич из правой колонки выше (те — предмет
следующих срезов). Проверяет связку Tauri + существующий веб на реальной
не-браузерной платформе. Детали — `docs/features/desktop-app.md`. Статус клиента в
таблице остаётся «строим» — срез 0 не закрывает десктоп-клиент целиком.

PWA и десктопное приложение не исключают друг друга: PWA — нулевой порог входа,
десктоп — то, чего браузер не даёт в принципе. Список в правой колонке — это ровно
те возможности, которые упираются в песочницу браузера, а не в качество реализации.

## 3. Стек клиентов

### 3.1 Мобильный — React Native + Expo

| Вариант | За | Против |
|---|---|---|
| **React Native + Expo** (рекомендую) | Контракты и типы из `@vire/api-contracts` переиспользуются **напрямую**, без кодогенерации. Один язык на весь стек — критично для одного разработчика с AI. `react-native-track-player` закрывает фоновое воспроизведение, HLS, lock-screen контролы, офлайн. Одна кодовая база на iOS и Android | Ощущается менее нативно в мелочах. Часть системной интеграции — через мосты |
| Нативные Swift + Kotlin | Максимальное качество ощущения, полный доступ к платформе | Две кодовые базы, два языка, генерация типов из OpenAPI/JSON Schema, кратный объём работы. Для одного разработчика — нереалистично при сроке «второй продукт через 3–6 мес» |
| Kotlin Multiplatform | Общая логика, нативный UI | Не переиспользует TS-контракты — нужен третий язык рядом с TS-бэкендом |

**Рекомендация — React Native + Expo.** Решающий довод не в самом RN, а в контрактах:
при TS-клиенте единый источник правды работает буквально (`z.infer` из тех же схем),
а при Swift/Kotlin между сервером и клиентом появляется генератор, который нужно
поддерживать и который расходится молча.

### 3.2 Десктопный — развилка

| Вариант | За | Против |
|---|---|---|
| **Tauri v2** (рекомендую) | Бинарник ~10–15 МБ против ~120 МБ у Electron, потребление памяти в разы ниже. Переиспользует **уже готовый веб-фронт** целиком — десктоп получается из существующего кода, а не пишется заново. Нативная часть на Rust даёт медиа-клавиши, трей, глобальные хоткеи, автозапуск, доступ к ФС для локальных файлов. Автообновление из коробки | Системный webview различается (WebView2 на Windows, WKWebView на macOS) — нужен прогон обеих платформ. Rust в стеке, хотя писать на нём придётся мало |
| Electron | Один Chromium везде — ноль расхождений рендеринга. Максимально зрелая экосистема для медиа-приложений | 120+ МБ бандл, заметное потребление памяти, отдельный процесс обновления. Chromium тянет за собой цикл обновлений безопасности |
| React Native for Windows/macOS | Общая кодовая база с мобильным клиентом | Зрелость заметно ниже мобильной RN; десктопный UX (окна, меню, хоткеи) пришлось бы строить с нуля, тогда как веб-версия уже готова |

**Рекомендация — Tauri v2.** Ключевой довод: у вас **уже есть отполированный веб-клиент
и PWA с офлайн-медиатекой**. Tauri превращает его в настоящее приложение, добавляя ровно
недостающий системный слой, вместо того чтобы строить четвёртый UI. Мобильный клиент при
этом остаётся на RN — это осознанное различие: там нужен нативный UX с нуля, здесь нужен
системный доступ к готовому UI.

**Что даёт десктоп поверх PWA практически:** медиа-клавиши и управление с гарнитуры,
глобальные хоткеи при свёрнутом окне, мини-плеер поверх других окон, трей с управлением,
автозапуск при входе в систему, полноценный доступ к локальной библиотеке файлов
(в плеере уже есть режим локальных файлов), дистрибуция установщиком и подпись.

Решение по обоим стекам фиксируется до Phase 8; на архитектуру Core не влияет — влияет
только на форму контрактов (TS-типы против генерации).

## 4. Аутентификация нативного клиента

**Сегодня:** Auth.js JWT в httpOnly cookie. Нативному клиенту не подходит.

**Задел, который уже есть:** HMAC-подписанные гостевые сессии в джем-комнатах
(`lib/session-signing.ts`) — рабочий шаблон токена, просто применённый к одному домену.

**Целевая схема:**

```
POST /api/v1/auth/token     { credentials | oauth code, device }
   → { accessToken (15 мин), refreshToken (ротируемый), deviceId }

POST /api/v1/auth/refresh   { refreshToken }
   → новая пара; старый refresh инвалидируется (ротация)

DELETE /api/v1/auth/devices/{id}   — отзыв устройства
```

- Access — короткий JWT, проверяется без БД.
- Refresh — ротируемый, привязан к записи в `devices`, отзывается по устройству.
- Веб продолжает работать на cookie; API принимает оба через **один адаптер** `getCaller()`.

Последнее важно: `auth()` вызывается в 60+ файлах. Правка широкая, но механическая —
один хелпер вместо прямого вызова, дальше всё едино. Побочная выгода: короткий access-токен
естественно снимает существующую боль «после смены роли нужен релогин».

**Что НЕ делаем:** свой OAuth-сервер и полноценный OIDC. Не нужен — клиенты свои.

## 5. Ядро плеера

Аудит нашёл готовый к переносу актив: `apps/web/lib/player/queue.ts` — **100% чистые
функции** (Fisher-Yates, включение/выключение shuffle с сохранением текущего трека,
окно персиста вокруг текущего индекса, ограничение live-очереди, вставка в очередь),
с нетривиальными краевыми случаями вроде `repeat=all` на единственном треке.

Это ровно тот код, который мобильный клиент **либо скопирует, либо перепишет и разойдётся
багами**. Перенос дешёвый, а цена бездействия высокая.

**Разрез плеера:**

```
Общее (@vire/core → platform/playback или music/playback):
  очередь, порядок, shuffle, repeat, переходы транспорта,
  синхронизация джема (offset/drift), правила «что играть дальше»

Платформенное (за портом IAudioEngine):
  play/pause/seek/загрузка манифеста, буферизация, вывод звука
```

```ts
interface IAudioEngine {
  load(src: { manifestUrl: string; startAt?: number }): Promise<void>;
  play(): Promise<void>; pause(): void; seek(sec: number): void;
  on(event: 'timeupdate'|'ended'|'stalled'|'error', cb): Unsubscribe;
}
```

Веб реализует через hls.js + `<audio>`, мобильный — через `react-native-track-player`.

**Отдельная работа, отмеченная аудитом:** `audio-engine.ts` (663 строки) сейчас мешает
логику решений с вебовым вводом-выводом и держит мутабельное состояние на уровне модуля.
Его расщепление — предусловие переноса, а не следствие.

## 6. Дизайн-токены и общие примитивы

**Статус (16.08.2026): платформенные токены экспортированы** — `packages/design-tokens`
(`tokens.json` источник правды + генераторы CSS/TS), подробности `docs/features/design-tokens.md`.
Артист-тема остаётся как есть (см. ниже) — это следующий шаг, не часть текущего экспорта.

**Было:** токены жили как CSS-переменные (OKLCH) и Tailwind-пресет. Артист-тема
применяется inline `color-mix()` в 25+ местах одного файла — не токенизирована.
За пределами `packages/ui` (2 компонента) существуют два независимых словаря
Tailwind-классов: `ui-kit.tsx` (25 экспортов, уже общий для админки и дашборда)
и `content-kit.tsx` («маркетинговый регистр»).

**Цель:** платформо-нейтральный источник токенов.

```
packages/design-tokens/tokens.json     ← источник правды
        ├── CSS-переменные   (веб)
        ├── TS-объект        (React Native)
        └── JSON             (нативные клиенты, если появятся)
```

Токены переносимы (цвет, размер, отступ, радиус, длительность). **Tailwind-классы
не переносимы** — `className="px-4 text-sm"` не существует в SwiftUI и Compose.
Поэтому в общий слой уходят токены, а не компоненты веба.

**Три слоя темизации сохраняются** как есть: нейтральная оболочка → тема артиста из
`theme_tokens` → плеер с акцентом текущего релиза. Эта модель уже данные-ориентированная
и переносится прямо; работа только в том, чтобы вывести артист-тему из inline `color-mix()`
в токены.

**В `packages/ui` переезжают** (по правилу «сначала директория, потом пакет» — по мере
реального переиспользования): `popover`, `sheet`, `toast`, `select`, `scroll-row`,
`date/number/color-field`, `icon`, `page-container`, generic-часть `ui-kit` (`Table`,
`Panel`, `StatCard`). **Не переезжают**: `RoleBadge`, `TrackStatusBadge`,
`ReleaseStatusBadge` — доменные, остаются рядом с продуктом.

## 7. Реалтайм

Три SSE-канала: мультиплексированный `realtime/stream` (чат + уведомления),
`jam/stream`, `playlists/stream`.

SSE как протокол переносим. Непереносима клиентская обёртка `use-realtime.ts` —
она построена на браузерном `EventSource`. Для RN нужна своя реализация разбора потока
(либо polyfill, либо `fetch` со стримом).

**Решение:** сохранить SSE, вынести обработку событий за порт. Переход на WebSocket
не рекомендую: SSE проще, переживает прокси, уже работает, и на 1 ГБ RAM держать
WebSocket-сервер дороже.

## 8. Офлайн и хранилище

Веб-реализация офлайна — ручная сегментация HLS в Cache Storage/IndexedDB. Это самая
веб-специфичная часть системы, и переносить её **не нужно**: у мобильных платформ есть
свои загрузчики (`react-native-track-player` умеет офлайн-треки штатно).

Общее здесь — не код, а **контракт библиотеки**: что скачано, кому принадлежит,
когда истекает, как связано с аккаунтом. Он уже существует (библиотека привязана к аккаунту)
и переносится как правило, а не как реализация.

---

## 9. Пуш-уведомления

Веб — VAPID/web-push. Мобильные — APNs/FCM. Общая часть — **решение о доставке**:
`decideExternalDelivery` в core уже чистая функция без музыки и без вебовой специфики.

Core получает реестр каналов (`platform/notifications`), провайдеры подключаются
реализациями порта. Локаль получателя берётся из БД на момент отправки — существующее
правило, оно и так корректно для любого клиента.

**Известный хвост:** VAPID на VPS не докатан.

## 10. Contract-тесты — то, что удерживает всё вместе

Единственный механизм, который не даёт серверу и клиентам разойтись молча:

```
zod-схема в @vire/api-contracts
   ├── сервер: ответ роута парсится этой схемой в тесте
   └── клиент: тот же импорт (TS) или сгенерированный тип (не-TS)
```

Расхождение падает в CI, а не в проде на телефоне пользователя, где откат стоит недели
ревью в сторе. Для мобильного клиента это не «хорошая практика», а условие
выживаемости релизного цикла.

Дополнительно: тест совместимости — клиент версии N−1 не получает блоков SDUI и полей,
которых не понимает (`sdui.md` §5).

## 11. Критерий готовности к новым клиентам (приёмка Phase 8)

Проверяется фактами, не ощущением:

- [ ] Каждый экран первой версии приложения собирается **только** из вызовов `/api/v1`.
      Ни одного случая «на вебе это читается напрямую из БД, а для мобилки надо дописать».
- [ ] Bearer-обмен работает, устройство отзывается, refresh ротируется.
- [ ] Контракты первой группы сущностей импортируются из одного пакета.
- [ ] Ядро плеера (очередь/транспорт) вызывается из общего кода; платформенным остаётся
      только `IAudioEngine`.
- [ ] Токены отдаются в платформо-нейтральном формате.
- [ ] Composite-тест: **посчитать строки бизнес-логики, скопированные из веба в мобильный
      клиент. Цель — ноль.** Любая копия означает, что граница проведена не там.

Последний пункт — главный. Он и есть проверка всей затеи: платформа удалась ровно
настолько, насколько мобильному клиенту нечего копировать.

## 12. Порядок

1. Read-path в HTTP (`migration-plan.md`) — без этого мобильному клиенту нечего вызывать.
2. Bearer-auth + устройства.
3. Контракты первой группы + contract-тесты.
4. Вынос ядра плеера и расщепление `audio-engine.ts`.
5. Экспорт токенов ✅ (16.08.2026) — `packages/design-tokens`.
6. SDUI на главной — до новых клиентов, чтобы протокол был обкатан на вебе,
   где откат бесплатный.
7. **Десктопный клиент (Tauri)** — раньше мобильного: переиспользует готовый веб-фронт,
   значит проверяет Bearer-auth, контракты и ядро плеера на реальном не-браузерном
   клиенте при кратно меньшем объёме новой работы. Ошибки в границах вылезут здесь,
   и чинить их будет дешевле, чем в мобильном приложении с релизным циклом через стор.
8. Мобильный клиент (RN + Expo).

Пункты 1–5 полезны VireMusic сами по себе и не требуют решения ни о мобильном,
ни о десктопном клиенте. Это не совпадение, а критерий, по которому они отобраны.

Порядок 7 → 8 — рекомендация, а не жёсткая зависимость: клиенты независимы и могут
идти параллельно, если так удобнее. Довод в пользу десктопа первым — он дешевле
как проверка архитектуры.
