## 2. Центральный принцип: сначала директория, потом пакет

Аудит дал прямое доказательство против создания пакетов «под будущего жильца»:
`packages/ui` (2 компонента при реальном ките на 25 в `apps/web`), `api-contracts`
(3 файла при 48 реальных схемах), `packages/media` (пуст). Пустой пакет не притягивает код.

**Правило:**

> Граница сначала существует как **директория внутри имеющегося пакета** и защищается
> правилом линтера. Она становится **отдельным пакетом только тогда, когда у неё
> появляется второй физический потребитель.**

Почему это работает лучше:
- перенос файла между директориями — один коммит, тривиальный откат;
- выделение пакета — `package.json`, tsconfig, сборка, версия, публикация, правка импортов
  во всех потребителях;
- граница, которая не выдержала проверки, откатывается бесплатно на первом варианте
  и дорого на втором.

Практически это значит: `@vire/core` внутри разделяется на `platform/` и `music/` **сразу**,
а на два пакета — в момент появления `apps/video-web`.

## 3. Целевая схема слоёв

```
        ┌──────────────┬──────────────┬──────────────┐
        │  Web (Next)  │    Mobile    │   Desktop    │
        └──────┬───────┴──────┬───────┴──────┬───────┘
               │              │              │
      in-process│         HTTP │         HTTP │
               │              │              │
        ┌──────┴──────────────┴──────────────┴───────┐
        │   API-слой: app/api/v1 (contract-typed)     │
        └──────────────────────┬──────────────────────┘
                               │
        ┌──────────────────────┴──────────────────────┐
        │  Application services  @vire/core           │
        │  ┌────────────────┐  ┌───────────────────┐  │
        │  │  platform/     │←─│  music/           │  │
        │  │  (Core)        │  │  (Domain)         │  │
        │  └────────────────┘  └───────────────────┘  │
        └──────────────────────┬──────────────────────┘
                               │  ports (интерфейсы)
        ┌──────────────────────┴──────────────────────┐
        │  Infrastructure: db · storage · queue ·      │
        │  mail · payments · presence · search         │
        └──────────────────────┬──────────────────────┘
                               │
              Postgres · Redis · S3 · внешние API
```

Направление зависимостей строго вниз. `music/` **может** зависеть от `platform/`;
`platform/` от `music/` — **никогда**. Это единственное правило, которое делает
второй продукт возможным, и оно проверяется автоматически (§8).

## 4. Ключевое решение: одна реализация, два входа

Аудит показал главный блокер: 27/53 страниц читают БД напрямую, HTTP-эквивалента нет.

Напрашивающееся «заставить страницы ходить в свой же HTTP» — **неверное решение**:
лишний сетевой хоп внутри одного процесса, потеря стриминга RSC, деградация TTFB,
и всё это на одном VPS (2 ядра / 2 ГБ).

Правильное:

> Логика чтения существует **в одном месте** — как read-сервис в `@vire/core`.
> У него **два входа**: Server Component вызывает его в процессе, HTTP-роут вызывает
> его же и сериализует через контракт.

```
                    ┌─────────────────────────┐
   Server Component─┤                         │
                    │  ReleaseCatalogService  ├──→ IReleaseReadRepository ──→ Postgres
   /api/v1/releases─┤   (packages/core)       │
                    └─────────────────────────┘
                              ↑
                    единственная реализация
```

Что это даёт: веб не теряет ни миллисекунды и ни строчки текущего поведения; мобильный
клиент получает эндпоинт; расхождение двух реализаций (которое **уже произошло** —
`/v1/artists/[slug]` существует и не используется страницей артиста) становится
структурно невозможным.

Практический путь: 48 файлов `packages/db/src/queries` поднимаются в core как read-сервисы
за портами — по одному ресурсу за раз, не пакетом.

## 5. Разделение `@vire/core`

```
packages/core/src/
├── platform/                    ← будущий @vire/platform-core
│   ├── identity/                auth, session, device, user-directory
│   ├── access/                  roles, permissions, can(), policy
│   ├── organizations/           org profile, membership, roles в организации
│   ├── billing/                 purchase, subscription, plan, entitlement
│   ├── media/                   MediaAsset, ProcessingJob, upload policy
│   ├── notifications/           event → channels → delivery
│   ├── messaging/               chat, conversations (продуктово нейтрален)
│   ├── social/                  friendship, block, report
│   ├── search/                  SearchIndex, SearchHit, регистрация индексов
│   ├── analytics/               Event, счётчики, снапшоты метрик
│   ├── content/                 OrgPost — пост от лица организации
│   └── util/                    Result, Clock, signing, saturation
│
└── music/                       ← будущий @vire/music
    ├── catalog/                 artist, release, track, contributors
    ├── audio/                   TrackAudio, bpm, musicalKey, waveform
    ├── playback/                queue, transport, wave (радио)
    ├── curation/                playlists, moods, genres, editorial
    ├── engagement/              likes, follows, presaves, favorite moments
    ├── jam/                     совместное прослушивание
    └── marketing/               smart links, presave-кампании
```

Обоснование каждой границы — `platform-core.md` §2. Спорные случаи разобраны там же
с явным решением и причиной, включая те, что **остаются в домене** вопреки
генерическому виду (плейлисты, смартлинки).

`packages/db` зеркалит то же деление: `schema/platform/**` и `schema/music/**`.

## 6. Что переезжает в Core и что остаётся — сводка решений

| Сущность | Решение | Почему |
|---|---|---|
| `artist_profiles` → `organizations` | **В Core**, с доменным расширением | Профиль креатора (слаг, аватар, bio, тема, ссылки) нужен каналу и школе один в один. `theme_tokens`/`links`/`videos` уже JSONB и уже нейтральны |
| `artist_members` → `organization_members` | **В Core** | Уже join-таблица с ролью; дашборд уже работает через membership. Дистанция до платформенной модели — переименование |
| `likes`, `follows` | **В Core**, полиморфные | Второй продукт подтверждён → есть второй тип сущности для лайка/подписки. Паттерн уже применён в `purchases`/`reports` |
| `playlist_tracks` | **В домене** | Коллаборация и приглашения плотно завязаны на доменную модель. Обобщать нечем подтвердить даже с VireVideo |
| `SearchService` | Механизм в Core, типы в домене | `SearchHit {kind, …}` вместо трёх жёстких полей |
| Медиа-пайплайн | Разрезать | Core: `MediaAsset`, `ProcessingJob`, upload/presign/CDN. Домен: FLAC, HLS, waveform, bpm, ONNX-жанры |
| `play_events` | Обобщить в Core | Уже без FK — готовый прецедент. Становится `events` с `entity_type`/`entity_id` |
| `platform_metrics_daily` | Переделать в Core | Фиксированные музыкальные колонки → `(day, metric_key, value)`, иначе каждый продукт = `ALTER TABLE` |
| Плейлисты, смартлинки, волна, джем, пресейвы | **Остаются в домене** | Один use-case. Пометить как кандидатов, не трогать |
| `jam-sync` (дрейф часов) | Пометить, не двигать | Генерический алгоритм, но второго потребителя нет до watch-party |

## 7. Двухступенчатый деплой

**Ступень A — сегодня, 2 ГБ RAM.** Core — набор пакетов, собираемых в тот же образ.
Ноль новых контейнеров. `apps/web` остаётся и фронтом, и API. Воркер как есть.

```
Caddy → web (Next: UI + API) → Postgres · Redis · MinIO
        worker
```

**Ступень B — после апгрейда, опционально.** Появляется `apps/api` — тот же
`packages/core`, но с HTTP-транспортом без Next. `apps/web` перестаёт держать
route handlers и ходит в API как обычный клиент.

```
Caddy → web (только UI)  ─┐
        api (Core)       ─┼→ Postgres · Redis · MinIO
        video-web        ─┤
        worker           ─┘
```

Переход возможен **без переписывания бизнес-логики** ровно потому, что §4 обеспечивает
единственную реализацию за портами. Стоимость перехода — новый транспортный слой,
а не новая архитектура. Решение о ступени B принимается по факту апгрейда,
и до тех пор в коде для неё ничего делать не нужно.

## 8. Как границы защищаются автоматически

Архитектурное правило, которое не проверяется, деградирует. Три барьера в CI рядом
с уже существующими (`check:routes`, `check:i18n`, smoke):

1. **`check:layers`** — ESLint `no-restricted-imports`: `core/src/platform/**` не смеет
   импортировать `core/src/music/**` и `@vire/db`. Ловит главную деградацию.
2. **`check:contracts`** — каждый роут под `/api/v1` имеет схему запроса и ответа
   в `@vire/api-contracts`. Не даёт вернуться к 48 схемам врассыпную.
3. **Contract-тесты** — ответ роута парсится той же zod-схемой, которую импортирует клиент.
   Расхождение сервера и клиента падает в CI, а не в проде на телефоне пользователя.

Барьеры вводятся вместе с первой работой каждого типа, а не заранее.

## 9. Что архитектура сознательно НЕ вводит

Явный список отказов, чтобы к ним не возвращаться:

| Отказ | Причина |
|---|---|
| 16 пакетов сразу, директория `products/` | §2 — доказательство пустых пакетов уже в репозитории. Продукт один; вложенность даст ноль выигрыша и сломает пути |
| Core как отдельный сервис сейчас | После апгрейда до 2 ГБ это уже не физический запрет, а вопрос целесообразности: второго продукта нет, а лишний процесс — лишняя эксплуатация. Ступень B — когда появится второй потребитель |
| Полноценная мультитенантность | Тенантов нет. Проектируются границы (§10), реализуется по факту первого клиента |
| Generic CRUD-фреймворк для админки | Ваше же требование «explicit configuration over magic», и оно верное |
| Product Manifest как рантайм-механизм | С одним продуктом это конфиг, описывающий сам себя. Вернуться, когда VireVideo реально начнёт собирать другой набор модулей |
| Перевод RSC на собственный HTTP | Лишний хоп в одном процессе, потеря стриминга, деградация TTFB. Решается через §4 |
| Микросервисы | Нет ни нагрузки, ни команды, ни железа |

## 10. Границы под будущую мультитенантность

Не реализуем, но проектируем так, чтобы потом не ломать:

- **Ключ тенанта** — `organization_id` уже станет присутствовать в Core-сущностях после §6.
  Отдельный `tenant_id` вводится только если появится клиент, у которого несколько
  организаций под одним брендом.
- **Блокер, который надо снять независимо от тенантов:** `NEXT_PUBLIC_*`, CSP и
  `images.remotePatterns` пекутся в образ на build-time — **один образ = один бренд**.
  Это чинится как задача конфигурации (рантайм-резолв брендинга по хосту), и она
  полезна сама по себе.
- **Audit logs отсутствуют полностью** — вводятся вместе с Core `access/`, потому что
  единый гейт авторизации это естественная точка записи.
- **Изоляция данных** — на уровне запросов через обязательный `organization_id` в
  read-сервисах, не через отдельные схемы БД.

## 11. Критерий успеха

Архитектура считается достигшей цели, когда создание нового продукта складывается из:

1. описать домен (`packages/<product>`), 2. подключить модули Core, 3. написать доменный UI,
4. настроить тему через токены, 5. описать SDUI-экраны, 6. подключить контент, 7. выкатить —

и **не** включает написание заново: аутентификации, пользователей, ролей, биллинга,
хранилища, уведомлений, поиска, аналитики, админки, API-каркаса.

Проверяемая формулировка для приёмки: *к моменту старта VireVideo доля кода, физически
переиспользованного из `platform/`, покрывает identity, access, organizations, media,
notifications, search, analytics и billing целиком — новый код пишется только в
`packages/video` и `apps/video-web`.*
