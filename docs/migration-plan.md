# План миграции — от VireMusic к Platform Core

**Статус:** предложение (Phase 2) · **Основание:** `architecture-audit.md`, `architecture.md`,
`platform-core.md`, `sdui.md`, `multiplatform.md`

Каждый шаг: малый, проверяемый, **обратимый**, оставляющий приложение работающим.
Ни один шаг не требует одновременной правки всей кодовой базы.

---

## 0. Правила, действующие на каждом шаге

| Правило | Причина |
|---|---|
| Приложение работает после каждого коммита | Прод живой, релизы по тегу |
| Старый путь удаляется **только** после того, как новый отработал в проде | Откат должен быть выключением, а не ревертом |
| Гейты зелёные до коммита: `typecheck`, `lint`, `check:routes`, `check:i18n`, `test`, `build`; при UI — `audit:design`; перед тегом — `pnpm audit` | Существующий контракт качества |
| Версия бампается в **двух** местах: корневой `package.json` и `apps/web/package.json` | Тег и отображаемая в UI версия |
| Менял `package.json` → `pnpm install` → коммит lockfile → **потом** тег | Ломало деплой раньше |
| Новая фича не готова без файла в `docs/features/` | Существующее правило проекта |
| Нетривиальный шаг идёт через `vire-loop` | Существующее правило проекта |

**Оценки сложности** ниже — относительные (S/M/L/XL), не в часах.

## Волна 1 — единый доступ (`platform/access`)

**Почему первая:** чинит **состоявшийся**, а не гипотетический дрейф — три независимых
списка admin-ролей уже разошлись по `VIEWER` (`proxy.ts`, `admin/system/route.ts`,
`admin/tracks/*`). Плюс `/api/**` исключён из matcher, единого гейта для 109 роутов нет.
Не требует ничего от остальной платформы.

### 1.1 `can()` и реестр прав — M ✅

**Что меняется:** `packages/core/src/platform/access/` — `Permission`, карта
`role → permissions`, чистая функция `can(actor, permission, resource?)`. Чистые функции,
покрываются тестами напрямую.

**Проверка:** unit-тесты на матрицу ролей; поведение приложения не менялось.

**Откат:** удалить директорию — её ещё никто не вызывает.

### 1.2 Перевод роутов на единый гейт — M ✅ (admin-периметр; остальные ~79 роутов — следующая пачка)

**Что меняется:** `apps/web/lib/require-access.ts` — хелпер для route handlers.
Роуты переводятся **пачками по разделам** (сначала `admin/*`, потом остальные),
не все 109 разом.

**Критично:** на этом шаге исправляется расхождение списков ролей. Решение по `VIEWER`
принимается один раз и фиксируется тестом.

**Проверка:** тесты прав на каждый переведённый роут (в проекте уже есть этот класс тестов);
ручная проверка админки под каждой ролью.

**Откат:** пачка роутов ревертится независимо от остальных.

**Риск:** средний — можно случайно расширить или сузить доступ. Снимается тестами
до перевода, а не после.

### 1.3 Аудит-лог — S ✅

**Что меняется:** таблица `audit_log` + запись из единого гейта. Сегодня аудит-логов нет.

**Проверка:** действие в админке → появилась запись.

**Откат:** отключить запись; таблица остаётся пустой и безвредной.

## Волна 2 — read-path в HTTP (главный блокер `Б1`)

**Почему:** 27/53 страниц читают БД напрямую; у главной, каталогов и ленты нет эндпоинта
вообще. Без этой волны мобильный клиент невозможен, а SDUI бессмыслен.

**Механика на каждый ресурс** (по `architecture.md` §4 — одна реализация, два входа):

```
1. Read-сервис в core за портом (логика переезжает из packages/db/src/queries)
2. Страница переключается на него       → поведение то же, вход в процессе
3. Роут /api/v1/... вызывает его же     → тот же ответ, вход по HTTP
4. Контракт ответа в @vire/api-contracts + contract-тест
5. Старая query-функция удаляется — только после того, как п.2 отработал в проде
```

Каждый ресурс — **отдельный, независимо откатываемый** шаг.

### Порядок ресурсов

| # | Ресурс | Сложность | Замечание |
|---|---|---|---|
| 2.1 ✅ | Артист (`/v1/artists/[slug]/page`) | M | Роут **уже существует и построен через core**, но страница его не использует, дублируя логику. Начинать отсюда: сходимость двух реализаций проверяется сравнением, а не гаданием |
| 2.2 ✅ | Релиз (`/v1/releases/[releaseId]/page`) | M | Отклонение от плана: старый `/v1/releases/[releaseId]` — ресурсный роут плеера (другой контракт, живой потребитель `lib/player/lazy-queue-fetchers.ts`), не трогали; экран получил отдельный `.../page` роут, как у артиста |
| 2.3 | Каталог релизов `GET /v1/releases` | M | Эндпоинта нет. Пагинация/сортировка — в контракт |
| 2.4 | Каталог артистов `GET /v1/artists` | M | Эндпоинта нет |
| 2.5 | Плейлист `/v1/playlists/[id]` | M | |
| 2.6 | Лента `GET /v1/feed` | L | Персонализирована; `lib/feed.ts` уже тонкий оркестратор над чистыми `composeFeed`/`scoreFeedItem` из core — переносится легко |
| 2.7 | Блоки главной | L | Каждый блок = свой эндпоинт. Прямое предусловие SDUI |

**Проверка на каждом шаге:** снапшот ответа страницы до и после (набор и порядок сущностей);
contract-тест роута; отсутствие регресса TTFB — на 1 ГБ это не формальность.

**Откат:** страница возвращается на старую query-функцию (она ещё не удалена) — один revert.

**Риск:** средний, но локальный: ошибка задевает один экран, а не систему.

**Что НЕ делаем:** не заставляем Server Components ходить в собственный HTTP. Лишний хоп
в одном процессе, потеря стриминга RSC, деградация TTFB.

## Волна 3 — контракты

### 3.1 Наполнение `@vire/api-contracts` — M, идёт параллельно волне 2

**Что меняется:** схемы запроса/ответа переезжают из route handlers (сейчас 48 схем
врассыпную) в пакет, по ресурсу за раз, **вместе** с соответствующим шагом волны 2.
Отдельной большой миграции контрактов не будет — это её главное достоинство.

**DTO-граница:** core-типы используют `Date`; контракт использует ISO-строку.
Маппинг явный, в одном месте на ресурс.

### 3.2 Барьер `check:contracts` — S

Роут под `/api/v1` без схемы в пакете → гейт красный. Вводится, когда переведена
первая группа, иначе он красный с первого дня.

### 3.3 Contract-тесты — M

Ответ роута парсится той же схемой, которую импортирует клиент.

**Откат для всей волны:** схемы остаются, роуты возвращаются к локальной валидации.

## Волна 4 — Bearer-аутентификация

**Почему после волны 2:** без эндпоинтов токен нечем пользоваться.

### 4.1 Адаптер `getCaller()` — M

**Что меняется:** единая точка получения актора вместо прямого `auth()` (60+ файлов).
Сначала адаптер просто оборачивает `auth()` — **поведение не меняется**, но появляется
единственное место, куда добавляется Bearer.

**Откат:** тривиальный, адаптер прозрачен.

### 4.2 Устройства и обмен токенами — L

**Что меняется:** таблица `devices`; `POST /v1/auth/token`, `POST /v1/auth/refresh`,
`DELETE /v1/auth/devices/{id}`. Ротация refresh. Веб продолжает на cookie.

**Проверка:** тесты обмена и ротации; отзыв устройства прекращает доступ;
существующие сессии веба не затронуты.

**Откат:** эндпоинты выключаются флагом; cookie-путь не менялся.

**Риск:** высокий по последствиям (аутентификация) → отдельный проход
`security-review` перед выкаткой.

## Волна 6 — медиа и хранилище

### 6.1 Расширение `IFileStorage` — M

Порт сегодня имеет **один метод** (`upload`), поэтому код ходит в S3 SDK мимо абстракции;
web и worker держат два независимых клиента. Добавляются `presign`, `delete`, `stat`, `copy`;
клиенты сводятся к одному.

### 6.2 `MediaAsset` / `ProcessingJob` — L

`track_audio` разделяется: нейтральное (ключ, статус, вид, метаданные) → Core `MediaAsset`;
музыкальное (`bpm`, `musicalKey`, `waveformPeaks`, `genreSuggestions`) → доменная таблица
со ссылкой.

Payload очередей параметризуется по ассету:
`TranscodeJobData { trackId } → ProcessMediaJobData { assetId, pipeline }`.

**Проверка:** прогон транскодинга целиком — загрузка FLAC → HLS → READY.
Гейты этого класса багов не ловят: проверять **сборкой Docker-образа**, не локальной
(прецедент с `sharp`/libvips, v1.34.0).

**Откат:** старые колонки не удаляются до подтверждения в проде; двойная запись на время
перехода.

**Риск:** высокий — трогает пайплайн, который уже ронял прод. Отдельный проход.

## Волна 8 — SDUI на главной

Полностью описано в `sdui.md` §10. Ключевое: композиция сначала повторяет текущий порядок
**один в один**, обе ветки живут рядом, откат = выключение флага, статическая ветка
удаляется только после подтверждения протокола мобильным клиентом.

**Предусловие:** волна 2.7 (блоки главной имеют эндпоинты) и 7.5 (флаги).

**Проверка:** одинаковый набор и порядок блоков; те же скелетоны; нет регресса TTFB;
**ноль композитных слоёв в скролл-области** (проверка через CDP `LayerTree` — существующее
требование, SDUI не должен его обойти).

## Волна 10 — полиморфные взаимодействия

**Условие запуска: появился второй тип сущности, которую лайкают/на которую подписываются.**
Раньше это чистая потеря referential integrity без выигрыша.

`likes.track_id` → `reactions(target_type, target_id)`;
`follows.artist_profile_id` → `follows(target_type, target_id)`.

**Цена, принимаемая сознательно:** потеря `ON DELETE CASCADE` → уборка при удалении трека
или артиста становится явным шагом доменного сервиса или фоновой задачей. Это единственный
настоящий минус, и он не обходится.

**Откат:** после бэкфилла — сложный. Поэтому шаг последний и по явному условию.

## Волна 11 — CI/CD под несколько продуктов

Делается **перед** появлением `apps/video-web`, не раньше.

- path-фильтрация по изменённым пакетам (сейчас каждый прогон гоняет весь монорепо);
- матрица образов вместо жёсткого перечисления web/worker в `deploy.yml`
  (третий продукт сегодня = копипаста всего блока build-push-deploy);
- рантайм-резолв брендинга по хосту вместо build-time запекания `NEXT_PUBLIC_*`/CSP/
  `remotePatterns` — **один образ = один бренд** сегодня, и это блокер white-label.

## Что считать успехом

Волна 2 — единственная, чья ценность не зависит ни от одного дальнейшего решения:
после неё у VireMusic появляется настоящий API, а расхождение двух реализаций
(которое **уже произошло** — `/v1/artists/[slug]` существует и не используется)
становится структурно невозможным.

Если программа остановится где угодно после волны 3, проект всё равно окажется
в лучшем состоянии, чем был. Это и есть проверка на «не платформа ради платформы».
