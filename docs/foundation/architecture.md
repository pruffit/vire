# Архитектура — музыкальная площадка

> **Документ 2 из 3.** Технический фундамент. Продуктовое видение — в [`../vision/concept.md`](../vision/concept.md), модель данных — в [`data-schema.md`](data-schema.md). Версия 1.0, июнь 2026.

Технический фундамент проекта. Документ описывает стек, структуру кода, потоки данных и деплой. Главный принцип сквозной: **этап 1 должен запускаться просто, но швы под этапы 2-4 заложены так, чтобы рост был переездом, а не переписыванием.** Прод — один VPS на Timeweb Cloud (Docker Compose), но архитектура к нему не привязана жёстко: managed-вынос Postgres/S3 — при росте.

---

## Принципы, на которых всё держится

- **API-first.** Вся бизнес-логика в сервисном слое, а не в компонентах или хендлерах. UI и API общаются через типизированные контракты. Любой будущий клиент (PWA, Tauri, нативка) — просто ещё один потребитель того же API.
- **Данные смотрят в будущее, инфраструктура живёт настоящим.** Схема БД сразу содержит поля под будущие этапы (доли прав, метаданные для волны). Тяжёлую инфраструктуру (движок выплат, ML) не строим, пока нет нагрузки, которая её оправдывает.
- **Тяжёлое — асинхронно.** Транскодинг, рассылки, аналитические агрегации не живут в HTTP-запросе. Очередь + воркеры с первого дня.
- **Монолит с швами, а не микросервисы.** На старте один деплой, но границы модулей проведены так, чтобы любой кусок можно было вынести отдельно без хирургии.
- **У каждого модуля одна задача.** Single Responsibility на всех уровнях — от функции до пакета. Если модуль трудно описать одним предложением без «и», его надо делить.
- **Чистое ядро, грязные края.** Бизнес-логика — чистые функции без побочных эффектов. Всё нечистое (БД, сеть, файлы, время, случайность) оттеснено на границы и спрятано за интерфейсами.
- **Явное лучше неявного.** Зависимости инъектируются, а не импортируются скрыто. Ошибки возвращаются типами, а не глотаются. Состояние предсказуемо.

Детали инженерных практик — в разделах «Парадигма и слои фронтенда», «Чистота и тестируемость», «Отказоустойчивость», «Наблюдаемость» ниже.

## Стек

**Язык:** TypeScript везде — фронт, бэк, воркеры, общие пакеты. Один язык на весь монорепо.

**Фронтенд и API:** Next.js (App Router). На этапе 1 он же и бэкенд — Route Handlers (`/api/v1/*`) поверх сервисного слоя. SSR/ISR для страниц артистов ради SEO.

**UI:** Radix Primitives / shadcn как headless-слой (поведение, доступность) + кастомный Tailwind поверх (токены темы, зерно, типографика). Тема — не глобальная константа, а CSS-переменные, перекрываемые на уровне страницы артиста.

**База:** PostgreSQL (self-hosted в Docker на VPS; managed-вынос при росте). ORM — Drizzle: типизированный SQL, легче и честнее на сложных запросах волны и аналитики. Миграции через drizzle-kit.

**Очередь и кэш:** Redis + BullMQ. Очередь задач (транскодинг, рассылки), кэш горячих данных, rate limiting, сессии при необходимости.

**Хранилище:** S3-совместимое — MinIO и на проде (за Caddy на cdn-сабдомене), и локально. Два логических бакета: «сейф» (сырой FLAC под Signed URL) и «стрим» (HLS-чанки за CDN).

**Транскодинг:** отдельный воркер на ffmpeg в Docker-образе. Режет HLS, считает waveform-пики, извлекает аудио-метаданные.

**Аутентификация:** Auth.js v5 — email/пароль, magic-link (через Brevo), Yandex. Google и Telegram убраны (406-ФЗ). Сессии JWT. Своё не катаем.

**Аналитический лог:** лог прослушиваний пишется отдельно от транзакционной базы (отдельная таблица сейчас, миграция в ClickHouse при росте).

## Структура монорепо

Turborepo + pnpm workspaces. На этапе 1 реально работает один `apps/web`, остальные пакеты появляются по мере роста, но границы заложены сразу.

```
.
├── apps/
│   ├── web/                  # Next.js — фронт + API (этап 1+)
│   ├── worker/               # фоновые воркеры: транскодинг, рассылки (этап 1+)
│   ├── desktop/              # Tauri-обёртка (этап 3-4)
│   └── mobile/               # React Native / Expo (этап 4)
│
├── packages/
│   ├── core/                 # бизнес-логика: сервисы, use-cases — НЕ зависит от Next
│   ├── db/                   # схема, миграции, ORM-клиент, репозитории
│   ├── api-contracts/        # типы запросов/ответов, zod-схемы валидации
│   ├── api-client/           # типизированный клиент API для всех фронт-оболочек
│   ├── ui/                   # общий UI-кит (Radix + Tailwind токены)
│   ├── media/                # утилиты транскодинга, HLS, waveform (общие для worker)
│   └── config/               # eslint, tsconfig, tailwind preset
│
├── docker-compose.yml        # postgres + redis + minio для локалки
└── turbo.json
```

Ключевой момент: **`packages/core` не импортирует ничего из Next.** Сервисы — чистый TypeScript. Route Handlers в `apps/web` тонкие: валидируют вход (zod), дёргают сервис из `core`, отдают ответ. Тот же `core` потом дёргает `apps/worker`. Когда (и если) на этапе 3 захочется вынести бэк в отдельный NestJS — переезжает `core` целиком, фронт не трогается.

## Слоистость внутри `core`

```
Route Handler (apps/web/api)         ← тонкий, только HTTP
        │
        ▼
Service / Use-case (packages/core)   ← вся логика: права, цены, доступ
        │
        ▼
Repository (packages/db)             ← запросы к БД, ничего про бизнес
        │
        ▼
PostgreSQL
```

Правила:
- Хендлер не знает про БД. Сервис не знает про HTTP. Репозиторий не знает про бизнес-правила.
- Внешние интеграции (платёжные вебхуки, S3, email) — за интерфейсами в `core`, реализации инъектятся. Так их легко мокать в тестах и менять провайдера.
- Генерация Signed URL, проверка «купил ли юзер трек», расчёт что показать в волне — всё это сервисы `core`, доступные любому клиенту через API.

По факту (07.2026): каталог/владение — `ArtistService`/`ReleaseService`/`TrackService`;
интерактивы слушателя — `FollowService`, `ListenerTrackService` (лайк/моменты/lyrics
трека), `TrackMoodsService`, `PlaylistService`; дашборд артиста — `ArtistPostService`
(посты/анонсы), `SmartLinkService` (bandlink-лендинги). Расширения: `ReleaseService`
(`create`/`update`/`changeStatus` — обложка через `IFileStorage`, уведомление о
публикации через `INotifyReleaseQueue`), `ArtistService.updateProfile` (тема/шрифты/
аватар, тайтлы видео через `IVideoTitleResolver`, каталоги шрифтов инъектируются
деп-объектом), `TrackService` (загрузка исходника в `IFileStorage`, `uuid` инъектируется).
Порты (`I*Repository`, `IFileStorage` — общий порт файлового хранилища, `IPlaylistCoverStorage`
теперь его алиас) объявлены в `core`, Drizzle-реализации — в `packages/db/src/repositories`,
S3-адаптеры (обложки релиза/смартлинка/плейлиста, аудио-исходник) — в `apps/web/lib/*`
(тот же паттерн, что у очереди). Волна/поиск/презейвы: `WaveService` (порты
`IWaveTrackSource`, `IWaveSessionStore` — Redis-сессия волны за портом, адаптер
`apps/web/lib/wave-session-store.ts` поверх `lib/wave-session.ts`), `SearchService`
(`ISearchRepository`), `PresaveService` (`IPresaveRepository`, инъекция `now`).
`AuthService` (порты `IUserAccountRepository`, `IPasswordHasher` — bcrypt за
портом, адаптер `apps/web/lib/password-hasher.ts`). Admin-методы на существующих
сервисах: `ArtistPostService`/`PlaylistService.adminUpdate`/`adminDelete`,
`ArtistService`/`ReleaseService.adminUpdate`, `TrackService.adminUpdate`/
`retranscode`/`retranscodeArtist` (deps: `moodsRepo`, `parseLrc`). Server actions
админки/auth теперь тонкий край (RBAC/zod/`revalidatePath`) поверх сервисов;
11 тривиальных actions (роль/верификация/статусы/участники/очереди) остались
прямыми вызовами query-функций осознанно.

## Потоки данных — ключевые сценарии

### Загрузка и публикация трека

```
1. Артист грузит FLAC → apps/web принимает, кладёт во временный «сейф»-бакет
2. web создаёт запись track (status=PROCESSING) и ставит задачу в BullMQ
3. apps/worker берёт задачу:
   - ffmpeg режет HLS (несколько битрейтов) → «стрим»-бакет
   - считает waveform-пики → JSON в БД
   - извлекает/проверяет аудио-метаданные (BPM, длительность)
   - перекладывает исходный FLAC в постоянный «сейф» по ключу /vault/tracks/{track_id}/source.flac
4. worker помечает track status=READY
5. web показывает артисту, что трек готов
```

Транскодинг никогда не происходит в HTTP-запросе. Артист видит статус, не ждёт с крутилкой.

### Прослушивание (стриминг)

```
1. Плеер запрашивает у API манифест трека
2. Сервис проверяет права (опубликован? не заблокирован?) и отдаёт .m3u8
   с подписанными ссылками на чанки (короткий TTL)
3. hls.js в плеере тянет чанки по мере воспроизведения через CDN
4. Событие прослушивания (дослушал до N сек) → отдельный лёгкий эндпоинт
   → очередь/буфер → таблица лога (НЕ основная транзакционная вставка на каждый тик)
```

### Покупка (этап 2, децентрализованный чекаут)

```
1. Слушатель жмёт «купить» → сервис создаёт pending-purchase, редиректит
   на платёжную ссылку мерчанта артиста (ЮKassa/Робокасса/самозанятый-сервис)
2. Слушатель платит — деньги идут НАПРЯМУЮ артисту, минуя площадку
3. Платёжный сервис шлёт webhook → apps/web эндпоинт вебхука
   → сервис верифицирует подпись, помечает purchase=PAID
4. Слушателю открывается скачивание FLAC по Signed URL из «сейфа»
   (ключ по track_id, поэтому работает даже если артист потом уйдёт)
```

Площадка нигде не держит чужие деньги — только подтверждает факт и открывает файл.

### Волна (этап 1-3, ступень 1)

```
1. Трек кончился → плеер просит у API «следующий»
2. Сервис волны: берёт теги/жанр/BPM текущего трека,
   ищет в БД пересечения, исключает уже сыгранное в сессии,
   сортирует по весу совпадения + лёгкий рандом, отдаёт следующий
3. Никакого ML — один взвешенный SQL-запрос
```

## Темизация технически

Профиль артиста хранит `theme_tokens` (JSON): фон, текст, акцент, флаг зерна, шрифтовая пара. При SSR страницы `/artists/[slug]` сервер читает токены и инъектит их как inline CSS-переменные в корневой контейнер. Компоненты из `packages/ui` написаны на `bg-[var(--artist-bg)]`, `text-[var(--artist-text)]` — один и тот же код рендерится мрачным у одного артиста и светлым у другого. Оболочка платформы (лента, поиск) использует свой нейтральный набор токенов, не артистов.

## Docker и окружения

### Локальная разработка

`docker-compose` поднимает только инфраструктуру, код гоняется нативно для быстрого хот-релоада.

```
docker-compose.yml:
  - postgres
  - redis
  - minio        # локальный S3, чтобы не трогать облако при разработке
```

Next.js и воркер запускаются через `pnpm dev` рядом, не в контейнере.

### Транскодинг-воркер

Единственное, что контейнеризуется и для разработки тоже — образ с ffmpeg и нужными кодеками. Гарантирует одинаковое поведение локально и на проде, снимает «а на сервере не та версия libavcodec».

### Продакшен — Timeweb Cloud

Весь стек на одном VPS (2 × 3.3 ГГц / 2 ГБ RAM / 40 ГБ NVMe + swap 4 ГБ). Наружу торчит только Caddy (80/443) с авто-TLS от Let's Encrypt.

> Апгрейд с 1 vCPU / 1 ГБ выполнен. Выводы, опиравшиеся на старую спеку («Sentry не влезает»,
> «поисковый движок не влезает», «Core как сервис невозможен»), не переоценены — см.
> `../architecture/audit-2026-08.md` §6.

```
Timeweb VPS  ·  docker-compose.prod.yml
  caddy          ← авто-TLS, reverse proxy
  web            ← Next.js standalone (:3000)
  worker         ← BullMQ + ffmpeg
  postgres       ← данные на именованном volume
  redis          ← очередь + rate limiting
  minio          ← S3-совместимое хранилище (vault + stream бакеты)

Образы собирает CI (GitHub Actions) → пушит в GHCR → сервер тянет готовые.
```

При росте — первым кончится диск (FLAC). Тогда: `S3_ENDPOINT`/`S3_PUBLIC_ENDPOINT` на внешний S3 (одна правка `.env`). Postgres выносится в managed-сервис когда объём/нагрузка оправдают цену.

Kubernetes — не сейчас и, возможно, никогда. Это инструмент этапа 4 с реальной нагрузкой, который до того только крадёт время.

## Парадигма и слои фронтенда — Feature-Sliced Design

Фронтенд (`apps/web`) строится по FSD — это даёт предсказуемую структуру, однонаправленные зависимости и понятные границы фич. Слои сверху вниз, импорт разрешён только вниз:

```
app/         — инициализация, провайдеры, роутинг, глобальные стили
processes/   — сложные межстраничные сценарии (опционально)
pages/       — страницы-композиции (в Next App Router мапятся на роуты)
widgets/     — самостоятельные блоки UI (плеер, карточка релиза, лента)
features/    — пользовательские действия (купить трек, лайкнуть, добавить в плейлист)
entities/    — бизнес-сущности на фронте (Track, Artist, Release, Playlist)
shared/      — переиспользуемое без бизнес-смысла (ui-кит, хелперы, api-клиент)
```

Правила FSD, которые соблюдаем жёстко:
- Импорт только вниз по слоям. `feature` может использовать `entity` и `shared`, но `entity` не знает о `feature`. Виджет не импортирует другой виджет.
- Каждый слайс имеет публичный API через `index.ts` — наружу торчит только то, что экспортировано. Внутренности слайса не импортируются напрямую.
- Сегменты внутри слайса: `ui/`, `model/` (состояние, логика), `api/`, `lib/`. Единообразно везде.

Это ровно та парадигма, в которой ты уже работал на портфолио и прошлых проектах — переиспользуем привычку.

**Состояние плеера** — отдельный разговор. Глобальная сессия (текущий трек, очередь, играет/пауза, прогресс) живёт в Zustand-сторе на уровне `app`, плеер монтируется один раз в корневом layout, чтобы звук не рвался при навигации. Zustand, а не Context — чтобы тик прогресса не ре-рендерил пол-приложения; подписки идут через селекторы.

**Бэкенд `core`** парадигмально ближе к гексагональной архитектуре (порты и адаптеры): use-case в центре, внешний мир (БД, S3, платежи) — через интерфейсы-порты, реализации-адаптеры инъектируются. FSD тут не нужен — это слой не про UI.

## Чистота и тестируемость

**Чистое ядро.** Бизнес-правила — чистые функции: на одинаковый вход одинаковый выход, без побочных эффектов. «Сколько стоит трек с промокодом», «доступен ли релиз этому юзеру», «какой трек следующий в волне» — это функции от данных к данным, их не волнует, откуда данные пришли.

**Эффекты на краях.** Всё нечистое изолировано за портами:
- Время — не `new Date()` в логике, а инъектируемый `Clock`. Иначе тесты пляшут от текущего времени.
- Случайность — не `Math.random()` посреди волны, а инъектируемый источник. Тогда поток детерминированно воспроизводим в тесте.
- БД, S3, платёжный провайдер, отправка почты — за интерфейсами. В тестах подменяются заглушками.

**Что это даёт.** Ядро тестируется без базы, без сети, без Docker — обычными быстрыми unit-тестами. Адаптеры тестируются отдельно интеграционными. Пирамида:
- Много **unit** на `core` (чистая логика) — миллисекунды, гоняются на каждый коммит.
- Меньше **интеграционных** на репозитории и адаптеры (с поднятой тестовой БД через testcontainers / тот же docker-compose).
- Мало **e2e** на критичные сценарии (покупка, загрузка, воспроизведение) через Playwright.

**Контракты на входе.** Любой внешний вход (тело запроса, вебхук, параметры) валидируется через zod до попадания в логику. Невалидное не проникает внутрь — ядро всегда работает с уже проверенными данными. Типы выводятся из zod-схем, один источник правды.

## Отказоустойчивость

**Граница падения — запрос, а не процесс.** Ошибка в одном запросе не роняет сервер. Глобальный error boundary на API возвращает корректный код и не светит стектрейс наружу. На фронте — React error boundary на уровне виджета: упал плеер — страница живёт.

**Ошибки как значения, а не сюрприз.** Сервисы возвращают явный результат (`Result<T, Error>` или дискриминированный union), а не кидают исключения сквозь слои. Вызывающий обязан обработать обе ветки — компилятор не даст забыть. Исключения остаются для действительно исключительного.

**Очередь переживает падения.** Задачи транскодинга в BullMQ с retry и экспоненциальным backoff. Воркер упал на середине — задача вернётся в очередь, не потеряется. Идемпотентность: повторная обработка той же задачи не создаёт дублей (проверка по `track_id` + статус).

**Вебхуки идемпотентны.** Платёжный провайдер может прислать вебхук дважды. Обработчик проверяет, не обработан ли уже этот `payment_id`, прежде чем открывать доступ. Подпись вебхука верифицируется всегда.

**Внешние вызовы с таймаутом и фолбэком.** Любой вызов наружу (платежи, S3, почта) обёрнут таймаутом. Где уместно — circuit breaker, чтобы не долбить упавший сервис. Деградация мягкая: не пришли waveform-пики — плеер показывает плоскую линию, а не падает.

**Транзакции на согласованность.** Операции, меняющие несколько таблиц (покупка → доступ → лог), идут в транзакции БД. Либо всё, либо ничего — не бывает «оплата прошла, а доступ не открылся» в самой базе.

**Бэкапы — часть архитектуры, не дополнение.** Автоматические бэкапы Postgres (`pg_dump` по расписанию в отдельный холодный S3; managed-вынос при росте). Сырые FLAC — единственная копия мастера артиста, поэтому репликация в другой регион/датацентр. Восстановление проверяется, а не предполагается.

## Наблюдаемость

Нельзя чинить то, чего не видишь. С первого дня, минимально но обязательно:

- **Структурные логи** (JSON, не строки) с `request_id`, прокинутым через все слои. Один запрос — одна нить логов, которую можно проследить.
- **Sentry** на фронте и бэке — ошибки прилетают с контекстом, не теряются в логах. У тебя уже был опыт с Sentry на портфолио.
- **Метрики** базовые: латентность API, длина очереди транскодинга, размер хранилища, ошибки вебхуков. На старте — хоть простой дашборд, чтобы видеть пульс.
- **Health-check эндпоинты** (`/health`, `/ready`) — проверка живости БД, Redis, S3 для деплоя и мониторинга.

## Качество кода и процесс

- **TypeScript strict.** `strict: true`, без `any` без явной причины. Типы — первая линия защиты.
- **Линт и формат** едины на весь монорепо (`packages/config`): ESLint + Prettier, запускаются в pre-commit хуке и в CI.
- **Conventional Commits** — предсказуемая история, автогенерация changelog позже.
- **Ветки:** `dev` — текущая разработка; `main` — стабильный, только через PR. CI (typecheck + lint + test + design audit + build) на каждый пуш в `dev` и каждый PR. Красный CI не мёржится.
- **Миграции БД версионируются** и катятся автоматически, никаких ручных правок схемы на проде. Откат миграции продуман до её применения.
- **Секреты — только в окружении**, не в коде и не в гите. `.env.example` фиксирует список переменных без значений.
- **Feature flags** для незрелых фич — выкатывать выключенным, включать по готовности без передеплоя.

## Принятые решения

1. **ORM — Drizzle.** Волна и аналитика с самого начала требуют нетривиальных запросов (пересечения по тегам с весами, агрегации по логу прослушиваний). Prisma на таком буксует и вынуждает писать сырой SQL в обход себя. Drizzle — типизированный SQL: пишешь близко к запросу, но с автодополнением и проверкой типов, легче и быстрее в рантайме, честно показывает что уходит в базу. Миграции через drizzle-kit.

2. **Бэкенд — Next.js без отдельного NestJS.** Сервисный слой в `packages/core` уже даёт чистую логику, инъекцию зависимостей и тестируемость — то, ради чего тянут Nest. Второй деплой на этапе 1 — оверинжиниринг. Если `core` дисциплинированно чист, переезд в Nest на этапе 3 (если вообще понадобится) — перенос пакета, а не переписывание. Стартуем с одного приложения.

3. **Инфраструктура — один VPS на старте.**
   Всё в Docker Compose на одной машине (Timeweb Cloud). Managed-сервисы добавятся когда нагрузка оправдает их стоимость: первый кандидат — Postgres (managed снимает задачу бэкапов), второй — S3 (когда vault с FLAC упрётся в диск).

Логика баланса: Drizzle берёт будущую сложность, Next держит старт лёгким, всё на одном VPS держит расходы минимальными пока нет реальной нагрузки.
