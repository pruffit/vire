## Тесты и CI

### ✅ `turbo run test` флейкал по таймауту — закрыто (ограничение конкуренции)

Обнаружено 28.08.2026, закрыто там же.

**Симптом.** `pnpm turbo run test` ронял в `@vire/web` 6–13 тестов, всегда с
`Test timed out in 5000ms`. Отдельный прогон `pnpm --filter @vire/web test` —
стабильные 2026/2026.

#### Корневая причина: RESOURCE CONTENTION — два нескоординированных слоя параллелизма

Vitest **сам** параллелит файлы внутри пакета (пул `forks`, до `availableParallelism − 1`
воркеров). Turbo поверх этого параллелит **пакеты** (дефолт — до 10 разом). Произведение
двух слоёв не ограничено ничем:

```
машина разработчика (8 ядер):  10 пакетов × 7 воркеров = до 70 процессов на 8 ядер
раннер GitHub (2 ядра):        10 пакетов × 1 воркер   = до 10 процессов на 2 ядра
```

Ядер не хватает, тесты не укладываются в `testTimeout` и падают.

#### Почему падали именно эти четыре файла

Замер в изоляции (`vitest run` по четырём файлам, машина не нагружена):

| Файл | 1-й тест | последующие |
|---|---:|---:|
| `app/api/v1/push/subscribe/route.test.ts` | **2303 мс** | 2–5 мс |
| `lib/player/audio-engine.test.ts` | **1660 мс** | 26–46 мс |
| `lib/jam/sources/youtube-source.test.ts` | **1297 мс** | 77–95 мс |
| `lib/jam/sources/soundcloud-source.test.ts` | **1296 мс** | 38–108 мс |

Первый тест каждого файла платит за исполнение графа модулей: `await import(...)` стоит
**внутри** `it()`, а не на верхнем уровне, поэтому инициализация считается в бюджет теста.
Трое из четырёх дополнительно зовут `vi.resetModules()` в `beforeEach` — граф
переисполняется на каждый тест. Уже на пустой машине это 26–46% от 5 с.

Это **усилитель, а не причина**: при росте нагрузки падения расползались на 2-й и 3-й
тесты тех же файлов, которые в изоляции стоят 2–100 мс. Значит голодание процессорное,
а не «тесты медленные».

#### Доказательства

| Конфигурация | Ядер | Прогонов | Упало | Время |
|---|---:|---:|---|---:|
| `turbo run test` (дефолт) | 8 | 5 | **5/5** (8–13 тестов) | 133 с |
| `turbo run test --concurrency=1` | 8 | 3 | 0/3 | 134 с |
| `turbo run test` (дефолт) | **2** | 1 | **1/1** (10 тестов) | 128 с |
| `turbo run test --concurrency=1` | **2** | 3 | 0/3 | 134 с |
| `pnpm test` (боевая точка входа, `TURBO_FORCE=true`) | **2** | 4 | **0/4** | 133–137 с |

**Итого фикс валидирован 10 прогонами подряд без единого падения** против 6/6 падений
на базлайне.

2 ядра эмулированы через `ProcessorAffinity` (маска 3) — дочерние процессы наследуют её,
то есть ограничено всё дерево. Кэш turbo в валидационных прогонах выключен
(`Cached: 0 cached, 10 total`), иначе прогон вырождается в воспроизведение логов за 2 с.
Бисект: на чистом дереве без правок фазы 1 падали те же тесты — долг существовал до неё.

#### Фикс

`--concurrency=1` для таска `test` в корневом `package.json`; workflow'ы зовут `pnpm test`,
а не `turbo run test`. Vitest остаётся единственным владельцем параллелизма и использует
ядра сам.

**Сериализация пакетов бесплатна и даже выигрышна:** web в одиночку идёт 98.9 с против
131.0 с в конкуренции, а остальные девять пакетов суммарно 21 с укладываются в тот же
бюджет. Общее время не изменилось (133 с → 134 с).

Регресс закрыт барьером `scripts/check-test-concurrency.mjs` (в обоих workflow рядом с
остальными гейтами): падает, если из корневого скрипта убрали `--concurrency` или если
workflow снова зовёт `turbo run test` напрямую. Проверен на обоих режимах регресса.

#### Почему отвергнуты другие подходы

| Подход | Почему нет |
|---|---|
| Поднять `testTimeout` | Маскирует симптом: настоящее зависание станет неотличимо от нехватки ядер. Причина — не в том, что тестам законно нужно больше времени |
| Retry упавших тестов | Прячет недетерминизм вместо устранения |
| Гонять web отдельным шагом CI | Прячет проблему, не решает: остальные 9 пакетов продолжат перепрописывать ядра друг другу |
| Ограничить `maxWorkers` в каждом пакете | Не помогает: 10 пакетов × 1 воркер — всё ещё 10 процессов на 2 ядра |
| Переписать 4 файла (вынести `await import` в `beforeAll`) | Лечит усилитель, не причину. Осталось бы голодание на остальных тестах; риск правки рабочих тестов без выигрыша в детерминизме |

**Остаточный риск.** Первый тест в этих четырёх файлах по-прежнему стоит 1.3–2.3 с из
5 с бюджета. Запас есть (валидация 5/5 на двух ядрах), но он не бесконечен: если файлы
станут тяжелее или раннер медленнее, они первыми упрутся снова. Дешёвая профилактика,
если это случится, — вынести `await import(...)` из `it()` в `beforeAll`, чтобы стоимость
инициализации не считалась в бюджет утверждения.

## Аутентификация и сессии

### ✅ JWT без перечитывания БД — закрыто (bounded refresh)
Раньше: роль/имя/аватар клались в JWT при логине и не перечитывались → после смены роли
(`db:make-admin`, верификация, `createArtistForUser`) до релогина — рассинхрон авторизации.

Закрыто (17.07.2026): `jwt`-callback (`apps/web/auth.ts`) перечитывает роль/имя/аватар из БД
не чаще раза в TTL (`JWT_ROLE_REFRESH_MS`, 5 мин) через чистый хелпер
`apps/web/lib/jwt-refresh.ts` (`applyJwt`/`shouldRefreshRole`). Рефреш идёт **только в
Node-рантайме** (`isNodeRuntime`) — `proxy.ts` это edge-middleware, там postgres.js недоступен,
токену доверяем как раньше. При любом реальном обращении к БД (успех / юзер удалён / ошибка)
`syncedAt` продвигается → просадка БД не превращается в рефетч на каждый запрос (повтор не
раньше TTL). Ошибка БД → роль/имя остаются старыми (деградация к прежнему поведению).
Итог: рассинхрон роли ограничен ≤5 мин без релогина, без per-request DB и без dynamic rendering
(статические SEO-страницы `auth()` не зовут). `session`-стратегия с БД / Redis-инвалидация
не понадобились.

### `createArtistForUser` повышает только LISTENER
При создании артиста через `/admin/users` роль меняется `LISTENER → ARTIST`, но `MODERATOR`/`ADMIN`/`SUPERADMIN` не понижается. Сделано после инцидента, когда создание артиста на email суперадмина отобрало доступ к админке.

## Безопасность

### `'unsafe-inline'` в CSP
CSP содержит `script-src 'unsafe-inline'`, что ослабляет защиту от XSS. Убрать без nonces нельзя: Next.js 15/16 инжектирует инлайн-скрипты гидрации/RSC-стриминга без nonce-атрибутов из коробки.

**Исследовано и отложено с находками (10.07.2026).** Nonce-путь был реализован полностью (per-request nonce в `proxy.ts` middleware, `buildCsp(nonce)` в отдельном модуле) и **сознательно откачен**. Три причины:

1. **Сырые инлайн-скрипты не получают nonce.** Next автоматически проставляет `nonce=` только на *свои* инлайн-скрипты (читает nonce из CSP заголовка запроса через `getScriptNonceFromHeader`). Наш `<script dangerouslySetInnerHTML>` reduce-motion в `app/layout.tsx:100` — не next-script, nonce ему не достаётся → в проде без `'unsafe-inline'` он **блокируется** браузером (анимации мигнут у выбравших приглушение). Dev это маскирует: там `'unsafe-inline'` остаётся (nonce в dev не подмешан намеренно). Каждый будущий инлайн-скрипт пришлось бы вручную протягивать nonce из `headers()` — постоянный источник тихих проком-багов.
2. **Nonce ⇒ dynamic rendering всей площадки.** Per-request nonce нельзя вычислить статически → Next выводит страницы из статики/ISR в динамику. Это регрессия LCP публичных SEO-страниц (артисты/релизы/треки), которые как раз держатся на статике. В пассе стабилизации — недопустимо.
3. **Hash-only не спасает.** Хэш сработал бы для статичного reduce-motion скрипта, но инлайн RSC-стриминг Next (`self.__next_f.push(...)`) несёт per-request данные → его хэш не фиксируется. Значит для фреймворковых скриптов всё равно нужен либо `'unsafe-inline'`, либо nonce.

**Возврат** — отдельной задачей вне стабильной версии: либо (a) убрать сырой инлайн-скрипт reduce-motion (перевести на next/script с nonce или на CSS-only pre-paint), затем nonce + принять dynamic rendering там, где нет статики; либо (b) дождаться нативной поддержки nonce для статики в Next.

## Observability

### `request_id`-корреляция — отложена вместе с Sentry
Структурные JSON-логи **уже есть**: `apps/web/lib/observability.ts` (`captureError`) пишет в stderr
JSON `{level, service, message, ...ctx, ts}` + опциональные Telegram/webhook-алерты (анти-шторм-гейт).
Открыт именно **`request_id`** — сквозной идентификатор запроса (middleware → AsyncLocalStorage → лог),
чтобы скоррелировать все строки одного запроса при инциденте.

**Отложено с причиной.** Реальную ценность request_id даёт только агрегатор трейсов (Sentry/GlitchTip),
а он вырезан (решение принято на 1 ГБ; после апгрейда до 2 ГБ основание отпало — см. `TODO.md` «Observability»). Полумера
(request_id в логах, которые читаются только через `journalctl`, без аггрегации) — низкая
ценность. Возврат — единой задачей вместе с внешним приёмником ошибок.

### ✅ Каталожный гейт видимости не смотрел на статус трека — закрыто
Найдено 04.09.2026 при покрытии гейтов тестами на живой базе, закрыто в тот же день.

Было: `artistHasPublishedTrack` (`packages/db/src/queries/artists.ts`) проверял только
`releases.status = 'PUBLISHED'`. Артист с единственным треком в `BLOCKED` или `FAILED`

`search.ts`. **`PROCESSING` намеренно оставлен видимым:** транскодинг это минуты, а
`artist-guard.ts` отдаёт 404 артисту без опубликованных треков — иначе свежеопубликованный
артист ловил бы 404 на собственной странице, пока режется HLS.
