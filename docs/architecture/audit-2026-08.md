# Vire — инженерный аудит: что построено, что менять, что не трогать

**Дата:** 28.08.2026 · **Версия:** v1.51.6 · **Ветка:** main
**Метод:** чтение кода, прогон тестов, внешний ресёрч. Read-only, код не менялся.
**Спутники:** `current-state.md` (карта системы), `dependency-map.md` (граф),
`documentation-audit.md` (расхождения доков), `../vireglass/spec-2026-08-28.md` (спецификация стекла).

---

## Итог

**Стек менять не надо** — ни язык, ни фреймворк, ни базу, ни очередь. Ни один
кандидат (Go, Rust, Bun, NestJS, Elixir) не выигрывает в том, что для Vire имеет
значение: тяжёлая работа уже в нативном коде (ffmpeg на C, ONNX на C++), HTTP-слой
узким местом не является, а стоимость перехода на 127 000 строк с 3 405 тестами реальна.

**Архитектура здоровее, чем обычно бывает.** `packages/core` действительно не знает
про Next, React и БД — проверено grep, а не декларацией, и защищено барьером в CI.
3 405 тестов, все зелёные. Восемь статических гейтов, каждый вырос из реального
инцидента на проде. Четыре из пяти блокеров прошлого аудита закрыты за две минорные
версии.

**Главная находка — не в коде, а в расхождении документации с железом.** Спека сервера
устарела в 16 файлах, и на неё опираются архитектурные выводы («Sentry не влезает»,
«поисковый движок не влезает», «Core как сервис невозможен»). Тюнинг Postgres до сих
пор посчитан от вдвое меньшей машины.

**Стратегическая находка по VireGlass отрицательная.** «Кросс-платформенная система
материалов» в исходной постановке недостижима: iOS и веб физически не дают шейдеру
доступ к пикселям фона. Это ограничение платформ, а не архитектуры. Из этого следует
правильная и достижимая постановка — и в ней у Vire уже есть работающее ядро.

## Поправка к первой версии этого отчёта

Первая редакция утверждала, что прод — **1 vCPU / 1 ГБ**, и строила на этом часть
рассуждений. Это неверно. Источник ошибки: `docs/ops/deployment.md`, где спека устарела
после выполненного апгрейда.

Ошибка методическая, а не арифметическая: весь смысл аудита был «репозиторий — источник
правды, документам не верить», и единственное место, где я поверил документу, оказалось
именно тем, что нельзя проверить из репозитория. Правильное поведение было — пометить
факт как непроверяемый и спросить, а не принять.

Дополнительно снята иллюстрация с числами «190 с → 154 с» из §6: эти значения были
выдуманы для наглядности. Замеров разбивки времени транскода не существует, и приводить
их как оценку было нельзя.

**Что изменилось по существу:**

# Часть I · Система

## 1. Текущая система

Четыре приложения, десять пакетов, Turborepo + pnpm. Полная карта — `current-state.md`.

| Область | Строк | Роль |
|---|---:|---|
| `apps/web` | 81 180 | Next.js 16.2.11 / React 19.2.4 — фронт и 127 route handlers |
| `packages/core` | 19 051 | Домен и платформа, чистый TS |
| `packages/db` | 10 766 | Drizzle: схема, 58 миграций, 21 репозиторий, `queries/` |
| `apps/mobile` | 9 377 | React Native 0.86 / Expo 57, Android |
| `apps/worker` | 4 215 | 12 BullMQ-воркеров в одном процессе |
| `apps/desktop` | 323 | Tauri v2 — Rust-обвязка, UI через WebView |

### Два пути данных, а описан один

`CLAUDE.md` заявляет `Route → Service → Repository → Postgres`. Это верно для записи.
Чтение идёт иначе и не задокументировано нигде:

```
ЗАПИСЬ:  Route Handler → Service (core) → Repository (db) → Postgres
ЧТЕНИЕ:  Server Component → packages/db/src/queries/*.ts → Postgres
         Route Handler    → packages/db/src/queries/*.ts → Postgres
```

`packages/db/src/queries` — **50 файлов, 7 235 строк**, ~150 экспортов, 240
файлов-потребителей. Там живут ранжирование, агрегации и фильтры видимости.

Практическое следствие: «вынести core в переиспользуемый пакет» ≠ «вынести
бизнес-логику». Мобилка это уже показывает — она не может импортировать `@vire/db`
(Drizzle не работает в RN), поэтому берёт контракты (29 импортов) и клиент (7),
а `core` — всего 4 раза.

### Блокеры прошлого аудита — закрыто 4 из 5

| Блокер (v1.49.4) | Сейчас | Доказательство |
|---|---|---|
| RBAC размазан по 19 файлам, три списка ролей разошлись | **закрыт** | `core/platform/access`; inline-проверок роли осталась 1 |
| Контракты не централизованы (4 эндпоинта) | **закрыт** | `api-contracts`: 3 → 26 файлов, гейт `check:contracts` |

| Read-путь внутри веба | **открыт** | 7 235 строк `queries/` в обход core |

## 3. Сильные стороны

Только проверенное и только то, что реально редко встречается.

**1 · Чистота ядра — фактическая.** `packages/core` не импортирует Next, React,
`@vire/db`. Нет `new Date()` в логике (инъектированный `Clock`), нет `Math.random()`,
`fetch` только за портом. И это **защищено машиной**: `check-layers.mjs` валит CI.

**2 · Восемь статических гейтов, каждый из реального инцидента.** `check:routes`
(конфликт имён динамических сегментов — ронял прод в рантайме, `next build` молчал),
`check:i18n`, `check:layers`, `check:contracts`, `check:caller`, `audit:design`,
`pnpm audit`, smoke прод-артефакта. Плюс Dockerfile валит сборку без `libvips-cpp.so.*`
после того, как `sharp` уронил прод на v1.34.0.

**3 · Реконсиляция хранилища.** Удаление сущности не удаляет файлы синхронно: запись
падает в `storage_orphans` (bucket, prefix, reason, attempts, lastError), почасовой
воркер выгребает с grace-периодом в сутки. Падение между БД и S3 не теряет ключи.

**4 · Идемпотентность транскода.** Job проверяет `status === 'READY'` и выходит.
Терминальное падение переводит `PROCESSING → FAILED` *условным* UPDATE — поздний
`READY` не затирается — и шлёт письмо артисту. Никогда не бросает.

**5 · Модель членства уже изоморфна платформенной.** `artist_members` — join
`user_id ↔ artist_profile_id` + role. Дашборд уже работает через `innerJoin`.
Переход к `organization_members` — переименование, а не проектирование с нуля.

**6 · Нулевая зависимость от UI-фреймворка.** README заявляет «Radix Primitives /
shadcn». Фактически установлен один `@radix-ui/react-slot` — утилита, не набор
примитивов. Диалоги, поповеры, шиты написаны свои. **Документация занижает реальность.**

| Проблема | Класс | Суть |
|---|---|---|
| **Тюнинг Postgres посчитан от 1 ГБ** | **HIGH** | `shared_buffers=96MB`, `effective_cache_size=256MB` на машине с 2 ГБ — база недообеспечена |

# Часть II · Технологии

## 6. Анализ бэкенда: где узкое место на самом деле

### Профиль нагрузки

| Операция | Характер | Где исполняется |
|---|---|---|
| HTTP-запросы, SSR | IO-bound | Node, event loop не насыщен |
| Запросы к Postgres | IO-bound | postgres.js, пул 10 |
| Транскод HLS | **CPU-bound** | **ffmpeg — нативный C, вне JS** |
| Классификация жанра | **CPU-bound** | **ONNX — нативный C++**, блокирует поток |
| BPM / тональность / мел-спектрограмма | **CPU-bound** | **~600 строк чистого JS** |
| SSE (чат, джем) | долгие соединения | Node подходит хорошо |
| Фоновые джобы | смешанный | отдельный процесс, API не блокирует |

### Главный вывод

**Смена языка HTTP-слоя не даёт ничего, потому что HTTP-слой не является узким местом.**
Вся тяжёлая работа уже вынесена в нативный код: ffmpeg на C, ONNX на C++. Node в этой
системе оркеструет процессы и ходит в БД — то, в чём он хорош и где разница между
рантаймами не читается.

Этот вывод **не зависит от числа ядер**. Ни на одном, ни на двух, ни на восьми ядрах
переписывание Express-подобного слоя на Go не ускорит ffmpeg.

### Единственный кандидат на нативную переработку

`detectBPM` (автокорреляция O(n·lags)) и `detectKey` (Goertzel по полутонам на кадр) —
~600 строк чистого JS. Это настоящий CPU-bound JavaScript, и теоретически Rust/C дал бы
здесь кратное ускорение.

**Но насколько это важно — неизвестно, потому что разбивка времени транскода
не измерялась.** Транскод состоит из четырёх этапов (ffmpeg → BPM/key → ONNX → waveform),
и доля JS-DSP в общем времени не замерена ни разу. Без этого числа решение о нативном
модуле принимать нельзя: если DSP занимает 10% — переписывать бессмысленно, если 50% —
оправданно.

**Замер стоит один вечер:** обернуть четыре этапа в `performance.now()` и записать
в лог джоба. Это же закрывает пробел §13 (телеметрия длительности).

Классификация: **RESEARCH** — сначала измерить, потом решать.

## 7. Сравнение стеков

Правило отбора: новая технология обязана выиграть в том, что для Vire имеет значение.
«Современнее» и «все используют» — не аргументы.

| Кандидат | Что выиграет | Что проиграет | Вердикт |
|---|---|---|---|
| **Текущий: Next 16 + Node 22** | SSR и API в одном процессе; один язык на 4 клиента; 3 405 тестов уже написаны | — | **KEEP** |
| **Go** | Меньше RSS, быстрый старт | Потеря SSR (нужен второй процесс); переписывание 127 роутов; потеря общих типов с фронтом и мобилкой; ~19 000 строк core заново. Не ускоряет ffmpeg | REJECT |
| **Rust (axum)** | Максимум производительности и минимум памяти | То же, что Go, плюс кратно ниже скорость разработки. Для соло-разработчика с продуктовым темпом — прямой убыток | REJECT |
| **Bun** | Быстрее старт и установка | Next 16 на Bun в проде — риск без выигрыша; нативные модули (`sharp`, `onnxruntime`, ffmpeg) — самая хрупкая часть, и там совместимость наименее гарантирована | REJECT |
| **NestJS** | Структура «из коробки» | Vire *уже* имеет более строгую структуру, чем даёт Nest, и она проверяется машиной. DI-контейнер добавит вес без единого нового свойства | REJECT |
| **Elixir / Phoenix** | Лучший в классе realtime | Полное переписывание, второй язык у соло-разработчика, отказ от общих типов. Текущий SSE работает | REJECT |
| **Гибрид: нативный воркер для DSP** | Кратное ускорение BPM/key | Доля DSP в общем времени не измерена; риск нативной зависимости в Docker (прецедент `sharp`) | **RESEARCH** |

### Монолит против сервисов

Текущая раскладка (web + worker) — уже правильное разделение: одна граница ровно там,
где нужна (долгие CPU-задачи не блокируют API). Второе ядро делает это разделение
эффективнее, а не избыточнее.

Дробить дальше на 2 ГБ с шестью контейнерами — добавлять операционную нагрузку без
выигрыша. **KEEP.**

Отдельно: вывод «Core как отдельный сервис невозможен» из прошлого аудита был сделан
на 1 ГБ. На 2 ГБ он **перестал быть физическим ограничением** и стал вопросом
целесообразности. Целесообразности по-прежнему нет — второго продукта не существует, —
но формулировку в `architecture.md` стоит поправить: это выбор, а не невозможность.

## 8. База данных

PostgreSQL 16 + Drizzle. 58 миграций, 20 файлов схемы. Замены не требует.

### Что сделано правильно

- `track_contributors.payout_share numeric(5,2)` — деньги отвязаны от бренда артиста.
  Решение, которое обычно приходится переделывать через год
- `rights_holders` отдельно от `artist_profiles`
- Полиморфизм без FK уже применён точечно: `purchases.itemId`, `reports.targetId`
- Live-присутствие в Redis (ZSET), не в Postgres — правильно, это высокочастотная запись

### Главная находка: тюнинг отстал от железа

```yaml
# docker-compose.prod.yml — сейчас (посчитано от 1 ГБ)
-c shared_buffers=96MB
-c effective_cache_size=256MB
-c work_mem=4MB
-c max_connections=50
```

Машина теперь 2 ГБ, цифры не пересматривались. `effective_cache_size` — это подсказка
планировщику о том, сколько данных реально лежит в кэше ОС; заниженное значение
заставляет его избегать index scan там, где тот выгоден. То есть это влияет не только
на память, но и **на выбор планов запросов**.

Направление правки (проверять замером, не принимать на веру):

```yaml
-c shared_buffers=256MB          # ~12% от 2 ГБ; box разделяемый, 25% было бы агрессивно
-c effective_cache_size=768MB    # реалистичная оценка кэша ОС
-c work_mem=8MB
-c max_connections=30            # согласовать с пулом драйвера
```

Верификация: `EXPLAIN (ANALYZE, BUFFERS)` на тяжёлых запросах ленты и волны до и после.
Классификация: **IMPROVE**, приоритет высокий — это самый дешёвый прирост в отчёте.

### Пул соединений

```ts
// packages/db/src/client.ts — сейчас
const client = globalForDb._pgClient ?? postgres(connectionString);
```

Без опций postgres.js берёт `max: 10`. Web и worker дают до 20 бэкендов. Задать явно
и согласовать с `max_connections`. **IMPROVE**, приоритет средний.

### Про N+1 — честно

В `queries/` найдено 29 мест с `await` внутри цикла и 23 с `Promise.all`. Построчный
разбор 7 235 строк в объём аудита не вошёл. Утверждать, что N+1 есть или нет, я не могу —
это требует профилирования на проде с реальными данными.

## 9. Воркеры

12 воркеров BullMQ в **одном процессе**.

| Свойство | Состояние |
|---|---|
| Идемпотентность | есть — проверка `READY`, `onConflictDoUpdate`, условный UPDATE при падении |

| Расписания | `upsertJobScheduler` — идемпотентно при рестарте |
| Обработка краха процесса | есть — алерт с ожиданием доставки, затем `exit(1)` |
| Блокировка API воркерами | невозможна — отдельный контейнер |
| Потеря лока под нагрузкой | смягчена — `lockDuration` 10 мин |
| `concurrency: 2` у транскода | **корректно** — по задаче на каждое из двух ядер |
| Отмена задачи | **нет** — запущенный транскод не остановить |
| Телеметрия длительности | **нет** — есть только факт падения |

**Замена BullMQ не оправдана.** RabbitMQ, NATS, Kafka — ещё один постоянный процесс.
Redis уже стоит и используется для присутствия и rate limiting. **KEEP.**

Что добавить: запись длительности джоба по этапам (см. §6). Одна строка в обработчике
`completed`, и она одновременно отвечает на «почему медленно» и даёт число для решения
о нативном DSP. **IMPROVE.**

## 15. Философия и центральное ограничение

**Проблема VireGlass — не шейдер. Проблема — доступ к пикселям фона.**

Шейдер уже написан, дважды, и написан хорошо. Не решено то, что определяет всю
стратегию: *можно ли на данной платформе получить уже отрисованный фон в виде текстуры
на каждом кадре*.

| Платформа | Доступ к фону | Механизм |
|---|---|---|
| **Android 13+** | да, официально | `RenderEffect.createRuntimeShaderEffect` — доказано в репозитории |
| Android 12 | частично | `createBlurEffect` есть, runtime-шейдера нет |
| **iOS / macOS** | **нет публичного API** | `drawViewHierarchyInRect` слишком медленный для 60 fps; Apple использует приватный `CABackdropLayer` |
| Web (Chrome) | косвенно | `backdrop-filter: url(#svg)` + `feDisplacementMap` |
| **Web (остальные)** | **нет** | WebGPU/WebGL не видят DOM; `HTML-in-Canvas` — origin trial Chrome |
| Desktop (Tauri) | как web | системный WebView |

**Вывод, меняющий постановку:** VireGlass не может быть «кросс-платформенной системой
материалов с единым рендерингом». Не из-за архитектуры — три из четырёх платформ
не дают шейдеру фон.

Честная формулировка: *VireGlass — спецификация материала плюс референсная реализация
на Android, с деградацией до перцептивных приближений там, где оптика недоступна.*

## 16. Что уже построено

Три слоя, и разделение правильное:

```
┌─ Skia-канвас (SKSL)   — поверхность: фаска, Френель, блик, кромка, иконка, тень
├─ GlassLensView (AGSL) — преломление: семплирует размытый фон по смещённой координате
└─ BlurView (dimezis)   — бэкдроп: живой размытый контент экрана
```

Что сделано правильно и должно сохраниться:

1. **Профиль поверхности — плоская середина плюс фаска, а не полусфера.** В коде есть
   объяснение: полусфера гнёт всё поле зрения и читается мыльным пузырём
2. **Форма через SDF скруглённого прямоугольника.** Круг — частный случай. Кнопка
   навигации и панель мини-плеера используют один шейдер
3. **Нормаль как градиент SDF** — корректный Френель на произвольном rounded-rect
   без 3D-геометрии
4. **Аберрации только в фаске** (∝ t²). Перцептивно верно: в толстом стекле центр резкий
5. **Premultiplied-альфа обработана корректно** — `straight()` с порогом 0.004
6. **Кромка — две дуги, а не кольцо.** Ровное кольцо читается нарисованным контуром;
   перепад яркости по кругу глаз опознаёт как стекло. Лучшее решение в коде

## 17. Модель слоёв и главная граница

| Слой | Вклад в восприятие | GPU-цена | Нужен фон? |
|---|---|---|---|
| Backdrop (захват) | обязателен | **максимальная** | — |
| Blur / diffusion | высокий | средняя | да |
| Refraction | **высокий** — отличает стекло от матовой плёнки | средняя (6 выборок) | да |
| Edge / Fresnel | **очень высокий** — даёт толщину | низкая | **нет** |
| Specular | высокий | низкая | **нет** |
| Tint | средний | ~0 | **нет** |
| Distortion (эластичность) | средний — это «характер» | ~0 | **нет** |
| Dispersion | низкий отдельно | низкая | да |

**Ключевое наблюдение:** Fresnel + Specular + Edge + Tint + Distortion — это один
фрагментный проход по SDF, которому фон не нужен вообще.

```
СЛОЙ A «поверхность» — SDF, Френель, блик, кромка, тинт, деформация
        фон не нужен · дёшев · портируется на ВСЕ платформы

СЛОЙ B «оптика»      — захват фона, блюр, преломление, дисперсия
        фон нужен · дорог · доступен не везде
```

**Это архитектурная граница VireGlass.** Слой A даёт 60–70% эффекта и работает везде,
включая iOS и веб. Текущий код это разделение уже физически воплощает (Skia-канвас = A,
GlassLens + BlurView = B) — но не называет его так и потому не может им пользоваться.

## 18. Бэкдроп: где текущая реализация не масштабируется

Каждая поверхность несёт *свой* `BlurView` (`dimezisBlurView`), который перерисовывает
дерево вьюх в bitmap каждый кадр. Это не системный блюр — библиотечная эмуляция,
придуманная до Android 12.

Три следствия, два уже проявились:

1. **Стоимость линейна по числу поверхностей.** N стёкол = N захватов всего экрана
2. **Рекурсия в дереве RenderNode** — уже случилась: `SIGSEGV`, `prepareTreeImpl`,
   170 повторов пары в стеке. Вылечено ограничением области, но причина конструктивная
3. **Стекло внутри экрана деградирует до фолбэка** — иначе замкнётся дерево. То есть
   *сегодня настоящее стекло получают только таб-бар и мини-плеер*

### ⛔ Предлагавшаяся замена — ОТМЕНЕНА экспериментом (Phase 2)

Здесь предлагалось заменить `dimezisBlurView` на
`createChainEffect(runtimeShaderEffect, blurEffect)`. **Это неверно.**

`RenderEffect` не даёт доступа к пикселям ПОД вьюхой — он преобразует содержимое
самого узла вместе с детьми. Фон в шейдер попадает именно от `BlurView`-ребёнка,
а не от эффекта. `createBlurEffect` в такой цепочке размыл бы пустое собственное
содержимое вьюхи, то есть заменять было бы нечего.

Доказано зондом на устройстве (карта альфы: без детей — сплошной ноль при
исполняющемся шейдере). Разбор и данные — `docs/vireglass/ADR-001-rendering-architecture.md` §3.

Ошибка была в том, что фраза документации «эффект применяется к содержимому узла»
прочиталась как «эффект даёт содержимое под узлом». Ниже — рассуждение в исходном виде,
оставлено как след ошибки.

| Что даёт | Против текущего |
|---|---|
| Системный блюр вместо перерисовки в bitmap | Быстрее и качественнее — прямая рекомендация документации Android |
| Рекурсия невозможна конструктивно | Убирает целый класс крашей |
| Стекло работает внутри экранов | Сейчас доступно только двум элементам |
| Минус сторонняя зависимость | `dimezisBlurView` через `expo-blur` уходит |

**REFACTOR — самая ценная техническая правка во всём VireGlass, и она локальна:**
`GlassLensView.kt` плюс удаление BlurView-обвязки.

## 19. Модель материала

```
Material {
  // слой A — везде
  shape:     { halfW, halfH, corner }   // SDF
  bevel:     0…1
  tint:      rgba
  edge:      { keyLight, intensity }
  specular:  { roughness, intensity }
  elastic:   { pull, stretch }

  // слой B — где платформа позволяет
  blur:      radius
  thickness: → magnify
  chroma:    0…n                        // только в фаске
  spherical: 0…n                        // только в фаске
}
```

Три дешёвых улучшения:

- **Связать толщину с размером.** Apple при увеличении элемента усиливает лензинг.
  Сейчас `magnify` — константа 1.22. Одна строка. **IMPROVE**
- **Гироскоп в блик.** Apple привязывает блик к гироскопу — это то, что «делает материал
  физическим». Стоимость — две униформы. **Самое дешёвое заметное улучшение.** **IMPROVE**
- **Морфинг через SDF.** Круг → капсула → rounded-rect — интерполяция `u_half` и
  `u_corner`, без кроссфейда. Вьюха *уже принимает эти пропы*. **IMPROVE**

Чего **не** делать: полный PBR/GGX. Различие с Blinn-Phong на экране не читается,
стоимость выше.

## 20. Рендер-граф и блюр

Схема «один захват → пирамида блюра → много поверхностей» **на Android не нужна**:
`RenderEffect` уже даёт один захват, система кеширует RenderNode. Она станет нужна
только при собственном рендерере (WebGPU на вебе).

Блюр, если придётся писать самому:

| Алгоритм | Проходов | Качество | Когда |
|---|---|---|---|
| Box | 1–2 | низкое, «квадратит» | никогда для стекла |
| Gaussian (сепарабельный) | 2 | эталон | малый радиус |
| Kawase | 3–5 | близко к Gaussian | средний радиус |
| **Dual Kawase** | 2·log r | почти Gaussian | **большой радиус, мобильный GPU** |
| Mipmap-пирамида | 1 + ген. | грубое | качество LOW / MINIMAL |

Замеры Intel: Dual Kawase быстрее Gaussian в 1.5–15×; 5-проходной Kawase — 20 выборок
на пиксель против 34 у Gaussian 35×35. Придуман под мобильную пропускную способность.

| Платформа | Слой A | Слой B | Как |
|---|---|---|---|

| Android 12 | Skia SKSL | блюр без преломления | `createBlurEffect` |

2. **WebGPU** — доступен во всех браузерах с конца 2025, но **не видит DOM**. Годится,

3. **Только слой A** — SDF, Френель, блик, тинт поверх `backdrop-filter: blur()`

**Рекомендация: (3) как база, (2) точечно там, где фон — своя графика** (плеер поверх
обложки — идеальный случай). (1) не брать.

## 23. Качество и доступность

Порядок отключения при снижении качества, по возрастанию «жалко терять»:

```
дисперсия → сферическая аберрация → преломление → радиус блюра →
блик → Френель/кромка → тинт
```

Кромка и Френель уходят последними: дают толщину и работают без фона.

```
Полное стекло → без преломления → блюр + тинт → тинт → сплошной фон
```

**Гистерезис обязателен:** вниз — при среднем frame time выше порога за 2 с, вверх —
не раньше 10 с стабильности. Иначе осцилляция на границе.

**Доступность — не опция.** `Reduce Transparency` отключает слой B, `Reduce Motion` —
эластичность. Контраст текста считается *от сплошного фолбэка*, а не от стекла.

## 24–25. OSS и лицензия

| Компонент | Отделяется? |
|---|---|
| `modules/glass-lens` (Kotlin + AGSL) | **да** — полностью автономен |
| SKSL-шейдер поверхности | **да** — знает об `ICON_PATHS`, развязывается пропом |
| `lib/blur-target.tsx` | **да** — доменно-нейтрален |
| Остальное из `liquid-glass.tsx` | нет — `colors` из темы Vire, `IconName` из каталога |

**Секреты в истории git:** `.env` не коммитился ни разу, FCM-креды и `*.jks`/`*.p8`/`*.p12`
в `.gitignore`. **Препятствий к публикации нет.**

**Стоит ли публиковать — пока нет.** Публиковать имеет смысл то, что (а) решает чужую
проблему, (б) измерено, (в) работает больше чем на одной платформе. Сейчас выполнено
**ноль из трёх**. Порядок: §18 → §22 → выделение пакета → публикация. **DEFER.**

**Лицензия — Apache-2.0, не MIT.** Причина конкретная: Apache даёт явный патентный грант.
VireGlass — графическая техника в области, где у Apple есть патенты на интерфейсные
эффекты. MIT о патентах молчит.

# Часть IV · Платформа и активы

## 26. VireMusic как dogfooding

Принцип «VireGlass → VireMusic, а не наоборот» правильный и **сейчас соблюдается**:
`glass-lens` не знает ни о треках, ни о плеере — он принимает геометрию и параметры оптики.

Единственное просачивание продукта — `ICON_PATHS` в шейдере поверхности. Развязывается
передачей маски как пропа.

## 27. Возможности платформы

Правило: пакет появляется, когда в него *переезжает работающий код*, а не заранее.
Доказательство из репозитория — `packages/media` создан заранее и за всё время набрал
109 строк, из них 72 теста.

| Кандидат | Основание | Вердикт |
|---|---|---|
| Логика очереди плеера (`lib/player/queue.ts`) | 100% чистые функции, второй потребитель *уже существует* | **EXTRACT** |
| Форматтеры | Дублируются в web и mobile прямо сейчас | **EXTRACT** |
| Утилиты насыщения сигнала | Три копии одной идеи в репозитории | **EXTRACT** |
| Модель членства (`artist_members`) | Уже изоморфна платформенной | KEEP до второго продукта |
| Уведомления, покупки, жалобы | Уже полиморфны без FK | KEEP |
| White-label / мультитенантность | Упирается в build-time конфиг | DEFER |
| Полиморфизация `likes`/`follows` | Второго типа лайкаемой сущности нет | DEFER — сейчас это чистая потеря целостности |

Только то, что реально существует в коде. **Спроса на рынке я не измерял и выдумывать
его не буду** — колонка «уникальность» отражает наблюдаемое, не желаемое.

инцидентах, и их ценность объяснима одним абзацем.

## 29. Кандидаты на миграцию

**Крупных миграций не предлагается ни одной.** Ни бэкенда, ни базы, ни очереди,
ни стиля API. Это вывод из §6 и §7, а не осторожность.

Единственная обсуждаемая — вынос DSP в нативный модуль, и она требует сначала замера
доли DSP в общем времени транскода (§6).

# Часть V · Решения

## 30. Что не трогать

| Что | Почему |
|---|---|
| Next.js + Node + TypeScript | Один язык на 4 клиента; SSR и API в одном процессе |
| PostgreSQL + Drizzle | Ни одного доказательства против; схема продумана на годы вперёд |
| BullMQ + Redis | Redis уже нужен для присутствия и rate limiting |
| Один процесс на 12 воркеров | Правильная раскладка для этого объёма памяти |
| Чистота `packages/core` и барьер `check:layers` | Главный архитектурный капитал проекта |
| Реконсиляция `storage_orphans` | Правильно спроектирована, работает |
| Отсутствие Radix/shadcn | Нулевая зависимость от чужого UI-фреймворка — преимущество |
| Восемь статических гейтов | Каждый оплачен реальным инцидентом |
| REST-стиль API | Работает, покрыт контрактами; GraphQL/tRPC не решают существующих проблем |
| `concurrency: 2` у транскода | Соответствует двум ядрам |
| Профиль стекла «плоская середина + фаска» | Верное перцептивное решение |
| Кромка двумя дугами | Лучшее решение в графическом коде |

## 31. Риски

| Риск | Вероятность | Смягчение |
|---|---|---|
| **Документация разошлась с реальностью в несущих фактах** | **состоялась** | Спека железа — в одно место, остальное ссылками |
| Свежая advisory валит `gates` и роняет релиз | **высокая** — уже случалось (v1.48.0, `nanoid`) | Гонять `pnpm audit` перед тегом; фиксить кареткой, не `>=` |
| Нативная зависимость ломает прод, локальная сборка молчит | средняя — уже случалось (`sharp`, v1.34.0) | Барьер в Dockerfile есть; ленивый импорт в try |
| Postgres недообеспечен относительно машины | **состоялась** | §8, переоценка тюнинга |
| OOM выбивает Postgres, а не воркер | средняя | `mem_limit` контейнерам |
| VireGlass не выдержит замеров на реальном железе | **неизвестна — не измерялось** | §22 до любого расширения |
| Патч `react-native-track-player` отвалится на мажоре | средняя | Патч в `patches/`; переносить вручную |
| 7 235 строк `queries/` расходятся с эндпоинтами | средняя | Прошлый аудит уже нашёл две реализации одного чтения |
| Соло-разработчик — единственная точка отказа | — | Документация сильная; барьеры в CI работают как «второй разработчик» |

## 32. Открытые вопросы

1. **VireGlass — продукт или украшение VireMusic?** Если продукт, первым идёт §18 + §22.
   Если украшение, §19 (гироскоп, морфинг) даёт больше результата на вложенный час
2. **Есть ли реальное Android-устройство для замеров?** Без него §22 невыполним,
   а без §22 VireGlass не готов ни к публикации, ни к расширению
3. **Этап 2 (YooKassa) или платформенная работа?** Конкурируют за одно время
4. **Второй продукт — план или гипотеза?** От ответа зависит, сколько обобщения оправдано
5. **Планируется ли ещё апгрейд?** 2 ГБ снимают часть ограничений, но потолок ёмкости
   на новом железе не измерен — единственный замер (15–20 слушателей, 27.07.2026) сделан
   на старой конфигурации и устарел
