# Замер масштабирования — 28.08.2026, эмулятор

**Что меряли:** как растёт стоимость кадра с числом стеклянных поверхностей
в текущей архитектуре (dimezis-захват + AGSL-линза + Skia-поверхность).

---

## Стенд

| Параметр | Значение |
|---|---|
| Устройство | эмулятор Android `VireMusic_Test` (x86_64) |
| Android | 16 (SDK 36) |
| GPU | **host-ускорение**, AMD Radeon Vega 8 через ES-транслятор, OpenGL ES 3.1 |
| Разрешение | 1080×2400, 420 dpi (плотность 2.625) |
| Частота | 60 Гц (`hw.lcd.vsync = 60`) |
| Сборка | **debug**, JS в dev-режиме, Metro |
| Сцена | `apps/mobile/screens/glass-bench.tsx`, `EXPO_PUBLIC_GLASS_LAB=bench` |
| Компонент | продовый `LiquidGlassButton`, размер 58 dp |
| Фон | 40 строк текста, непрерывная анимация (2.2 с цикл) |

> ⚠️ **Границы применимости.** Это десктопная iGPU через слой трансляции, а не мобильный
> тайловый GPU (Adreno/Mali), и debug-сборка вместо release. Абсолютные миллисекунды сюда
> не переносятся, пропускная способность памяти и термалка не воспроизводятся вовсе.
> Валидно **относительное** сравнение и **форма** зависимости от N.

---

## Протокол

`scripts` стенда: тап по кнопке N → 4 с на стабилизацию → `dumpsys gfxinfo <pkg> reset`
→ 15 с анимации → снятие статистики. Сырые дампы и скриншот каждой сцены сохраняются.

Каждая сцена проверялась скриншотом: число видимых стёкол должно совпадать с N.

### Стоимость одного стекла

Прирост p50 над контролем, делённый на N:

| N | Δp50 | на стекло |
|---:|---:|---:|
| 1 | 0 мс | ~0 |
| 3 | +14 мс | 4.7 мс |
| 6 | +31 мс | 5.2 мс |
| 10 | +43 мс | 4.3 мс |

**Зависимость линейная, ~4.3–5.2 мс на поверхность.** Ничего между поверхностями
не переиспользуется: каждое стекло несёт свой захват фона, свой блюр и свой шейдер.

Первое стекло почти бесплатно (0 мс к p50) — оно укладывается в уже существующий
простой кадра; со второго начинается видимый рост.

### Бюджет кадра

При 60 Гц бюджет 16.7 мс. **Контроль уже 34 мс** — сцена сама по себе не укладывается
(debug-сборка + эмулятор). Поэтому «сколько стёкол влезает в бюджет» по этим цифрам
сказать нельзя; можно сказать только, во сколько обходится каждое дополнительное.

Практический ориентир текущего продукта — 2 стеклянные поверхности одновременно
(таб-бар + мини-плеер), что соответствует ~5–10 мс сверх базовой стоимости кадра.

## Что этот замер НЕ показывает

- абсолютную производительность на реальном телефоне;
- поведение мобильного тайлового GPU (bandwidth, on-chip память);
- термальный троттлинг и расход батареи;
- release-сборку (JS dev-режим искажает базовую линию);
- 90/120 Гц.

---

## Побочная находка: краш воспроизводится за секунды

Первая редакция стенда клала стёкла **внутрь** их же `BlurTargetView`. Результат —
детерминированный `SIGSEGV` в RenderThread:

```
RenderNode::prepareTreeImpl
SkiaDisplayList::prepareListAndChildren   ← сотни повторов пары
```

Это тот же краш, что живой прогон поймал в инкременте 27, и он **не частный баг стенда**,
а следствие конструкции: `dimezisBlurView` рисует цель внутрь себя, поэтому стекло не
может находиться внутри своей цели захвата.

Обход в проде — `BlurTargetScope`: потребитель внутри цели получает `null` и деградирует
до полупрозрачной плашки. Отсюда прямое продуктовое следствие: **настоящее стекло сегодня
доступно только поверхностям вне экрана** (таб-бар, мини-плеер), а внутри экранов его нет.
