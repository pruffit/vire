# Замеры VireGlass — протокол

Ссылка на этот файл стоит в `apps/mobile/screens/glass-bench.tsx`.

## Правила, без которых замер бессмысленен

1. **Только физическое устройство.** Эмулятор завышает стоимость GPU примерно в 20 раз
   (десктопная iGPU через трансляцию). Для проверки *корректности* он годится, для оценки
   *стоимости* — нет даже по порядку величины. Доказательство: расхождение
   `2026-08-28-scaling-emulator.md` и `2026-08-28-scaling-device-release.md`.
2. **Только release-сборка.** В debug JS-бандл раздаёт Metro, и в кадр попадает не то.
3. **Фон обязан двигаться.** На статике `dimezisBlurView` не перезахватывает контент, а
   `gfxinfo` не наберёт кадров.
4. **Стекло — снаружи своей цели захвата.** Внутри цели дерево RenderNode замыкается и
   рантайм падает (ADR-001 §2). В сцене замера `BlurTargetView` оборачивает только фон.
5. **Записывать частоту экрана.** Бюджет кадра от неё зависит: 120 Гц → 8.33 мс.
6. **Записывать питание и температуру.** Зарядка и нагрев меняют результат.

## Прогон

> ⚠️ **Смена `EXPO_PUBLIC_GLASS_LAB` сама по себе новую сборку не даёт.** Переменная
> инлайнится babel'ом в JS-бандл, но gradle сравнивает входы задачи бандла по содержимому
> файлов — переменной окружения он не видит и оставляет задачу UP-TO-DATE. В APK уезжает
> бандл от прошлого режима, и вы меряете не тот экран (проверено: сборка с `=bench` дала
> стенд материала). Перед сменой режима снести выход бандла:
>
> ```bash
> rm -rf app/build/generated/assets/react app/build/intermediates/assets/release
> ```
>
> Если JS-исходники между сборками менялись, пересборка происходит сама и удалять ничего
> не нужно.

```bash
cd apps/mobile/android
rm -rf app/build/generated/assets/react app/build/intermediates/assets/release
EXPO_PUBLIC_GLASS_LAB=bench ./gradlew assembleRelease
adb install -r app/build/outputs/apk/release/app-release.apk
adb shell am start -n com.anonymous.viremobile/.MainActivity

adb shell dumpsys gfxinfo com.anonymous.viremobile reset
# переключить сцену в приложении, дать ей поработать ~20 с
adb shell dumpsys gfxinfo com.anonymous.viremobile
```

Снимать на каждой конфигурации: `Total frames`, `Janky frames` (число и %),
`Missed Vsync`, `Frame deadline missed`, перцентили 50/90/95/99.
Три повтора на конфигурацию, два независимых прохода.

## Матрица

Разделять оси нельзя смешивать: сцена умеет два режима, и в каждом варьируется **одна**
переменная.

| Режим | Что варьируется | Что фиксировано |
|---|---|---|
| `счёт` | 0…10 поверхностей | кнопка 68 dp, продовый `LiquidGlassButton` |
| `площадь` | кнопка · мини-плеер · таб-бар · панель | число поверхностей |

Материал: `без преломления` · `Material v1`. Опорная точка изолирует смещение выборки —
RenderEffect накладывается в обоих, но в первом вырожден. Это **не** конвейер до Phase 3
(там линза не включалась вовсе, `../material-lab.md` E-01).

**Прогрев обязателен:** 6 с после смены конфигурации, затем `gfxinfo … reset` — иначе в
окно попадают компиляция шейдера, первая инициализация бэкдропа и раскладка.
Три повтора на конфигурацию. Приложение между конфигурациями не перезапускать.

## Что ещё не мерялось

- Слабое железо — проверено одно устройство среднего сегмента; порог наверняка ниже шести.
- 60 и 90 Гц — на HyperOS частота через adb не переключается, менять вручную в настройках.
- Устойчивая нагрузка дольше ~8 минут и расход батареи.
- Механизм насыщения на 7-й поверхности.

## Как читать метрики (обязательно)

Разбор — `2026-08-29-scaling-validation.md` §1. Кратко:

- **`Total frames rendered` на HyperOS/Android 16 удвоен.** Делить на 2. Проверка:
  `Number High input latency` равен ровно 2× счётчика кадров.
- **`GPU p50` — не время кадра**, а время завершения работы GPU по фенсу. Конвейер держит
  ~3 кадра в полёте, поэтому GPU-время свободно превышает бюджет без пропуска vsync.
- **`Janky frames` судит по дедлайну приложения**, а он равен `WorkloadTarget = 10 мс`,
  а не 8.33 мс; у части кадров дедлайн снят вовсе. Просадка 120 → 72 кадра/с идёт при
  `0.00 % janky`. **Судить по частоте кадров, а не по jank.**
- **`DisplayPresentTime` в timeline равен нулю** — фактическое время предъявления через
  `gfxinfo` недоступно.

Частота считается как `Total frames rendered / 2 / elapsed`, где `elapsed` берётся из
самого дампа: `(Uptime × 10⁶ − Stats since) / 10⁹`.

## Валидация сцены

`dumpsys gfxinfo` печатает `Layer Info` — по одному `GlLayer` на стеклянную поверхность.
`numLayers` обязан совпадать с запрошенным числом стёкол, размер слоя — с геометрией.
Это объективная проверка, что сцена действительно переключилась; скриншот — вторая.
