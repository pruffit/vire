# Спека: индексы под горячие запросы + общий оптимистичный toggle

Дата: 10.07.2026. Источник: `docs/roadmap/TODO.md` → «Аудит перед стабильной версией».
Две независимые пачки, объединены одним циклом, но разными коммитами.

---

## Пачка 1 — индексы БД под горячие запросы

### Проблема (наблюдаемая, не гипотетическая)

1. `play_events` имеет три одиночных индекса: `track_id`, `started_at`, `user_id`
   (`packages/db/src/schema/analytics.ts:17-21`). Все горячие места читают его
   **связкой** «равенство по треку + диапазон по времени»:
   - `queries/popularity.ts:10-12` — коррелированный `count(*) … where pc.track_id = tracks.id
     and pc.started_at >= now() - interval 'N days'` (скоринг популярности);
   - `queries/popularity.ts:238-240` — то же за 30 дней внутри волны;
   - `queries/wave.ts` — `qualityScore` и `fatigue` того же вида;
   - `queries/admin.ts:634` — `playsTotal` (только `track_id`).

   Планировщик может взять только один одиночный индекс, а второе условие
   отфильтровать пост-фактум (либо строить BitmapAnd из двух). Композит
   `(track_id, started_at)` обслуживает обе части одним обращением: равенство по
   ведущей колонке, диапазон по второй.

2. Поиск (`queries/search.ts:76,96,115`) — `ILIKE '%q%'` по
   `artist_profiles.name`, `releases.title`, `tracks.title`. Ведущий `%` исключает
   btree ⇒ seq scan на каждый запрос пользователя.

### Решение

- **Заменить** `play_events_track_id_idx` на композит
  `play_events_track_started_idx (track_id, started_at)`.
  Одиночный индекс по `track_id` после этого избыточен: композит с той же ведущей
  колонкой обслуживает любой предикат `track_id = X`. Замена, а не добавление —
  чтобы не растить стоимость записи в самой горячей на вставку таблице.
- **Оставить** `play_events_started_at_idx` (нужен для агрегатов без трека:
  `admin.ts:88-92`, `admin.ts:149` — окна 24ч/7д/30д по всей таблице) и
  `play_events_user_id_idx`.
- **Добавить** расширение `pg_trgm` и три GIN-индекса `gin_trgm_ops` на
  `artist_profiles.name`, `releases.title`, `tracks.title`.

### Явные не-цели

- `wave.ts` не меняется. Ни строки. Цель пачки — узнать, нужен ли вообще рефактор
  скоринга, а не сделать его.
- `admin.ts` `ilike` по `slug`/`email`/`name` пользователей — вне охвата (админка,
  холодный путь, 50 строк).
- `CREATE INDEX CONCURRENTLY` не используем: миграции гоняются в транзакции, а
  таблицы на проде малы (платформа молодая). Блокировка на секунды приемлема.

### Риски и как снимаем

| Риск | Снятие |
|---|---|
| `CREATE EXTENSION` требует прав | Миграции на проде гоняются от `POSTGRES_USER` (владелец БД, суперюзер в compose) — `deploy.yml:148`. `pg_trgm` входит в `postgres:16-alpine`. Проверяем локально. |
| drizzle-kit не умеет `.using('gin', …)` в снапшоте ⇒ вечный дифф | После генерации миграции гоняем `db:generate` ещё раз и убеждаемся, что новых изменений нет. Если умеет плохо — индексы уходят в ручной SQL, а из схемы убираются. |
| Триграммный индекс не применяется к коротким запросам (<3 символов) | Принимаем: это свойство pg_trgm. Поиск с лимитом 5, короткие запросы дёшевы. Документируем. |
| Замена индекса ухудшит какой-то незамеченный запрос | Полнотекстовый grep по `play_events` уже сделан (6 мест), все совместимы с ведущей `track_id`. |

### Критерии приёмки

- [ ] Миграция применяется на чистой БД и на текущей локальной без ошибок.
- [ ] Повторный `db:generate` не порождает диффа (снапшот консистентен схеме).
- [ ] `EXPLAIN` на синтетике: коррелированный подзапрос популярности использует
      `play_events_track_started_idx`; `ILIKE '%…%'` использует GIN-индекс.
- [ ] Замер до/после на синтетических данных (≥200k `play_events`): зафиксированы
      тайминги `getWaveTracks` и `search`.
- [ ] По результату замера — вердикт в `TODO.md`: нужен ли рефактор скоринга волны.
- [ ] Гейты зелёные.

## Пачка 2 — `useOptimisticToggle` + оживление `@vire/api-client`

### Проблема

Паттерн «оптимистично флипнуть → сходить в сеть → откатить и показать тост»
скопирован в пять мест, и копии уже разъехались:

| Файл | pending | Ошибка сети | Тост |
|---|---|---|---|
| `app/(listener)/artists/[slug]/follow-button.tsx` | `useTransition` | `.catch(() => null)` + `!res?.ok` | есть |
| `.../tracks/[trackId]/like-button.tsx` | `useTransition` | `.catch(() => null)` + `!res?.ok` | есть |
| `components/presave-button.tsx` | `useState(busy)` | `try/catch` + `throw` на `!res.ok` | есть |
| `components/upcoming-presave-button.tsx` | `useState(busy)` | `try/catch` | есть |
| `components/use-playlist-like.ts` | `useState(pending)` | `try/catch` | **нет** |

Последняя строка — живой баг: лайк плейлиста при 401/429/5xx молча откатывается,
пользователь видит, как его клик «не сработал», без объяснения.

Параллельно `packages/api-client` пуст (`.gitkeep`), хотя CLAUDE.md описывает его
как типизированный fetch-клиент. В `apps/web` — 78 сырых `fetch(` в 52 файлах.

### Решение

Три слоя, каждый со своей ответственностью:

1. **`packages/api-contracts`** — zod-схемы ответов toggle-эндпоинтов
   (`{following}`, `{liked}`, `{presaved, guest?}`). Один источник правды о форме
   ответа для хендлера и клиента.

2. **`packages/api-client`** — типизированный `request()`:
   - возвращает `ApiResult<T> = {ok:true; data:T} | {ok:false; error:ApiError}`
     (ошибки как значения — правило CLAUDE.md), никаких throw наружу;
   - сетевой сбой и HTTP-ошибка сводятся к одному представлению;
   - тело ошибки `{error: string}` с сервера попадает в `error.message`
     (нужно гостевому пресейву, который сегодня показывает серверный текст);
   - ответ валидируется схемой из `api-contracts`; несоответствие = ошибка, не тихий `any`.
   - **Не зависит от `@vire/core`**: пакет едет в браузерный бандл, тащить туда
     доменные сервисы незачем. `ApiResult` — собственный тип той же формы.

3. **`apps/web/lib/use-optimistic-toggle.ts`** — чистая машина состояния:
   ```ts
   useOptimisticToggle({
     initial: boolean,
     initialCount?: number,
     request: (next: boolean) => Promise<ApiResult<unknown>>,
     errorMessage?: string,
   }) => { on, count, pending, toggle }
   ```
   Хук не знает про URL — сеть инжектится колбэком (правило DI из CLAUDE.md;
   заодно тестируется без мока `fetch`).

### Сознательные изменения поведения (не рефактор-инвариант)

1. **`use-playlist-like` получает тост об ошибке.** Было — молчание. Это и есть
   тот дефект, ради которого унификация затевалась.
2. **`follow-button` и `like-button` уходят с `useTransition` на `useState`.**
   Обновления тривиальные, приоритезация не нужна; `disabled={pending}` сохраняется
   один-в-один.
3. Остальное — инвариант: тексты тостов, разметка, стили, `aria-pressed` не трогаем.

### Явные не-цели

- **Не мигрируем** остальные 70+ `fetch` на `api-client`. Пакет получает узкий и
  честный охват (toggle-эндпоинты) и служит плацдармом. Массовая миграция —
  отдельная задача, иначе диф не отревьюить.
- Гостевая форма email в `presave-button` — **не toggle**, остаётся своей логикой;
  через `api-client` идёт только ради серверного текста ошибки.
- UI не меняется ⇒ `audit:design` прогоняем, но изменений там не ждём.

### Критерии приёмки

- [ ] Пять файлов не содержат ни одного `fetch(` и ни одной ручной ветки отката.
- [ ] Поведение при HTTP-ошибке и при сетевом сбое идентично во всех пяти.
- [ ] Двойной клик по кнопке шлёт один запрос (guard по `pending`).
- [ ] Тесты: `packages/api-client` (ok / HTTP-ошибка с телом / сетевой сбой /
      ответ не по схеме) и хук через `@testing-library/react` (оптимизм, откат,
      тост, guard).
- [ ] `docs/features/` описывает `api-client`.
- [ ] Гейты зелёные, число тестов выросло.
