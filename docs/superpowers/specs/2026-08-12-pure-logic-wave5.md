# Спека: перенос чистой логики в core (волна 5)

**Основание:** `docs/migration-plan.md` §Волна 5. Цель волны — снять чистую логику с
`apps/web` и положить в `@vire/core`, чтобы будущий нативный клиент переиспользовал
решения, а не переписывал их. Риск волны заявлен минимальным; всё, что этому
не соответствует, из волны выводится (см. §5.5).

## Что выяснила разведка и как это меняет скоуп

| # | План | Факт | Решение |
|---|---|---|---|
| 5.1 | `lib/player/queue.ts` → core | 122 строки, чисто; единственная зависимость — тип `PlayerTrack` из web-стора | Переносим, **обобщив по `{ id: string }`** — тип `PlayerTrack` остаётся в web |
| 5.2 | `lib/format.ts` → core | 44 строки, ни одного импорта, 26 потребителей | Переносим в `platform/util`, на старом пути — реэкспорт |
| 5.3 | «три параллельные реализации насыщения» | Кривые **разные**: линейный клэмп K=3, лог-отношение K=100, SQL-клэмп K=5 | Сводим не в одну функцию, а в два именованных примитива; поведение не меняем |
| 5.4 | `wave-session.ts` за порт | Порт `IWaveSessionStore` и DI **уже есть**, web — легальная реализация | Волна почти закрыта: переносим только константы политики и ключи |
| 5.5 | расщепление `audio-engine.ts` (663 строки) | 23 потребителя, 12 модульных `let`, I/O переплетён с решениями | **Сужаем:** вынимаем чистые решения, порт `IAudioEngine` откладываем |

## 5.1 Очередь плеера

`sliceWindowAroundIndex`, `capLiveQueue`, `nextQueueIndex`, `fisherYates`, `shuffleOn`,
`shuffleOff`, `insertIntoQueue`, `dedupeQueue` уезжают в
`packages/core/src/music/playback/services/queue.ts`.

Функциям нужен от трека только `id`. Поэтому сигнатуры обобщаются:
`capLiveQueue<T extends { id: string }>(...)` и т.д. Это **лучше** переноса `PlayerTrack`
в core: тип несёт вебовые поля (`coverUrl`, `hlsUrl`) и в ядре ему не место. `Repeat`
переезжает как доменный тип playback.

`Math.random` остаётся дефолтом параметра `rand` — это уже инъектируемый эффект,
как `Clock` в `platform/ports/effects.ts`.

**Совместимость:** `apps/web/lib/player/queue.ts` остаётся файлом-реэкспортом, оба
потребителя (`store/player.ts`, `audio-engine.ts`) не правятся. Тесты уезжают вместе
с кодом.

## 5.2 Форматтеры

`apps/web/lib/format.ts` → `packages/core/src/platform/util/format.ts` целиком, без
изменения поведения. Локале-зависимости нет: `formatListenTime` принимает подписи
единиц параметром, суффикс `k` в `formatCount` уже нелокализован и таким остаётся —
это отдельный вопрос i18n, не этой волны.

**Совместимость:** `apps/web/lib/format.ts` — реэкспорт из `@vire/core`; 26 файлов-
потребителей не трогаем. Тест переезжает в core.

## 5.3 Насыщение

Формулировка плана («три параллельные реализации») подтвердилась лишь частично:

- `friendSignal` (discovery-scoring): `min(1, n/3)` — линейный клэмп;
- `popularityScore` (feed-ranking): `log1p(n)/log1p(n+100)` — асимптотика, **другое семейство**;
- `momentScore` (`packages/db/src/queries/wave.ts`): `LEAST(1.0, n/5.0) * 0.2` — тот же
  линейный клэмп, но на SQL, с весом внутри выражения.

Свести всё в одну функцию нельзя — это изменит ранжирование ленты. Делаем то, что
даёт выигрыш без смены поведения:

1. `packages/core/src/platform/util/scoring.ts` — `saturateLinear(n, k)` и
   `saturateLog(n, k)`, две именованные кривые с тестами. Рядом они документируют
   выбор: почему у ленты асимптотика, а у остальных — потолок.
2. `friendSignal` и `popularityScore` переписываются через них. Выход обязан
   совпасть до последнего знака — это проверяется существующими тестами.
3. SQL-выражение `momentScore` остаётся SQL, но константы `5` и `0.2` уезжают в
   именованные экспорты `wave-scoring.ts` и подставляются в шаблон (число в
   `sql`-шаблон интерполировать безопасно — запрет касается `Date` и колонок).

## 5.4 Сессия волны

Порт `IWaveSessionStore` (`music/playback/repositories/wave.ts`), сервис, который его
потребляет, и DI в роуте `/v1/wave` уже существуют — целевая форма из
`docs/foundation/architecture.md` достигнута. Redis-команды по определению живут в
адаптере, их место в `apps/web`.

Остаётся один шов: политика (`TTL_SEC = 6ч`, `MAX_SERVED_IDS = 300`) и имена ключей
Redis лежат в web, хотя это часть контракта сессии, а не транспорта. Переносим их
в core рядом с портом — ровно по прецеденту `platform/util/presence-keys.ts`.
Больше в 5.4 не трогаем ничего.

## 5.5 Движок аудио — сужение скоупа

План предполагал расщепление на «логику в core + I/O за `IAudioEngine`». Против
полного расщепления сейчас три факта: 663 строки при 12 модульных мутабельных
переменных и 23 потребителях; вся реально переиспользуемая математика очереди уже
вынесена (`queue.ts`, `wave-buffer.ts`); второго клиента, который бы доказал форму
порта, ещё нет. Проектировать `IAudioEngine` под воображаемого потребителя — ровно то,
что запрещает §3 задания программы («abstract after evidence»), а цена ошибки — плеер,
центральная функция продукта.

Поэтому в этой волне вынимаем только то, что доказано чистое, в
`packages/core/src/music/playback/services/engine-policy.ts`:

| Что | Сейчас | Правило |
|---|---|---|
| Порог ошибок волны | `handleWaveLoadError`, счётчик 3 | `shouldGiveUpOnWave(consecutiveErrors)` |
| Порог отсутствующих локальных файлов | `attachLocalTrack`, счётчик 3 | `shouldStopLocalRetries(misses)` |
| Триггер префетча манифеста | `duration - currentTime >= 15` | `shouldPrefetchNext(currentTime, duration)` |
| Троттл тика | `now - lastTickAt >= 5000` | `shouldRunTick(now, lastTickAt)` |
| Починка индекса после восстановления | `clampRestoredQueueIndex` | переносится как есть |
| Хвост сыгранного для запроса волны | срез последних 100 | `playedIdsWindow(ids)` |

Мутабельные счётчики остаются в движке — в core уезжают только предикаты. Файл
после этого читается как «драйвер I/O, зовущий политику», что и есть предусловие
будущего `IAudioEngine`.

**Порт `IAudioEngine` — отдельная задача, по условию:** появляется нативный клиент
или второй драйвер (например, полностью офлайновый). До этого — не делаем.

## Границы и проверка

- Ни одного изменения поведения ни в одном пункте. Все переносы — чистые функции,
  тесты переезжают вместе с ними и остаются зелёными.
- `check:layers` обязан остаться зелёным: `platform/util/**` не может ссылаться
  на `music/**`; `scoring.ts` и `format.ts` этого и не делают.
- Барьер отката для каждого пункта — реэкспорт со старого пути: вызывающая
  сторона не знает о переезде.
- Гейты после каждого среза: typecheck (web/core), lint, `check:routes`,
  `check:i18n`, `check:contracts`, `check:layers`, тесты. Сборка — в конце волны.
