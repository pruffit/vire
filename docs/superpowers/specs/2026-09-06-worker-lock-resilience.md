# Устойчивость воркера к потере локов BullMQ + читаемость алертов

Реакция на инцидент 06.09.2026: четыре очереди (`scheduled-publish`, `jam-reaper`,
`storage-cleanup`, `editorial`) разом отдали `could not renew lock` / `Missing lock …
moveToFinished`. Джобы были запланированы на 03:05–04:00 MSK, а упали в 05:04–05:09 —
между этими точками в алерт-канал не пришло ничего.

## Что чиним

Не корневую причину (окно недоступности Redis / стопор хоста — подтверждается только
прод-логами), а три усилителя, из-за которых она прошла незаметно и ударила шире, чем должна.

### 1. Разный `lockDuration` в одном процессе

Все двенадцать воркеров живут в одном процессе и делят event loop. Три из них
(`transcode`, `analyze`, `analyze-genre`) знают, что блокируют его на минуты (ffmpeg,
синхронный ONNX-инференс), и подняли себе лок до 10 минут. Остальные девять остались на
дефолтных 30с — и лок теряют именно они, на чужой работе. Упавшие 06.09 очереди — ровно
из этой девятки.

**Решение:** общий `lockDuration` 5 минут на все воркеры процесса (`baseWorkerOptions`).
Тяжёлая тройка сохраняет свой явный оверрайд в 10 минут.

Цена: джоба мёртвого процесса переоткрывается не через 30с, а через 5 минут
(`stalledInterval` остаётся дефолтным). Для минутного крона `scheduled-publish` это
задержка публикации на единицы минут — приемлемо против регулярной потери локов.

### 2. Обрыв Redis не виден в момент обрыва

`maxRetriesPerRequest: null` (обязателен для блокирующих команд bullmq) заставляет
команды ждать вечно вместо ошибки. `connection` — plain-объект, bullmq поднимает ioredis
сам, и повесить слушатель не на что: обрыв всплывает часами позже, хвостом из потерянных локов.

**Решение:** общий инстанс IORedis со слушателями `error`/`close`/`reconnecting`/`ready`.
Безопасно: bullmq переиспользует переданный инстанс только под обычные команды, а
блокирующее соединение каждый воркер дублирует сам (`utils/create-backend.js`,
`createBlockingConnection`). Побочно: 12 обычных соединений схлопываются в одно.

Алерт-политика — одно сообщение на инцидент, не на ошибку: 🟠 на первом `close`,
🟢 на `ready` с длительностью простоя. Иначе двухчасовой обрыв дал бы ~120 сообщений
(троттл-гейт держит только 60с на одинаковый текст).

Инстанс пинится на `protocol: 2`, как весь остальной Redis-код проекта
(`apps/web/lib/redis.ts`, `realtime.ts`): ioredis 6 включил RESP3 по умолчанию, и
соединение bullmq было единственным местом, которое после мажора 03.09 уехало на RESP3.

На тот же инстанс переезжают три собственных клиента воркера — `jam-cleanup`,
`notify-debounce`, `user-presence`: у всех только обычные команды и такой же глухой
`on('error', () => {})`. Итого пять соединений процесса схлопываются в одно, и ошибки
всех троих теперь видны.

### 3. Алерт без текста ошибки

`🔴 [web] POST /ru:` — шаблон `${where}: ${message}` при пустом `error.message`.
Алерт без типа ошибки нечитаем.

**Решение:** чистая функция `describeError` с фолбэком на `name` + `digest`, для не-Error —
на `String`/`Object.prototype.toString`.

## Границы

Вне скоупа: корневая причина инцидента (нужны прод-логи), `apps/web/lib/redis.ts`
(та же слепая зона на стороне web — отдельной задачей), тюнинг `stalledInterval`.
