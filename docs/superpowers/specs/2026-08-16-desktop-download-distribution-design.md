# Скачивание десктоп-приложения — страница, баннер, дистрибуция — дизайн

**Статус:** реализуется · **Основание:** запрос пользователя (16.08.2026), продолжение
`docs/features/desktop-app.md` (срезы 0-2 desktop-клиента, уже в `main`)

## Что это

Публичная часть истории десктоп-клиента: страница `/download`, баннер с детекцией
устройства, и пайплайн, который реально публикует собранный `.msi`/`.exe` в двух местах
после каждого релиза — без этого кнопка «Скачать» ведёт в никуда.

## Дистрибуция (решено с пользователем)

Репозиторий **приватный** (подтверждено: анонимный запрос к GitHub API вернул 404) —
прямая ссылка на GitHub Release не откроется анонимному посетителю сайта. Решение:
публиковать в **оба** места одним шагом CI:

1. **GitHub Release** (тег `vX.Y.Z`, тот же, что запускает `deploy.yml`) — версионированный
   архив для команды/истории. Доступ только у тех, кто может видеть репозиторий.
2. **MinIO-бакет `vire-stream`** (`S3_BUCKET_STREAM`, уже публично отдаётся анонимно —
   `mc anonymous set download` в `docker-compose.yml`, тот же bucket, что обложки и HLS)
   под **стабильным** ключом `downloads/desktop/windows/VireMusic-Setup-x64.exe` (без
   версии в пути — перезаписывается каждым релизом). Публичный URL —
   `${S3_PUBLIC_ENDPOINT}/vire-stream/downloads/desktop/windows/VireMusic-Setup-x64.exe`,
   то есть `https://cdn.viremusic.ru/vire-stream/downloads/desktop/windows/...` в проде.
   Это то, на что реально ссылается кнопка «Скачать» на сайте — стабильный URL, сайту не
   нужно знать номер версии или дёргать GitHub API.

**Секреты для загрузки в MinIO — НЕ пытаться получить/угадать самому.** Пользователю
нужно завести в GitHub → Settings → Secrets новые repo secrets самому (не присылать
значения в чат — прошлый инцидент этой сессии с паролем от VPS в открытом виде): имена
секретов ниже, значения — из `.env` на проде (те же переменные, что использует
рантайм-сервис). Пока секретов нет — шаг загрузки в CI будет падать, это ожидаемо и не
блокирует остальной пайплайн, если вынести шаг в `continue-on-error` явно ИЛИ (лучше)
пользователь заводит секреты перед первым реальным тегом. Написать в отчёте прямым
текстом, какие секреты и куда положить.

## CI: новый job в `.github/workflows/deploy.yml`

`build-desktop`: `needs: gates`, `runs-on: windows-latest`, тот же триггер (`vX.Y.Z` тег),
что и `build-and-push`/`deploy` — параллельно им, десктоп не зависит от образов веба.

Шаги:
1. Checkout, Rust toolchain (`dtolnay/rust-toolchain@stable` — стандартное GitHub Action
   для Rust, кэширует лучше, чем ручной `rustup`), pnpm/node (только для `apps/desktop`
   — веб-сборка тут НЕ нужна, `apps/desktop` грузит внешний URL, не бандлит фронт).
2. Сборка: официальный `tauri-apps/tauri-action` (умеет собрать + сразу приложить артефакт
   к GitHub Release одним шагом) **или** руками `cargo install tauri-cli && cargo tauri
   build` + `softprops/action-gh-release` — выбрать по факту, что проще подключить с рабочим
   результатом, не гадать заранее. `tauri-action` предпочтительнее, если заводится без
   сюрпризов (меньше кода, официально поддерживается).
3. Публикация в GitHub Release для тега (см. выше).
4. Загрузка в MinIO: `aws s3 cp <installer> s3://vire-stream/downloads/desktop/windows/VireMusic-Setup-x64.exe --endpoint-url ${{ secrets.S3_PUBLIC_ENDPOINT }}`
   (AWS CLI работает с S3-совместимым MinIO через `--endpoint-url`, доп. установка не
   нужна — стоит на `windows-latest`/`ubuntu-latest` раннерах из коробки; если раннер для
   этого шага windows — можно вынести именно этот шаг на отдельный `ubuntu-latest` job,
   если так проще). Новые secrets, которые понадобятся (имена финальные, не менять
   произвольно): `S3_UPLOAD_ACCESS_KEY`, `S3_UPLOAD_SECRET_KEY`, `S3_UPLOAD_ENDPOINT`
   (это MinIO endpoint, доступный из GitHub Actions — вероятно тот же `cdn.viremusic.ru`,
   раз Caddy проксирует туда весь порт 9000, но подтвердить в отчёте, что это осознанное
   предположение, не проверенный факт — сама загрузка с реальными секретами не
   тестируется в этом заходе, секретов ещё нет).

**Не в этом заходе**: Mac/Linux-сборка (нет раннера с сборкой макОС, требующей Apple
подписи — отдельная большая задача), автообновление приложения, публикация в Microsoft
Store (нужен аккаунт разработчика — решение пользователя, не инженерное).

## Веб: страница `/download` + баннер

- **`apps/web/lib/platform-detect.ts`** — чистая функция `detectPlatform(userAgent:
  string): 'windows' | 'macos' | 'linux' | 'ios' | 'android' | 'unknown'` по
  `navigator.userAgent`/переданной строке (чистая — тестируема без DOM). Простые эвристики
  (`/windows/i`, `/mac os|macintosh/i` минус iPad (см. ниже), `/android/i`, `/iphone|ipad|ipod/i`,
  `/linux/i` после проверки android — Android UA тоже содержит "Linux"). Задокументировать
  порядок проверок как неочевидное «почему» (одна строка комментария, не больше).
- **Страница `app/[locale]/(listener)/download/page.tsx`** (по образцу `about/page.tsx` —
  `generateMetadata` + `pageMetadata`, серверный компонент). Секции по платформам:
  - Windows: реальная кнопка «Скачать для Windows», href — стабильный CDN URL, собранный
    сервером из `process.env.S3_PUBLIC_ENDPOINT` (тот же паттерн, что
    `streamStorage`/`publicBaseUrl` в `packages/storage`, см. `apps/web/lib/s3.ts`), не
    просить клиента знать env var.
  - macOS/Linux: карточка с пометкой «скоро» (`badge`/приглушённый стиль, без рабочей
    кнопки) — честно, не выдавать отсутствующее за готовое.
  - iOS/Android: карточка «скоро» — мобильного приложения нет вообще, это не первый
    приоритет по договорённости этой сессии (мобильный клиент = отдельная будущая задача
    из `multiplatform.md` §12 п.8).
  - PWA-путь остаётся видимым как актуальная альтернатива уже сегодня (уже в проде) —
    короткая заметка/ссылка «Установить как веб-приложение» рядом, не теряться среди
    «скоро»-карточек нативных клиентов.
- **Баннер**: клиентский компонент, вызывает `detectPlatform(navigator.userAgent)` на
  маунте, показывает короткое сообщение («Скачайте VireMusic для Windows») + кнопку на
  `/download` (не начинает скачивание сразу — ведёт на страницу с подробностями, там же
  правильная платформа может быть предвыбрана/проскроллена якорем `#windows` и т.п., на
  усмотрение реализации). Дизайн — на усмотрение реализации, принципы Impeccable по
  умолчанию (проект правило). Не показывать баннер повторно после закрытия — запомнить в
  `localStorage` (простой ключ, TTL не нужен, разовое дозаклытие достаточно — как другие
  разовые баннеры в проекте, если такой паттерн уже есть — поискать перед тем как писать
  свой). Где размещать (`Nav`/отдельно на главной/везде через layout) — решить по месту,
  не создавать новый на каждой странице отдельно (один общий монтаж).
- **i18n**: строки в `packages/i18n/messages/{ru,en}/download.json` (или расширение
  существующего namespace, если по смыслу подходит) — заполнить **обе** локали
  одновременно (правило проекта, `check:i18n` в гейтах это проверит).
- **`docs/features/desktop-app.md`**: дополнить секцией про страницу скачивания и
  публикацию — не новый файл, тот же (это часть той же фичи «десктоп-клиент»).

## Проверка

- `pnpm --filter @vire/web typecheck && lint && check:i18n && test && audit:design`
- Открыть `/download` локально (`pnpm --filter @vire/web dev`), убедиться, что все секции
  рендерятся, кнопка Windows ведёт на реальный (пусть пока не существующий физически до
  первого тега) стабильный URL нужного вида.
- YAML нового job — валиден (`yamllint`/просто отсутствие ошибок парсинга; реальный запуск
  проверяется только настоящим тегом, не в этом заходе — секретов ещё нет).
