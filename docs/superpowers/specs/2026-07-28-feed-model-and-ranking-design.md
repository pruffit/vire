# Лента: модель состава и ранжирование (stage-2 §4.2–4.3) — дизайн

Дата: 28.07.2026. Сейчас на главной секция «Новое у подписок» — плоский `getFeed`:
релизы подписок, сортировка по дате выхода, `limit 50`, показ первых 12. Ни вкуса, ни
разнообразия, ни анонсов; у слушателя без подписок секции нет вообще.

Отдельной страницы `/feed` нет и не будет (§4.1 закрыт: страница удалена, контент —
секция главной). Здесь переделывается **состав и порядок** этой секции.

## Продуктовые развилки (решены автономно — работа по команде 28.07)

| Развилка | Решение | Почему |
|---|---|---|
| Что попадает в ленту | Релизы (подписки + вкус), анонсы артистов подписок, скорые релизы подписок | Это весь материал, который уже есть в БД и имеет автора и дату |
| Активность друзей | Остаётся **отдельной** секцией, в ленту не смешиваем | Разный масштаб события: «друг лайкнул трек» ≠ «вышел релиз» |
| Персональные треки («Для тебя») | Остаются отдельным блоком | Это треки, а не события; смешение ломает единицу карточки |
| Слушатель без подписок | Лента строится по вкусу, при нехватке добивается свежим | Пустая секция — та самая болезнь, из-за которой убили `/feed` |
| Прозрачность | У каждого элемента подпись-причина («вы подписаны», «похоже на ваши вкусы») | Иначе непонятно, почему это здесь, и лента читается как реклама |
| Бесконечная лента | Нет: 12 элементов + «Показать ещё» до 24 | Главная — хаб, а не бесконечный скролл |

## Единица ленты

```ts
type FeedItemKind = 'RELEASE' | 'POST' | 'UPCOMING';
type FeedReason = 'follow' | 'taste' | 'fresh';

interface FeedItem {
  kind: FeedItemKind;
  id: string;              // релиз или пост
  artistSlug: string; artistName: string; artistAvatarUrl: string | null;
  occurredAt: Date;        // выход релиза / публикация поста / дата анонса
  reason: FeedReason;
  score: number;
  // поля под карточку конкретного вида
}
```

## Ранжирование — чистые функции в `packages/core/src/services/feed-ranking.ts`

Образец — `wave-scoring.ts`: веса-константы + чистые функции + тесты, никакого IO.

```
score = recency * W_RECENCY
      + affinity * W_AFFINITY
      + popularity * W_POPULARITY
      + kindBonus
```

- **recency** = `exp(-ageDays / halfLife)`; halfLife: релиз 7 дней, анонс 3 дня,
  скорый релиз считается от даты выхода вперёд (чем ближе — тем выше).
- **affinity** — **максимум**, не сумма: подписка `1.0`, артист из профиля вкуса `0.7`,
  совпадение по жанру/настроению вкуса `0.5`, иначе `0.25` (добивка свежим).
- **popularity** = `log1p(plays30d) / log1p(plays30d + K)`, вес маленький (0.15) и
  насыщается — это «не мёртвое», а не «самое популярное». Именно здесь хоронят малых
  артистов, поэтому сигнал сознательно слабый и сжатый логарифмом.
- **kindBonus** — анонс `+0.05`, скорый релиз `+0.1` (событие впереди ценнее прошедшего).

Веса: `W_RECENCY 0.45`, `W_AFFINITY 0.40`, `W_POPULARITY 0.15`. Сумма 1.0 — score
сравним между видами элементов.

## Состав (композиция) — тоже чистая функция

`composeFeed(candidates, { limit, maxPerArtist, smallArtistShare })`:

1. Сортировка по score.
2. **Кап на артиста** — не более 2 элементов одного артиста в выдаче.
3. **Квота малым** — минимум 30% слотов отдаётся артистам, у которых `plays30d`
   ниже медианы кандидатов, если такие есть. Это защита из §4.3 («без алгоритма,
   хоронящего малых артистов») в явном виде, а не на словах.
4. Дедуп по `kind+id`.

Ни один шаг не ходит в БД: на вход подаётся готовый массив кандидатов.

## Данные

Один запрос-сборщик `getFeedCandidates(userId, { limit })` в `packages/db/src/queries/feed.ts`,
внутри — независимые под-выборки, объединяемые в JS:

- релизы подписок (существующий предикат «вышел в эфир»);
- релизы артистов из `taste.topArtistIds` и релизы с пересечением по жанрам/настроениям вкуса;
- анонсы (`artist_posts`) артистов подписок за 30 дней;
- скорые релизы подписок (`SCHEDULED` с будущей датой);
- `plays30d` на релиз — одним агрегатом на все id, не подзапросом на строку.

Кандидатов берём с запасом (до 120), ранжирование и композиция — в core.
Профиль вкуса читается существующим `getTasteProfile` (с TTL-кэшем).

Холодный старт: если после композиции < 6 элементов — добираем свежими релизами
(`reason: 'fresh'`), чтобы секция не была пустой и не исчезала.

## UI

Секция «Ваша лента» на месте «Новое у подписок» (`home-sections.tsx`):

- вертикальный список карточек на всю ширину секции (не горизонтальная лента —
  у элементов разный вид и нужна подпись-причина);
- три вида карточки: релиз (обложка + название + артист), анонс (аватар + текст,
  клик — на страницу артиста), скорый релиз (обложка + отсчёт + пресейв, переиспользуя
  существующие `ReleaseQuickLook`/`CountdownBadge`/`PresaveButton`);
- подпись-причина мелким текстом у каждого элемента;
- 12 элементов + «Показать ещё» до 24 (клиентский разворот уже загруженного массива,
  без второго запроса).

Мобилка — одна колонка, тач-таргеты 44px, никаких горизонтальных скроллов внутри карточки.

## Что не делаем

Бесконечная лента, ML-рекомендации, смешение активности друзей и персональных треков,
серверная пагинация, персональные пуши по ленте, скрытие/«не интересно» (нет UI под
обратную связь — отдельная фича).

## Риски

- **Малый каталог** — на текущем объёме лента может состоять из 5–10 элементов; квота
  малым и добивка свежим не дают ей выглядеть пустой.
- **Стоимость запроса** — 4 под-выборки + агрегат прослушиваний; всё под `.catch(() => [])`
  и внутри `Suspense`, как остальные секции главной: сбой ленты не роняет главную.
- **Смещение к подпискам** — при affinity 1.0 у подписок лента может выродиться в
  «только подписки»; кап на артиста и квота малым это ограничивают, а вес свежести
  почти равен весу близости.
