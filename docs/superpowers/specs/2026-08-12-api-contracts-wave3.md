# Спека: контракты `/api/v1` (волна 3)

**Основание:** `docs/migration-plan.md` §волна 3 · конвенции `docs/api-contracts.md`.

## Проблема

119 роутов под `/api/v1`. Из них 14 импортируют `@vire/api-contracts` (волна 2), 47 держат
локальную zod-схему, ~40 валидируют вход руками (`typeof`/`Set.has`/regex) — весь
`dashboard/**` и часть mutation-роутов. Единого места, откуда клиент берёт контракт, нет,
и ничто не мешает завтра добавить роут без схемы.

Расхождение уже состоялось: `playlists/[id]/collaborators` отдаёт `joinedAt` сырым `Date`,
а `playlists/[id]/page` тот же тип мапит в ISO. На проводе разницы нет (`Date.toJSON`),
но TS-тип ответа расходится с контрактом — то есть клиент типизируется по тому, чего нет.

## Решение

Три среза по ресурсам + барьер. Каждый срез самостоятелен и откатывается независимо.

| Срез | Ресурсы | Что даёт |
|---|---|---|
| 1 | follow/like×2/presave, wave, `GET /v1/artists/{slug}`, `GET /v1/releases/{id}` | Подключает уже написанные схемы (`toggle.ts`, `wave.ts`); заводит `common.ts`; закрывает два `raw+Date` роута через существующие `catalog.ts`-схемы |
| 2 | `playlists/**` (кроме SSE) | Чинит `joinedAt`; внутренние схемы `playlist-page.ts` становятся переиспользуемыми |
| 3 | `chat/**`, `notifications/**` | Схемы с нуля: `ChatMessage`, `ChatConversation`, `Notification` |
| 4 | барьер + доки | `check:contracts` с allowlist непереведённых групп |

**Вне волны 3** (allowlist барьера, отдельные подпроекты): `dashboard/**` (18 файлов —
multipart + ручная валидация, сначала нужны схемы входа), `jam/**` (18, union + SSE),
`admin/**`, `keys/**` (E2EE-протокол), `webhooks/**`, SSE-стримы, `health`.

## Принятые решения

1. **Форма ответа не меняется.** Конвенция `{ data: T }` из `docs/api-contracts.md` §3.1
   не соответствует факту: роуты отдают ресурсный объект (`{ items, hasMore }`,
   `{ liked }`), ошибку — плоскую `{ error: string }` (102 места — `'Unauthorized'`).
   Обёртка не даёт ничего типизированному клиенту, а миграция 119 роутов + всех фетчеров —
   ломающее изменение без выигрыша. Контракт описывает факт; для машиночитаемости
   добавляется **необязательное** поле `code` — совместимое расширение, наполняется
   по мере надобности (волна 4, мобильный клиент). Док §3.1 приводится в соответствие.
2. **Пакет остаётся плоским.** `common/platform/music` из `docs/api-contracts.md` §4
   не вводим: 10 файлов сейчас, ~16 после волны — раскладка по подпапкам добавит шум
   без выигрыша. Порог — 30 файлов.
3. **Date→ISO маппинг живёт в route handler'е** (эталон волны 2), не в контракте и не
   в core. Core держит `Date`, граница переводит в ISO.
4. **Барьер вводится с allowlist.** Требовать контракт от всех 119 сразу — гейт красный
   с первого дня, его выключат. Allowlist перечисляет непереведённые группы с причиной
   и сам не гниёт: файл в allowlist, который уже импортирует контракты, и путь
   несуществующего роута — тоже ошибка гейта.

## Границы

- Формы ответов и статус-коды на проводе не меняются ни в одном роуте. Изменение
  поведения в этой волне — только фикс `joinedAt` (сырой `Date` → ISO явно, на проводе
  идентично).
- Ручную валидацию входа на zod переводим только там, где схема и так пишется срезом;
  `dashboard/**` не трогаем — это отдельный подпроект.
- Живые потребители ресурсных роутов (`lib/player/lazy-queue-fetchers.ts` для
  `releases/{id}`) должны продолжать работать без правок.

## Проверка

Гейты web/core; contract-тест на каждый переведённый роут (ответ парсится схемой,
которую импортирует клиент) — в существующих `route.test.ts`; новый `check:contracts`
красный при роуте без схемы вне allowlist.

## Откат

Срез за срезом: роут возвращается к локальной схеме, контракт остаётся неиспользованным.
Барьер отключается снятием шага в `gates` и `prebuild`.
