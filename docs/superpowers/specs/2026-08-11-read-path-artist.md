# Read-path артиста — одна реализация, два входа (шаг 2.1)

**Дата:** 11.08.2026 · **Основание:** `docs/migration-plan.md` волна 2, `docs/architecture.md` §4

## Проблема

`/api/v1/artists/[slug]` существует и построен через core, но страница артиста им не пользуется:
она собирает экран из **восьми** независимых чтений (`page.tsx:56-72,114-118`) — профиль через
`ArtistService`, а дальше напрямую query-функции `@vire/db`: релизы, upcoming, посты, смартлинки,
playable-треки, explicit-флаги, follow-состояние и счётчик, presave-состояния. Роут отдаёт
только профиль, и даже гейт видимости (`artistHasPublishedTrackById` + `isArtistMember`)
у него отсутствует — то есть роут показывает скрытого артиста, а страница нет.

Это и есть расхождение двух реализаций, о котором писал аудит: у мобильного клиента способа
получить экран артиста нет вовсе.

## Решение

Экран собирается **одним read-сервисом в core**, у которого два входа: Server Component
вызывает его в процессе, HTTP-роут вызывает его же.

```
                         ┌──────────────────────┐
   page.tsx (RSC) ───────┤                      │
                         │  ArtistPageService   ├──→ IArtistReadRepository ──→ Postgres
   /v1/artists/[slug]/page┤   (packages/core)    │
                         └──────────────────────┘
```

**Порт `IArtistReadRepository`** (core) — узкие методы под каждое чтение экрана:
`findBySlug`, `hasPublishedTrack`, `isMember`, `listPublishedReleases`, `listUpcoming`,
`listPosts`, `listSmartLinks`, `listPlayableTracks`, `explicitReleaseIds`, `followerCount`,
`isFollowing`, `presavedReleaseIds`.

**Реализация в `packages/db`** — тонкие обёртки над **существующими** query-функциями.
SQL не переписывается: он остаётся в `packages/db/src/queries/*`, порт лишь даёт ему имя
на языке домена. Это условие обратимости шага.

**Сервис `ArtistPageService.getPage({ slug, viewerId, now })`** — оркестрация и правила:
гейт видимости (скрытый артист → `NotFoundError`), склейка explicit-флагов с релизами,
персональные части (following, presaved) только при `viewerId`. Правила проверяются
тестами на фейковом репозитории, без БД.

**Контракт** — `@vire/api-contracts`: zod-схема ответа `artistPageResponseSchema`.
Даты в контракте — ISO-строки, в core-типах остаются `Date`; маппинг явный, в одном месте.

**Роут** — новый `GET /api/v1/artists/[slug]/page`. Существующий `/api/v1/artists/[slug]`
(ресурсный профиль) не трогаем: у него свой контракт и свои тесты.

## Что НЕ делаем

- Не заставляем Server Component ходить в собственный HTTP (лишний хоп, потеря стриминга RSC).
- Не переписываем SQL и не удаляем старые query-функции: они остаются реализацией порта.
  Удаление — отдельным шагом после прода, по правилу волны.
- Не трогаем `SimilarArtistsSection` — он в своём Suspense и читает через `@/lib/discovery`;
  отдельный блок, отдельный шаг.

## Проверка

- Набор и порядок сущностей на странице до и после — совпадают (снапшот-тест ответа сервиса
  на фейках + ручная сверка страницы).
- Contract-тест: ответ роута парсится той же схемой, которую импортирует клиент.
- Гейт видимости: скрытый артист даёт 404 и на странице, и на роуте (сегодня роут его отдаёт —
  это чинится здесь).
- Нет регресса TTFB: число запросов к БД на рендер страницы не растёт.

## Откат

Страница возвращается на прежние вызовы (они не удалены) — один revert. Роут и контракт
можно оставить: они никого не ломают.
