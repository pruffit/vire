# E2EE личных сообщений (1:1) — дизайн

Дата: 2026-07-19. Раздел роадмапа: `docs/roadmap/stage-2.md` §11.5 (чат). Это **spec 2**
социального слоя; ветка `feat/social-friends`. Мёрж соцслоя в `main` — после этой спеки,
по явной команде. **В прод не катим** (деплой по тегу — вне скоупа).

## Что строим

Существующий чат 1:1 (spec §11.5) переводим в **end-to-end шифрование**: сервер хранит и
релеит только шифротекст и **не может** прочитать сообщения. Никакой модерации чата — по
дизайну невозможна. Уведомления spec-1 уже контентless — менять не нужно.

## Зафиксированные решения (из брейншторма)

- **Крипта:** libsodium, X25519. Ключ диалога выводится из **Диффи-Хеллмана личных ключей**
  двух друзей (без forward secrecy — принято; FS отдельным витком).
- **Ключи бесшовно, без парольных фраз/кодов для юзера.** Личный ключ генерится молча.
- **Мультидевайс:** новое устройство привязывается к уже настроенному **обменом с
  6-значным кодом** (SAS-аутентификация DH), без QR, без passkey, без запоминаемого пароля.
  Личный ключ переезжает на новое устройство → вся история читается везде.
- **Охват:** E2EE по умолчанию для всех 1:1. Плейнтекста сообщений в БД нет никогда.
  Чат не в проде → истории нет, стартуем с чистого листа.
- **Server-blind** — жёсткое требование. Отсюда неустранимый предел: завести новое
  устройство можно только когда **одно уже настроенное устройство под рукой**; потеря разом
  всех устройств = потеря истории (сервер восстановить не может).

### Почему так (крипто-обоснование)
Бесшовное чтение на «чистом» устройстве только по логину + слепой сервер — взаимоисключающи
(секрет восстановим лишь из того, что доступно, а доступен только логин, который знает
сервер). Поэтому секрет переезжает между устройствами **не через доверие к серверу**, а через
аутентифицированный DH-обмен телефон↔ноут, где 6-значный код (SAS) не даёт серверу вклиниться
(MITM). Пароль/passkey/QR отвергнуты явно.

## Крипто-модель

Примитивы: libsodium (`libsodium-wrappers` в браузере). Всё шифрование/дешифрование —
**на клиенте**. Сервер оперирует непрозрачными блобами.

### Личность
- У пользователя одна **identity-пара** X25519 (`ikPub`, `ikPriv`). Генерится молча на первом
  устройстве. `ikPriv` живёт в IndexedDB, **на сервер в открытом виде не уходит никогда**.
- Публичный ключ публикуется: `user_identity_keys(user_id, ik_pub, ...)` — одна строка на юзера,
  общий `ikPub` для всех его устройств.

### Ключ диалога (CK) — прямой DH, без хранения на сервере
Оба друга независимо вычисляют один и тот же симметричный ключ из своих identity-ключей:

```
shared = crypto_scalarmult(ikPriv_self, ikPub_other)          # X25519 DH (симметричен)
CK     = BLAKE2b(shared || ikPub_low || ikPub_high, personal="vire-chat-ck-v1")
```
`ikPub_low/high` — отсортированная пара публичных ключей (защита от unknown-key-share и
согласование значения на обеих сторонах). **Таблицы ключей диалога нет** — CK детерминированно
выводится из DH на лету любым устройством, у которого есть `ikPriv`.

### Сообщение
```
nonce  = random(24)
cipher = crypto_secretbox(plaintext_utf8, nonce, CK)          # XSalsa20-Poly1305
```
Хранится `{cipher (base64), nonce (base64)}`. Обе стороны (и все их устройства) вычисляют тот
же CK → шифруют и читают, включая свои отправленные и историю. FS нет: CK статичен на пару.

## Привязка нового устройства (6-значный код, SAS-аутентифицированный DH)

Задача: перенести `ikPriv` с настроенного устройства **A** на новое **B** через релей сервера
так, чтобы сервер не узнал `ikPriv` и не подменил себя посередине. Оба устройства — **один
залогиненный юзер**, поэтому сервер сшивает их сессии по `user_id` (не нужен код «найти
сессию» — нужен только код подтверждения).

```
1. B (новое): генерит эфемерную пару (eB). POST /keys/link/start {eB_pub}
   → сервер создаёт link-сессию для user U (Redis, TTL ~5 мин), возвращает link_id.
   B ждёт (SSE/поллинг).
2. A (настроенное, онлайн): видит запрос привязки (SSE «новое устройство» или экран
   «Устройства»). Генерит эфемерную пару (eA), забирает eB_pub, считает
   S = scalarmult(eA_priv, eB_pub), SAS = digits6(BLAKE2b(eA_pub || eB_pub || S)).
3. B получает eA_pub, считает то же S и SAS. **B показывает 6 цифр.**
   A спрашивает «введите код с нового устройства». Юзер читает с B, вводит в A.
   A сверяет с локально вычисленным SAS.
4. Совпало → A шифрует личный ключ на канале обмена ключом, выведённым из S с ДРУГОЙ
   доменной меткой, чем SAS (SAS и wrap-ключ не совпадают): wrapKey = BLAKE2b(S,
   personal="vire-link-wrap-v1"); wrapped = crypto_secretbox(ikPriv, nonce, wrapKey);
   POST /keys/link/complete {link_id, wrapped, nonce}.
   Сервер релеит B (через link/poll). B выводит тот же wrapKey из S → расшифровывает →
   получает ikPriv. Устройство настроено.
```
Сервер видел только `eA_pub`, `eB_pub`, `wrapped` — вычислить `S` не может (нет эфемерного
приватного), MITM невозможен без угадывания 6 цифр (одна попытка на одноразовую сессию,
шанс 1e-6; несовпадение → сессия аборчена). SAS считается по всему транскрипту (оба эфемерных
ключа), поэтому подмена ключа сервером ломает совпадение кода.

**Первое устройство вообще** (нет ни одного настроенного) → просто генерит новую identity,
привязка не нужна. Привязка — только для 2-го и далее устройств. A офлайн → «откройте VireMusic на
другом своём устройстве, чтобы подтвердить».

## Данные (миграция 0041)

- `user_identity_keys(user_id uuid pk → users cascade, ik_pub text not null,
  created_at timestamptz default now(), updated_at timestamptz default now())`.
- `messages`: `body` теперь **шифротекст** (base64); добавить `nonce text not null` и
  `enc_version smallint not null default 1`. Таблица пуста (чат не в проде) — миграция
  безопасна; при наличии dev-строк они очищаются в миграции.
- **Link-сессии — в Redis**, не в Postgres (эфемерны, TTL): ключ `chat:link:{link_id}` →
  `{ userId, eB_pub, eA_pub?, wrapped?, nonce?, status }`, TTL ~5 мин. Тот же `REDIS_URL`.
- Ключа диалога в БД нет (выводится из DH).

## Потоки

### Отправка (server-blind)
Клиент шифрует до POST: `POST /api/v1/chat/[conversationId]/messages { ciphertext, nonce }`.
Сервер валидирует: участник + гейт друзья/блок (без изменений) + **байтовый размер**
шифротекста (бонд ~8 КБ под 4000 симв. + оверхед), хранит как есть, релеит по SSE опаковый
блоб `{ ciphertext, nonce, senderId, createdAt }`. Плейнтекст-длину (1–4000) проверяет клиент
**до** шифрования.

`ChatService.send` меняет контракт: принимает `{ciphertext, nonce}` вместо plaintext-body,
снимает plaintext-валидацию длины, добавляет байтовый бонд. Публикация/уведомления — без
изменений.

### Чтение
Клиент выводит CK (DH), `crypto_secretbox_open` на истории и входящих. Устройство без `ikPriv`
(не настроено/не привязано) читать не может — «давать чтение только после успешного обмена».

### Список диалогов / превью
Сервер не может рендерить `lastMessageBody`. Отдаёт последний блоб; клиент расшифровывает
превью локально. Пока `ikPriv`/CK не готовы → «🔒 Зашифровано». **Непрочитанное — без
изменений** (по таймстемпам, контент не нужен). Уведомления spec-1 — контентless, совместимы.

## Доверие к публичному ключу (MITM identity)
Сервер раздаёт `ikPub` друга → активный сервер может подменить (MITM всей переписки). v1:
**TOFU** + показ **safety-number** (fingerprint от пары `ikPub`) в диалоге для ручной сверки по
желанию; смена `ikPub` собеседника (реенролл/сброс) → плашка «код безопасности изменился»
(как Signal/WhatsApp). Обязательную верификацию — на будущий виток.

## Сброс / ротация
Потерял все устройства/хочет заново → генерит новую identity-пару, `ikPub` заменяется. Старая
история (CK от старого DH) становится нечитаемой — принято, escape-hatch с явным
предупреждением. Новые сообщения — на новом CK; собеседник видит смену safety-number.

## Слои (vire-architecture)
- **Клиентская крипта** — `apps/web/lib/e2ee/*` (libsodium/WASM): генерация identity, вывод CK,
  encrypt/decrypt, IndexedDB-хранилище ключа, протокол привязки (эфемерный DH + SAS). Не в
  `packages/core` (ядро чистое и не браузерное).
- **Чистые функции** (тестируемые, могут жить в core или в `lib/e2ee` как pure util): формат
  safety-number, base64, size-guard, `digits6(SAS)` из входных байтов.
- **Сервер:** роуты `POST/GET /api/v1/keys` (свой `ikPub` upload / чужой `ikPub` fetch),
  `POST /keys/link/start`, `GET /keys/link/poll`, `POST /keys/link/complete` (релей привязки
  через Redis; single-use, TTL). `ChatService.send`
  — на `{ciphertext,nonce}`. Новый репозиторий/квери `user_identity_keys`. Link-сессии — Redis
  (`lib/`), деградируют как presence.

## Degradation
- Нет `ikPub` собеседника (не завёл ключи) → нельзя начать шифрованный диалог: показываем «у
  собеседника ещё не настроено шифрование». Т.к. E2EE обязателен — оба должны иметь identity.
- libsodium не загрузился → чат недоступен с явным сообщением (плейнтекст-фолбэка нет — E2EE
  обязателен).
- Redis недоступен → привязка устройства недоступна (деградирует, как presence); отправка/
  чтение на уже настроенных устройствах работают (крипта клиентская, релей — через существующий
  SSE/REST).
- Блок/расфренд → серверный гейт без изменений (не требует плейнтекста).

## Тестирование (vire-testing)
- **Крипто round-trip:** две identity-пары → обе выводят одинаковый CK → encrypt/decrypt;
  ассерт равенства CK с обеих сторон; ассерт, что в серверных полях нет плейнтекста.
- **Привязка/SAS:** A/B эфемерные → одинаковый S → одинаковый SAS (6 цифр); MITM (другой
  эфемерный) → SAS не совпал → аборт; `wrapped(ikPriv)` расшифровывается по `S`.
- **Чистые функции:** `digits6`, safety-number, base64, size-guard.
- **Роуты:** `keys` upload/fetch (authz), `link/*` (только тот же юзер, TTL, single-use),
  `chat send` хранит шифротекст дословно и режет oversize, гейты участника/друзья без изменений.
- **Инвариант server-blindness:** `messages.body` никогда не равен плейнтексту; уведомления
  остаются контентless.
- Все гейты VireMusic: typecheck (web/core/db), lint, check:routes, test (web/core/worker),
  audit:design (UI шифрования/устройств), build.

## UI (Impeccable / мобилка обязательна)
- Молчаливый энролл при первом входе в «Сообщения» (без экранов настройки в норме).
- Экран **«Устройства»**: список, «добавить устройство» (показ 6 цифр на новом / ввод на
  старом), отвязка. Узкий вьюпорт, тач-таргеты ≥44px, без `min-h-screen`.
- В диалоге — ненавязчивый индикатор «🔒 зашифровано» + доступ к safety-number.
- Состояния: «настрой шифрование», «подтверди на другом устройстве», «код безопасности
  изменился», «сообщение не расшифровать» (старый CK после сброса).

## Env
Новых переменных нет (identity/CK — клиентские; link-сессии на существующем `REDIS_URL`).

## Вне скоупа (будущие витки)
Forward secrecy / Double Ratchet, обязательная верификация ключей, группы, вложения,
восстановление истории без настроенного устройства, миграция плейнтекст-истории (её нет).
