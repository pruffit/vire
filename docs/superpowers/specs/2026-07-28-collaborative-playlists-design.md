# Коллаборативные плейлисты (stage-2 §7.3) — дизайн

Дата: 28.07.2026. Колонка `playlists.is_collaborative` зарезервирована с миграции 0000 и
до сих пор мертва. Задача — включить её: несколько человек ведут один персистентный
плейлист, изменения видны сразу.

Не путать с джемом (§8): джем — эфемерная очередь на тусовку, вход по коду, гости без
аккаунта, авто-закрытие 12ч. Здесь — постоянный плейлист, участие требует аккаунта.

## Продуктовые развилки (решены без Danya — работа автономная)

| Развилка | Решение | Почему |
|---|---|---|
| Кто может присоединиться | Любой авторизованный по ссылке-приглашению с токеном | Ссылка = capability; не требует ни публичности плейлиста, ни дружбы |
| Приватный + совместный | Разрешено: валидный токен даёт доступ к странице | Иначе владелец обязан публиковать плейлист, чтобы позвать друга |
| Кто что удаляет | Владелец — любой трек, коллаборатор — только свои добавления | Защита от вайпа чужой работы; `playlist_tracks.added_by` уже есть |
| Порядок треков | Меняют все участники | Не разрушает данные, а совместная сортировка — половина смысла |
| Метаданные/обложка/удаление/кик | Только владелец | Плейлист остаётся его |
| Гости без аккаунта | Нет | Персистентная запись требует субъекта; атрибуция и кик иначе не работают |
| Голосование, комментарии, история правок | Вне объёма | Отдельные фичи, не нужны для «включить колонку» |

## Модель

```
playlists.is_collaborative  boolean  — уже есть, начинает использоваться
playlists.collab_token      text     — NEW, nullable: токен приглашения
playlists.version           integer  — NEW, not null default 0: версия состава

playlist_collaborators      — NEW
  id, playlist_id → playlists(id) on delete cascade
  user_id → users(id) on delete cascade
  invited_by → users(id)
  joined_at
  unique(playlist_id, user_id), index(playlist_id), index(user_id)
```

`collab_token` живёт только пока `is_collaborative = true`: выключение тумблера обнуляет
токен (старые ссылки мертвеют), «сбросить ссылку» генерит новый. Членства при выключении
**не удаляются** — обратное включение возвращает ту же команду.

`version` инкрементится в **той же транзакции**, что мутация состава (add/remove/reorder) —
как `jam_sessions.queue_version`. Это опорная точка для realtime: событие несёт версию,
клиент отбрасывает устаревшие.

## Права

| Действие | Владелец | Коллаборатор | Прочие |
|---|---|---|---|
| Просмотр страницы | ✅ | ✅ | только PUBLIC или валидный токен в URL |
| Добавить трек | ✅ | ✅ | ❌ |
| Удалить трек | любой | только `added_by = self` | ❌ |
| Переупорядочить | ✅ | ✅ | ❌ |
| Метаданные, обложка, удаление плейлиста | ✅ | ❌ | ❌ |
| Тумблер совместности, сброс ссылки, кик | ✅ | ❌ | ❌ |
| Выйти из плейлиста | ❌ (владелец не участник) | ✅ | ❌ |

Гарды на присоединение: авторизован · `is_collaborative` · токен совпадает · не владелец ·
нет блокировки в любую сторону с владельцем (`isBlockedEitherWay`) · участников < 50.

Лимит добавлений коллаборатором — 20/мин на пользователя (тот же rate-limit, что в
остальных listener-роутах).

## Realtime

Канал `rt:playlist:{id}` поверх существующего `lib/realtime.ts` (`publishChannel` /
`subscribeChannel`). Порт в core — `ports/playlist-realtime.ts` с `broadcast(playlistId,
event)`, зеркало `jam-realtime.ts`.

События тонкие, без полезной нагрузки:
- `playlist:changed` — `{ playlistId, version, actorId }`
- `playlist:collaborators` — `{ playlistId, actorId }` (join / leave / kick)

Клиент, получив событие не от себя, дёргает `GET /api/v1/playlists/[id]/tracks` и заменяет
список. Полный список в событие не кладём: плейлист может быть на сотни треков, а
подписчиков на канал — по числу открытых вкладок.

SSE-роут `GET /api/v1/playlists/[id]/stream` — только участникам и только для совместного
плейлиста; snapshot с текущей версией на подключении, heartbeat 25с, cleanup по abort
(1:1 с `jam/[code]/stream/route.ts`). Подписка на клиенте включается только когда
плейлист совместный и зритель — участник; в остальных случаях соединение не открывается.

Падение Redis деградирует до «нет живых обновлений» — мутации и REST работают как прежде.

## Поверхности

- **Шапка `/playlists/[id]`** — бейдж «Совместный», стек аватаров участников (≤4 + «+N»).
- **Меню владельца** — тумблер «Совместный плейлист», копирование ссылки-приглашения,
  «Сбросить ссылку», список участников с «Исключить».
- **Меню коллаборатора** — только «Покинуть плейлист».
- **Баннер приглашения** при `?join=<token>` — кто зовёт + кнопка «Присоединиться»;
  неавторизованному — вход с возвратом на ту же ссылку.
- **Трек-строка** — аватар добавившего, только в совместных плейлистах.
- **Медиатека `/library`** — плейлисты, где юзер коллаборатор, показываются рядом со
  своими с пометкой роли (`PlaylistSummary.role`).
- **Уведомление** — новый тип `PLAYLIST_COLLAB_JOIN` владельцу при входе участника.
  Добавления треков не уведомляем (шум).

## Инварианты, которые нельзя сломать

1. Приватный плейлист без токена и без членства — по-прежнему 404 (включая OG-картинку).
2. Не-участник не может изменить состав никаким роутом (роуты уже owner-gated — гард
   расширяется, а не снимается).
3. `version` растёт монотонно и только в транзакции мутации.
4. Совместность не меняет `visibility`: приватный остаётся вне выдачи, sitemap и лайков.

## Риски

- **Гонка одновременных reorder** — существующий `isPermutation`-guard отклоняет
  переупорядочивание, не совпадающее с текущим составом; клиент получит 409 и перечитает.
  Достаточно: конфликт разрешается перечитыванием, данные не портятся.
- **Утечка через токен** — токен даёт доступ к приватному плейлисту любому, кому попал.
  Это осознанная семантика ссылки-приглашения; смягчение — «Сбросить ссылку».
- **Спам в чужом плейлисте** — кик + выключение совместности + rate-limit.
