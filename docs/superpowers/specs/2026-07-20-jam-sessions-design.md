# Джем — совместные плейлисты для тусовок (спека)

Дата: 2026-07-20. Источник: `docs/roadmap/stage-2.md` §8 (был помечен `[обсудить]`).

## 1. Что строим

Сессия «джема»: несколько человек подключаются по ссылке/QR к общей очереди треков,
добавляют и переставляют треки в реальном времени, **и слышат одно и то же в одну
секунду** на своих устройствах.

Продуктовые развилки §8.4 закрыты (решение Danya, 20.07.2026):

| Вопрос | Решение |
|---|---|
| Синхронное воспроизведение или общая очередь? | **Синхронное воспроизведение** — все устройства играют одну позицию одного трека |
| Гость без аккаунта? | **Да** — вход по ссылке/QR, имя вводится или генерится, аккаунт не нужен |
| Голосование за треки? | **Нет в v1** |
| Где живёт | **Отдельная страница `/jam/[code]`**, обычный плеер не трогаем |
| Объём v1 | права хоста, drag-n-drop порядка, сохранение джема в плейлист, приглашение друзей |

### Не входит в v1
Голосование за треки; синхронизация нескольких хостов; джем между городами как
продуктовый сценарий (технически работает, но целим в «одна комната, один вайфай»);
видео/чат внутри джема (для переписки есть `/messages`).

## 2. Ключевое техническое решение: синхронизация звука

Синхронное воспроизведение — единственная действительно сложная часть. Наивный подход
(«хост шлёт свою позицию, гости прыгают туда») даёт рывки: у каждого свой сетевой лаг и
свой буфер HLS.

**Модель: сервер-авторитетные часы, а не трансляция позиции.**

Состояние воспроизведения в Redis (`jam:{id}:playback`):

```
{ trackId, startedAtMs, paused, pausedPositionMs, version }
```

`startedAtMs` — момент серверного времени, в который позиция трека была бы `0`.
Текущая позиция выводится, а не передаётся:

```
position = paused ? pausedPositionMs : (serverNow - startedAtMs)
```

Это значит: событие рассылается **только при смене состояния** (play/pause/seek/смена
трека), а не каждую секунду. Клиент, потерявший событие или переподключившийся, сам
вычисляет верную позицию — самовосстанавливающаяся модель.

### Синхронизация часов клиента

Клиенту нужно знать серверное время. NTP-подобный замер через `GET /api/v1/jam/time`
(без БД, только `Date.now()`):

```
offset = tServer - (t0 + t1) / 2      RTT = t1 - t0
```

Берём 5 замеров, выбираем сэмпл с минимальным RTT (наименее зашумлённый), повторяем
раз в 5 минут. Точность в пределах локальной сети — единицы миллисекунд.

### Коррекция дрейфа

Цикл раз в 2с на клиенте:

| Дрейф | Действие |
|---|---|
| > 2000 мс | жёсткий `seek` (после буферизации/долгой паузы вкладки) |
| 150–2000 мс | `playbackRate = 1 ± 0.03` до схождения < 50 мс, затем обратно в 1 |
| < 150 мс | ничего |

Подтяжка скоростью незаметна на слух (3%) и не даёт слышимых прыжков, в отличие от
seek. `preservesPitch = true`, чтобы не плыла тональность.

### Автоплей

Браузеры блокируют автостарт звука без жеста пользователя. Гость, зайдя по ссылке,
**обязан** тапнуть «Подключиться к звуку» — это не UX-прихоть, а требование платформы.
Экран входа в джем строится вокруг этого тапа, а не прячет его.

## 3. Модель данных

**Postgres** (переживает рестарт, нужен для «сохранить в плейлист»):

- `jam_sessions` — `id`, `code` (6 симв., алфавит без похожих глифов), `host_user_id`,
  `title`, `status` (`LIVE`/`ENDED`), `created_at`, `ended_at`, `saved_playlist_id`
- `jam_participants` — `jam_id`, `user_id` (nullable), `guest_session_id` (nullable),
  `display_name`, `role` (`HOST`/`GUEST`), `joined_at`, `last_seen_at`
- `jam_queue_items` — `jam_id`, `track_id`, `position`, `added_by_participant_id`, `added_at`

**Redis** (горячее, эфемерное): состояние воспроизведения, presence участников
(ZSET по образцу `presence:track`), pub/sub канала комнаты.

Разделение сознательное: очередь мутируется относительно редко (человек тапает трек) и
должна пережить перезапуск, позиция воспроизведения читается постоянно и не должна
ходить в БД.

## 4. Realtime

Канал `rt:jam:{jamId}`. Существующий `lib/realtime.ts` уже подписан на `rt:*` через
PSUBSCRIBE — **подписчик менять не нужно**, достаточно обобщить построение ключа канала
(сейчас захардкожен префикс `rt:user:`).

Отдельный SSE-роут `GET /api/v1/jam/[code]/stream`: в отличие от
`/api/v1/realtime/stream` он **не требует `auth()`** — доступ по членству в комнате
(подписанный `sessionId` гостя или сессия пользователя), а не по аккаунту.

События: `jam:queue` (полная очередь + `version`), `jam:playback`, `jam:participants`,
`jam:ended`.

**Конфликты порядка.** Не CRDT и не 409-версии: мутация выражается как намерение
(«переместить элемент X на позицию N», «удалить X»), сервер применяет её к текущему
состоянию, поднимает `version` и рассылает **полную** очередь. Last-write-wins на
уровне намерения не может испортить список, а клиент применяет пришедшую очередь только
если `version` больше локальной. При активном локальном drag входящие обновления
буферизуются и применяются по отпусканию — иначе список дёргается под пальцем.

## 5. Гостевой доступ

Опираемся на существующий подписанный анонимный id (`POST /api/v1/session` +
`lib/session-signing.ts`) — он серверной генерации и не подделывается. Гость = запись в
`jam_participants` с `guest_session_id` и введённым именем. Это **не** аккаунт: прав
нет, профиля нет, вне джема идентичности нет.

Права: транспортом (play/pause/seek/следующий) управляет **только хост** — иначе на
тусовке начнётся война за паузу. Добавлять и двигать треки может любой участник.
Хост дополнительно может удалить любой трек, кикнуть участника и закрыть джем.

## 6. Защита от злоупотреблений

Публичная по ссылке комната с анонимным доступом — поверхность для флуда:
лимит добавлений на участника (10/мин), потолок очереди (200), потолок участников (50),
авто-закрытие джема после 12ч без активности, `code` достаточно широкий против перебора.

## 8. Слои (по `vire-architecture`)

- `packages/db` — схема `jam_*` + миграция, репозиторий
- `packages/core` — `JamService` (чистая логика: права, лимиты, применение мутаций
  очереди, вывод позиции воспроизведения из часов), порты `Clock`/`JamStateStore`
  (Redis за интерфейсом), `Result<T,E>`
- `apps/web/app/api/v1/jam/*` — только HTTP: zod-валидация, вызов сервиса, ответ
- `apps/web/app/(listener)/jam/[code]` — экран, FSD-слои вниз

Вывод позиции и решение о коррекции дрейфа — **чистые функции** с инъектируемым
временем: это самая тестируемая и самая ошибкоопасная часть фичи.

## 9. Риски

| Риск | Ответ |
|---|---|
| Дрейф звука на слабых мобилках/плохом вайфае | Коррекция скоростью + жёсткий seek на пороге; при провале — деградация в «общую очередь» без синхро |
| Автоплей заблокирован | Явный тап «Подключиться к звуку», без него в комнату не входим |
| Вкладка ушла в фон, таймеры задушены | Позиция выводится из часов, а не копится — по возвращении сразу верная |
| Redis лёг | Очередь в Postgres жива, синхро деградирует; по образцу остальных presence-путей — не 500, а тихая деградация |
| Один SSE на комнату × участники | Комнаты малы (≤50), нагрузка сопоставима с чатом |
