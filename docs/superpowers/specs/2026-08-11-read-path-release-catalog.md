# Спека: read-path каталога релизов (волна 2, шаг 2.3)

**Основание:** `docs/migration-plan.md` §волна 2 · продолжение шагов 2.1 (артист) и 2.2 (релиз).

## Проблема

`/releases` (`app/[locale]/(listener)/releases/page.tsx`) читает `listReleases` из `@vire/db`
напрямую: три вкладки (`fresh` / `week` / `popular`) маппятся в `{sort, sinceDays, limit: 60}`
прямо в компоненте. HTTP-эндпоинта каталога нет вообще — мобильный клиент не может получить
витрину релизов, и это единственный список, который дальше нужен SDUI-блоку главной.

Пагинации нет ни в каком виде: страница берёт 60 записей и раскрывает их по 24 на клиенте.
Плану волны 2 нужна пагинация в контракте — иначе эндпоинт наполовину бесполезен для клиента,
которому нужен второй экран выдачи.

## Решение

Одна реализация, два входа — та же механика, что в 2.1/2.2:

1. `ReleaseCatalogService` в `@vire/core` за портом `IReleaseCatalogRepository`.
2. Страница `/releases` вызывает сервис в процессе.
3. Новый `GET /api/v1/releases` вызывает тот же сервис.
4. Контракт запроса и ответа в `@vire/api-contracts` + contract-тест.

**Тип карточки.** `DiscoveryRelease` (db) и `ArtistUpcomingRelease` (core, заведён в 2.1) —
побайтово одна и та же форма. Вводится `ReleaseCard` в core, `ArtistUpcomingRelease` остаётся
его алиасом (экспорт 2.1 не ломается), в контрактах — общая `releaseCardSchema` в `catalog.ts`.

**Пагинация.** Порт принимает `{ sort, sinceDays, limit, offset }`; `listReleases` в db
получает `offset` (две ветки запроса, по одной строке в каждую). Сервис запрашивает `limit + 1`
записей и отдаёт `{ items, hasMore }` — второго запроса на счётчик нет.

**Валидация.** Параметры запроса — zod-схема в контрактах (`sort` из перечисления,
`sinceDays`/`limit`/`offset` — целые в границах), невалидный вход → 400. Сервис дополнительно
клампит значения: он не вправе рассчитывать, что вызывающий уже провалидировал.

## Границы

- Вкладки и их маппинг в параметры остаются на странице: это её UI-состояние, не доменное правило.
- Разметка, порядок карточек и прогрессивный показ по 24 не меняются.
- Видимость (`isActive` артиста + `releaseIsAired`) уже внутри `listReleases` — новых правил
  видимости не вводим и существующие не дублируем.
- `listReleases` не удаляется: её зовут другие места (главная, «скоро выйдет»).

## Проверка

Гейты core/db/web (`typecheck`, `test`, `lint`, `check:routes`, `check:i18n`, `check:layers`,
`build`). Contract-тест парсит ответ роута схемой, которую импортирует клиент. Сверка «до/после»:
три вкладки `/releases` дают тот же состав и порядок карточек.

## Откат

Один revert: страница возвращается к прямому `listReleases`, роут удаляется, сервис и контракт
остаются безвредными.
