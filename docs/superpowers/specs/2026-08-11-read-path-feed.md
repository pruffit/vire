# Спека: read-path ленты (волна 2, шаг 2.6)

**Основание:** `docs/migration-plan.md` §волна 2 · продолжение 2.1–2.5.

## Проблема

Оркестрация «Вашей ленты» живёт в `apps/web/lib/feed.ts`: тянет кандидатов и профиль вкуса
из `@vire/db`, гоняет чистые `scoreFeedItem`/`composeFeed` из core, добирает свежее при
холодном старте. Логика доменная (политика ранжирования и холодного старта), но лежит в web
и вызывается только Server Component'ом `components/home/feed-section.tsx`. HTTP-входа нет —
персонализированная лента для клиента без Next недоступна.

Константы политики (`FEED_LIMIT`, `FEED_COLD_START_THRESHOLD`, размер пула, потолок на артиста,
доля малых артистов) тоже живут в web.

## Решение

`FeedService` в `@vire/core` за портом `IFeedRepository` (`candidates`, `freshCandidates`,
`taste`), константы политики переезжают вместе с ним. Чистые `scoreFeedItem`/`composeFeed`
не трогаем — сервис остаётся тонким оркестратором над ними.

Два входа: `feed-section.tsx` зовёт сервис в процессе, новый `GET /api/v1/feed` — по HTTP.
Лента персональна: без сессии роут отвечает 401, `userId` берётся из сессии, а не из query.

Контракт — `feedResponseSchema` в `@vire/api-contracts` (`{ items }`, даты ISO).

## Границы

- Формула ранжирования и состав ленты не меняются: те же чистые функции, те же константы,
  тот же порядок вызовов. Шаг переносит оркестрацию, а не правит выдачу.
- `lib/feed.ts` остаётся тонкой обёрткой над сервисом (или уходит целиком, если у него
  не остаётся своих потребителей) — существующие тесты переезжают в core вместе с логикой.
- Пагинации у ленты нет и не вводим: это лимитированная выдача, а не каталог.

## Проверка

Гейты core/db/web + contract-тест роута. Существующие сценарии `lib/feed.test.ts`
(холодный старт, форс причины `fresh`, потолок на артиста) должны остаться зелёными
после переезда в core — это и есть проверка «выдача не изменилась».

## Откат

Один revert: `lib/feed.ts` возвращается к прямым вызовам, роут удаляется.
