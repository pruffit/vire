# Мобильное приложение (RN + Expo) — инкремент 1: walking skeleton

**Контекст:** `docs/multiplatform.md` (стек — RN+Expo, решение зафиксировано), `docs/roadmap/platform-core-brief.md`
(второй продукт — реальный план, не гипотеза). Предпосылки закрыты: read-path в HTTP,
Bearer-auth + устройства, контракты, ядро плеера в `packages/core` (`docs/migration-plan.md`,
волны 2–5). Мобильного клиента не было — старт с нуля, `apps/mobile`.

**Масштаб инкремента 1:** тонкий вертикальный срез, не вся мобилка. Цель — доказать связку
целиком (auth → навигация → реальный экран с реальными данными), а не покрыть функциональность.
Плеер/воспроизведение звука — **вне этого инкремента** (нужен порт `IAudioEngine`, который
пока не вынесен — отдельный следующий шаг после этого среза).

**Окружение:** на этой машине нет Android SDK/эмулятора/Java (проверено — `adb`/`java` не
найдены). Верификация — `npx expo start --web` (react-native-web превью в браузере, доступно
без эмулятора) для структуры/навигации/данных; финальная проверка на реальном устройстве —
Expo Go по QR-коду, это должен сделать человек с телефоном под рукой, не эта сессия. Не
заявлять «работает на Android/iOS» без реальной проверки — только то, что реально прогнано.

## Дизайн-направление (решение принято, не обсуждается)

**Не портировать веб-лейаут.** Нижний таб-бар (Главная / Поиск / Медиатека / Профиль) —
нативная идиома, не веб-сайдбар. Тёмная тема по умолчанию (уже основной вкус платформы —
`packages/design-tokens`), крупные тач-цели, свои переходы (native-stack), никакого веба
внутри WebView для контентных экранов. `packages/design-tokens/src/tokens.json` — источник
цветов (та же палитра OKLCH → пересчитать в RN-совместимый формат при потреблении, RN не ест
`oklch()` в JS-объектах напрямую — нужен hex/rgb эквивалент, см. `generate.ts` как образец
генератора, можно добавить RN-таргет по тому же принципу, что уже есть CSS/TS-таргеты).

## Компонент 1 — веб: мост входа (новый, маленький)

**Проблема:** `POST /api/v1/auth/devices` **отклоняет Bearer** и выдаёт пару токенов только
по доказанной cookie-сессии (`docs/features/device-auth.md`) — так и задумано (второй
поверхности проверки пароля не появляется). Device-code flow сознательно не делается.
Значит первый вход мобильного приложения обязан пройти через настоящую веб-сессию.

**Решение:** `apps/web/app/mobile-auth-bridge/page.tsx` — Server Component, top-level
нелокализованный маршрут (как `/admin`/`/fwqa688`/`/desktop`). Логика:
1. `auth()` — если сессии нет, `redirect('/sign-in?callbackUrl=/mobile-auth-bridge')`.
2. Есть сессия → вызвать **тот же core-сервис**, что уже дёргает
   `apps/web/app/api/v1/auth/devices/route.ts` (посмотреть его реализацию и повторить
   вызов в процессе — паттерн «одна реализация, два входа», `docs/architecture.md` §4,
   не копировать логику выдачи токенов).
3. `redirect(\`vire://auth-callback?accessToken=${...}&refreshToken=${...}&deviceId=${...}\`)`.

Никакого нового API-контракта не требуется (это не `/api/v1/**` JSON-роут, а браузерный
редирект) — `check:contracts` не должен его видеть.

## Компонент 2 — мобильное приложение

`apps/mobile` — Expo (managed workflow, TypeScript), pnpm workspace-пакет (`package.json` с
`name: "@vire/mobile"`, скрипты `mobile:dev`/аналог — **не** `dev`/`build`, чтобы корневой
`turbo run dev`/`build` не подхватывал его непреднамеренно, тот же приём, что у
`apps/desktop`, см. `docs/features/desktop-app.md` → «Где код»). React Navigation
(`@react-navigation/native` + `native-stack` + `bottom-tabs`).

**Auth:** `expo-web-browser` → `WebBrowser.openAuthSessionAsync(webBaseUrl + '/mobile-auth-bridge', 'vire://auth-callback')`
(ephemeral-сессия — не обычный встроенный `<WebView>`, чтобы пароль вводился в изолированном
системном контексте, не в контролируемом приложением вебвью). Результат — access/refresh/
deviceId, положить в `expo-secure-store` (не `AsyncStorage` — токены). Обновление access —
`POST /v1/auth/refresh` при 401 (интерцептор одного fetch-клиента, не размазывать по экранам).
Контракты запроса/ответа — из `@vire/api-contracts` (`device-auth.ts`), **не выдумывать
заново** — `z.infer` даёт TS-типы бесплатно.

**Экраны инкремента 1:**
- Таб-бар: Главная (реализован) / Поиск, Медиатека, Профиль (заглушки-стабы под IA, не
  функциональны — только чтобы таб-бар не выглядел недоделанным демо на 1 экран).
- Экран входа (перед таб-баром, если токенов в `expo-secure-store` нет).
- Главная: реальные данные с `GET /v1/home/*` или `GET /v1/releases`/`GET /v1/artists`
  (контракты уже есть в `@vire/api-contracts`) — нативный скролл-список обложек/названий,
  press-состояния, без имитации веб-карточек 1:1.

**Что вне скоупа инкремента 1 (явно, не забыть в отчёте):** воспроизведение звука, оффлайн,
пуши, глубокие ссылки на конкретный трек/релиз кроме самого входа, iOS-сборка (нет Mac —
конфигурация в `app.json` пишется для обеих платформ, но реально проверяется только Android/
Expo Go/RN Web).

## Проверка (честно, по факту, не «должно работать»)

- `npx expo start --web` поднимается, таб-бар и главная рендерятся, реальные данные с прод/
  локального API приходят (не моки).
- `mobile-auth-bridge` — проверить на реальном Next dev-сервере (`pnpm --filter @vire/web dev`)
  прямым переходом залогиненным браузером: редиректит на `vire://...` с параметрами (сам custom
  scheme браузер не откроет — это нормально и ожидаемо вне приложения, важно что редирект
  собран правильно и токены в нём настоящие, не пустые).
- Гейты веба (новый роут страницы): `typecheck`, `lint`, `check:routes`, `check:i18n`,
  `check:contracts` (не должен зацепить), `test`, `build`.
- Гейты мобилки: `tsc --noEmit` в `apps/mobile` (если есть свой скрипт typecheck — завести
  по образцу `apps/desktop`/остальных пакетов).
- **Явно указать в отчёте**, что реальный запуск на устройстве через Expo Go не проверялся
  агентом (нет телефона) — это следующий шаг для человека, не заявлять как «протестировано».
