# Sitemap: потолок 50k URL — дизайн

Дата: 28.07.2026. Бэклог: `docs/roadmap/TODO.md` → «Sitemap без потолка».

## Проблема

`apps/web/app/sitemap.ts` собирает один `<urlset>` из всех артистов, релизов, треков,
смартлинков и публичных плейлистов без каких-либо лимитов. Протокол sitemap ограничивает
файл 50 000 URL и 50 МБ. Сейчас каталог крошечный, но потолка нет вообще — при росте
поисковики начнут отбрасывать файл целиком. Дополнительно: на каждый заход краулера
поднимается весь каталог в память одним куском.

## Решение

Разбить на шарды по ≤ 10 000 URL, `/sitemap.xml` превратить в **индекс** (`<sitemapindex>`).

### Почему не `generateSitemaps`

Штатный механизм Next (`generateSitemaps` + `/sitemap/[id].xml`) требует перечислить
шарды **на этапе сборки** — а список зависит от количества записей в БД. В Docker-сборке
образа БД недоступна, и весь sitemap намеренно `force-dynamic` (иначе на сборке без
`AUTH_URL` в файл попадает `localhost:3000` — из-за этого уже один раз Яндекс не
подтверждал права, v1.0.58). Городить фолбэк на build-time перечислении — ровно тот класс
«гейты зелёные, прод мёртвый», от которого в репозитории стоят барьеры (`check:routes`,
smoke, libvips). Поэтому шарды — обычные route handlers, целиком request-time.

### Почему `/sitemap.xml` остаётся

Этот адрес уже подтверждён и подан в Яндекс.Вебмастер и Google Search Console
(20.06.2026). Менять его нельзя — он становится индексом, шарды живут отдельно.

## Схема

```
/sitemap.xml                    — <sitemapindex>, ссылки на шарды (request-time COUNT'ы)
/sitemaps/static.xml            — 4 статических маршрута
/sitemaps/artists-{N}.xml       — профили артистов
/sitemaps/releases-{N}.xml      — страницы релизов
/sitemaps/tracks-{N}.xml        — страницы треков
/sitemaps/smartlinks-{N}.xml    — лендинги
/sitemaps/playlists-{N}.xml     — публичные пользовательские плейлисты
```

Каждый шард — одна страница SQL (`LIMIT 10000 OFFSET N*10000`) со стабильным `ORDER BY id`,
поэтому потолок ровный по построению, а не «на глаз».

## Что попадает в выдачу (не меняется)

Инвариант: множество URL совпадает с текущим `sitemap.ts`. Предикаты видимости
переносятся один в один:

- артисты — `is_active` И есть хотя бы один трек в PUBLISHED-релизе (`listActiveArtists`);
- релизы — `PUBLISHED` ИЛИ `SCHEDULED` с наступившей датой (`findPublishedByArtist`),
  и только у видимых артистов;
- треки — все треки этих релизов;
- смартлинки — `is_published`, у видимых артистов;
- плейлисты — `PUBLIC` + `kind='USER'` + непустые (`getSitemapPlaylists`).

`lastModified`/`changeFrequency`/`priority` сохраняются как сейчас.

## Деградация

БД недоступна → индекс отдаёт один `static.xml` (сегодняшнее поведение try/catch:
статические маршруты вместо 500). Шард при ошибке БД отдаёт пустой `<urlset>`, не 5xx:
краулер не должен получать ошибку на подчинённом файле.

## Риски

- Потеря `/sitemap.xml` как `<urlset>` — переезд на индекс поисковики понимают штатно,
  адрес не меняется, повторно подтверждать права не нужно.
- Внутри одного шарда порядок стабилен только пока не меняется набор записей; между
  пересборками возможен сдвиг записи между шардами. Для sitemap это безразлично —
  краулер читает объединение.
