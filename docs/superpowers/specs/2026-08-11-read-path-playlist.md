# Спека: read-path плейлиста (волна 2, шаг 2.5)

**Основание:** `docs/migration-plan.md` §волна 2 · продолжение 2.1–2.4.

## Проблема

Экран `/playlists/[id]` частично через core (`PlaylistService.getForViewer`, `checkInvite`,
`listCollaborators`), но сам собирает состав экрана и добирает данные мимо сервиса:
`getPlaylistWithTracks` в `generateMetadata`, `getPlaylistLikeState`, `getUserProfile` для
имени пригласившего, плюс вычисление роли зрителя (OWNER/COLLABORATOR/VIEWER) прямо в
компоненте. HTTP отдаёт `GET /api/v1/playlists/[id]` → `{ playlist }` — ресурс без роли,
коллабораторов, лайка и приглашения, то есть экран по нему не собрать.

Дополнительно: `generateMetadata` и рендер независимо читают плейлист — два одинаковых
чтения за запрос (та же болезнь, что чинили в 2.2).

## Решение

`PlaylistPageService` в core поверх существующего `PlaylistService` (композиция, не копия
правил доступа) + порт на то, чего у него нет: состояние лайка и имя владельца.

Результат — размеченный по виду экрана:

```
NotFound                                   → 404 / notFound()
{ kind: 'invite', title, ownerUserId }     → экран приглашения (аноним по валидной ссылке)
{ kind: 'playlist', playlist, role, collaborators, liked, invite, inviterName }
```

Два входа: страница вызывает сервис в процессе (через `cache()`-обёртку — она же чинит
двойное чтение), новый `GET /api/v1/playlists/[id]/page` вызывает тот же сервис.
Ресурсный `GET /api/v1/playlists/[id]` не трогаем: у него свой контракт и PATCH/DELETE рядом.

## Правила доступа (переезжают как есть, ни одного нового)

- Видимость и join-токен — только через `PlaylistService.getForViewer(id, viewerId, joinToken)`.
- `role`: владелец → `OWNER`; иначе, если зритель вошёл и плейлист коллаборативный и
  `listCollaborators` разрешён → `COLLABORATOR`; иначе `VIEWER`.
- `collaborators` спрашиваются только когда зритель — владелец или коллаборант.
- `liked` — только для вошедшего не-владельца (владелец лайк-кнопку не видит).
- `inviterName` — только когда экран реально покажет баннер приглашения.
- Аноним с валидным токеном получает `kind: 'invite'` (заголовок и владелец), **без состава
  плейлиста** — это уже действующее правило страницы, теперь оно одинаково для обоих входов.

## Границы

- Разметка, порядок блоков, JSON-LD, OG-картинка не меняются.
- `PlaylistService` не переписывается: `getForViewer`/`checkInvite`/`listCollaborators`
  остаются единственным источником правил доступа.
- Мутации (PATCH/DELETE/треки/коллабораторы/лайк) не трогаем — это write-path.

## Проверка

Гейты core/db/web + contract-тест роута. Сверка «до/после» на четырёх зрителях: владелец,
коллаборант, посторонний вошедший, аноним (в т.ч. с токеном и без) — состав экрана,
видимость лайка и коллабораторов, 404 на приватном.

## Откат

Один revert: страница возвращается к прямым вызовам, роут удаляется.
