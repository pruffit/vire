## 1. Волна ступень 2 — адаптивный алгоритм потока

**Сейчас (ступень 1):** взвешенный SQL — совпадение mood-тегов + близость BPM +
тональность + шум (`packages/db/src/queries/wave.ts`). Без персонализации,
без поведенческих сигналов.

**Куда идём:**
- [ ] Поведенческие сигналы из `play_events`: дослушивания vs скипы
  (`duration_played_sec / duration`), переслушивания (повторные сессии),
  источник запуска. Скип на волне = негативный сигнал к похожим трекам.
- [ ] Профиль вкуса слушателя: агрегат по лайкам, дослушиваниям, mood-тегам
  лайкнутых треков (материализуется по крону, не на лету).
- [ ] Анти-усталость: декей повторов (трек слышали недавно → штраф),
  баланс «знакомое/новое».
- [ ] Учёт любимых моментов (`favorite_moments`) как сильного позитивного сигнала.
- [ ] Деградация: при пустом профиле (аноним/новичок) — текущая ступень 1.

## 2. Автоанализ треков (жанр / настроение / BPM / тональность)

**Сейчас — честно:**
- BPM и тональность НЕ вычисляются: воркер читает их из тегов FLAC-файла
  (`apps/worker/src/lib/metadata.ts`) — есть только если артист прописал их в файле.
- Настроение — ручные теги слушателей (mood-picker), не автоматика.
- Жанра нет вообще (ни поля, ни UI).

**Куда идём:**
- [ ] BPM-детект в воркере (aubio / essentia / собственный onset-анализ по PCM —
  PCM мы уже извлекаем для waveform) — fallback, когда в тегах пусто.
- [ ] Key-детект (chroma-анализ) — тем же пайплайном.
- [ ] Поле `genre` в схеме (enum или таблица) + UI в дашборде; автоопределение
  жанра/настроения — ML-классификатор по аудио (CLAP/MusicNN-класс моделей),
  отдельный этап — потребует GPU или внешнего API, решение отложено.
- [ ] Бэкфилл: прогнать анализ по существующим трекам.

## 3. Безопасность — аудит и доводка

**Сейчас есть:** Auth.js v5 (JWT, httpOnly), роли в `proxy.ts` (/dashboard,
/admin) + `requireAdmin` в server actions, zod-валидация входа на API-роутах,
проверка владения в сервисах (core), FLAC только по presigned URL, YooKassa
webhook верифицируется через API (телу не доверяем), секреты в env, S3-бакеты
разделены (vault приватный / stream публичный), CSRF — внутри Auth.js.

**Дыры, закрыть до 1.0:**
- [ ] Rate limiting на API (login/magic-link, поиск, лайки, upload) — Redis уже есть.
- [ ] Security headers: CSP, X-Frame-Options/frame-ancestors, Referrer-Policy,
  Permissions-Policy (next.config headers()).
- [ ] Лимиты загрузки: максимальный размер FLAC, проверка mime/magic bytes
  (сейчас валидация есть в `lib/upload` — перепроверить серверно).
- [ ] `pnpm audit` в CI + Dependabot/Renovate.
- [ ] Бэкапы Postgres (pg_dump по крону) и стратегия восстановления.
- [ ] Пентест-проход по чек-листу OWASP Top 10 перед продом.

## Справка: ответы на вопросы повестки (состояние на 10.06.2026)

**Как создаётся обратный отсчёт до релиза.** Артист создаёт релиз с датой в
будущем и жмёт «Запланировать» → статус SCHEDULED. Все публичные запросы
показывают SCHEDULED-релизы только когда `release_date <= now()` — т.е. релиз
«открывается» сам, без крона. До этого на странице артиста и главной висит
`CountdownBadge` (клиентский тик раз в секунду до release_date). При публикации
уходит рассылка подписчикам (queue notify-release → Resend).

**Безопасность** — см. блок 3: базовая модель здоровая (роли, валидация,
владение, presigned, верификация вебхуков), до прода нужны rate limiting,
security headers, бэкапы и аудит зависимостей.

**Авто-теги треков** — см. блок 2: сейчас BPM/key только из тегов файла,
mood — от слушателей, жанра нет. Автоанализ — отдельный этап работ.
