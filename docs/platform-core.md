# Platform Core — состав и границы

**Статус:** предложение (Phase 1) · **Основание:** `architecture-audit.md` · `architecture.md`

Документ отвечает на один вопрос: **что именно попадает в Core, что остаётся в домене,
и по какому доказательству принято решение.** Каждое включение обосновано либо тем, что
код уже сейчас не знает о музыке, либо подтверждённой потребностью второго продукта
(реальный план на 3–6 мес).

---

## 1. Критерий включения

Сущность попадает в Core, если выполняется **хотя бы одно**:

- **A. Уже нейтральна.** Код не содержит музыкальных понятий и не изменится при переносе.
  *Пример: `friendship`, `block`, `chat`, `user-directory`.*
- **B. Знает о музыке случайно.** Музыка входит через тип-параметр или значение enum,
  развязка дешёвая и не меняет поведения. *Пример: `notifications` — полиморфные
  `actorId`/`entityId` уже есть, мешает только закрытый enum типов.*
- **C. Второй потребитель подтверждён.** Для VireVideo/VireLearn нужен тот же примитив,
  и это следует из их предметной области, а не из фантазии. *Пример: профиль организации,
  членство, медиа-пайплайн.*

Остаётся в домене, если: единственный use-case **и** обобщение требует придумывать
второго потребителя. Формулировка «когда-нибудь пригодится» — не критерий.

## 2. Состав Core по модулям

### 2.1 `platform/identity` — личность и сессии

**Сейчас:** Auth.js v5, провайдеры email/пароль + Яндекс + magic link. `AuthService` в core
уже нейтрален (регистрация, хеш, установка пароля). Таблицы `users`, `accounts`, `sessions`,
`verification_tokens` — стандартные Auth.js.

**Критерий:** A.

**Целевой контракт:**
```ts
User { id, email, name, avatarUrl?, locale, createdAt }
Session { id, userId, expiresAt }
Device { id, userId, platform, name, lastSeenAt, revokedAt? }   // новое
Credential { userId, provider, providerAccountId }
```

**Что добавляется:** `Device` — под нативные клиенты (Bearer-токены привязываются к
устройству, отзыв по устройству). Основание: `multiplatform.md` §4.

**Что НЕ трогаем:** набор провайдеров — это продуктовое и юридическое решение
(406-ФЗ, Google/Telegram вырезаны). Core даёт механизм, список провайдеров — конфигурация.

**Известное ограничение к исправлению:** роль и identity кладутся в JWT в момент логина,
БД не перечитывается — после смены роли нужен релогин. При введении Core `access/`
это стоит пересмотреть (короткоживущий access-токен снимает проблему естественно).

### 2.2 `platform/access` — роли, права, аудит

**Сейчас — худшее место в системе.** Роль хранится централизованно (`users.role`:
`LISTENER | ARTIST | MODERATOR | ADMIN | SUPERADMIN | VIEWER`), но проверки — inline
`role === 'ADMIN'` в **19 файлах**. Единой `requireRole()`/`can()` нет.

**Три независимых списка admin-ролей уже разошлись** (`proxy.ts`, `admin/system/route.ts`,
`admin/tracks/*` — `VIEWER` то включён, то нет). Плюс `/api/**` исключён из matcher
в `proxy.ts` — единого гейта для 109 роутов нет.

**Критерий:** A (сам механизм) + C (роли внутри организации нужны любому продукту).

**Целевой контракт:**
```ts
type Permission = `${string}:${string}`          // 'release:publish', 'user:role:set'

interface Actor { userId; platformRole; memberships: Array<{ orgId; orgRole }> }

can(actor: Actor, permission: Permission, resource?: { orgId?: string }): boolean
```

Два уровня, оба уже существуют в данных:
- **платформенная роль** — `users.role` (модерация, админка);
- **роль в организации** — `artist_members.role` (уже есть колонка).

**Аудит-лог** вводится здесь же: единый гейт — естественная и единственная точка записи
«кто, что, над чем, когда». Сегодня аудит-логов нет вообще.

**Почему это первая работа программы:** чинит состоявшийся (не гипотетический) дрейф
безопасности, стоит дёшево, ничего не требует от остальной платформы.

### 2.3 `platform/organizations` — организации и членство

**Сейчас:** `artist_profiles` (слаг, имя, bio, аватар, `theme_tokens` JSONB, links, videos,
verified, isActive) + `artist_members` (`user_id ↔ artist_profile_id` + `role`, уникальный
индекс на пару). Дашборд **уже** работает через `innerJoin(artistMembers)`, а не через
прямое владение.

**Критерий:** C — каналу VireVideo и школе VireLearn нужен ровно тот же примитив:
публичный профиль с слагом, аватаром, темой и списком участников с ролями.

**Целевой контракт:**
```ts
Organization {
  id, kind: 'MUSIC_ARTIST' | 'VIDEO_CHANNEL' | 'LEARN_SCHOOL',
  slug, name, bio?, avatarUrl?, themeTokens?, links[], verified, isActive, createdAt
}
OrganizationMember { orgId, userId, role: 'OWNER'|'ADMIN'|'MEMBER', createdAt }
```

**Развилка реализации** (решается в `migration-plan.md`, обе обратимы):

| Вариант | Суть | Плюс | Минус |
|---|---|---|---|
| **A. Переименование** | `artist_profiles` → `organizations` + колонка `kind` | Нет джойна, меньше строк кода | Одна большая миграция, затрагивает всё сразу |
| **B. Расширение** (рекомендую) | Новая `organizations`; `artist_profiles` остаётся с `organization_id` и музыкальными полями | Пошагово, обратимо, чистое разделение Core/Domain | Джойн в запросах, дублирование ключа на время перехода |

Рекомендация — **B**: соответствует требованию обратимости каждого шага. Музыкальные поля
(`rights_holders`, музыкальная специфика профиля) остаются в домене, нейтральные
(`theme_tokens`, `links`, `slug`, `verified`) переезжают в Core.

**Что НЕ вводим:** отдельный `tenant_id`. Организация и есть единица изоляции, пока не
появится клиент с несколькими организациями под одним брендом.

### 2.4 `platform/media` — файлы и обработка

**Сейчас:** всё слито в `track_audio` (1:1 к `tracks`): `hlsManifestKey`, `waveformPeaks`,
`flacKey`, `bpm`, `musicalKey`, `genreSuggestions`. Контракты очередей в `core/src/jobs.ts`
жёстко про трек: `TranscodeJobData { trackId, sourceKey }`.

Хранилище: порт `IFileStorage` существует, но с **одним методом `upload`**; web и worker
держат два независимых S3-клиента.

**Критерий:** C — видео и учебные материалы проходят тот же путь «загрузка → хранилище →
фоновая обработка → готовый ассет», отличаясь только тем, что делает обработчик.

**Граница проходит здесь:**

| Core | Domain (music) |
|---|---|
| `MediaFile` — исходник в хранилище: ключ, размер, MIME, владелец, чексумма | — |
| `MediaAsset` — производный ассет: ключ, вид, статус, метаданные JSONB | `TrackAudio` — bpm, musicalKey, waveformPeaks, genreSuggestions |
| `ProcessingJob` — статус, попытки, ошибка, идемпотентность | конкретный ffmpeg/HLS-конвейер, ONNX-анализ жанра |
| upload policy, presign, delete, CDN-URL | FLAC-специфика, signed FLAC после покупки |

**Целевой контракт очереди** — параметризован по ассету, а не по треку:
```ts
ProcessMediaJobData { assetId, sourceKey, pipeline: string }
```
Имя конвейера (`'audio-hls'`, `'video-hls'`, `'document-pdf'`) выбирает обработчик в воркере.
Само имя очереди уже нейтрально; переделывается payload.

**Что расширяется в `IFileStorage`:** `presign`, `delete`, `stat`, `copy` — сейчас их нет
в порту, поэтому код ходит в S3 SDK мимо абстракции. Два независимых S3-клиента (web и worker)
сводятся к одному.

**Что НЕ обобщаем:** саму нарезку HLS и извлечение пиков — это доменная работа,
у видео она будет другой при том же контракте job'а.

### 2.5 `platform/notifications` — события и доставка

**Сейчас:** три канала работают (email через Brevo HTTP API, web-push VAPID, in-app таблица
`notifications`) + Telegram-алерты через CF Worker. `notifications` уже полиморфна
(`actorId`/`entityId` без FK). `decideExternalDelivery` — чистая функция политики доставки,
полностью нейтральна.

Мешает: `notification_type` — **закрытый enum** с доменными значениями (`JAM_INVITE`,
`PLAYLIST_COLLAB_JOIN`); письма релиза и транскодинга не переиспользуют общий
`email-templates.ts`; сообщение о провале транскодинга захардкожено по-русски мимо i18n.

**Критерий:** B — развязка дешёвая, поведение не меняется.

**Целевой контракт:**
```ts
DomainEvent { name: string, actorId?, orgId?, entityType, entityId, payload, occurredAt }
// 'track.released', 'video.published', 'course.completed'

NotificationChannel = 'email' | 'push' | 'in-app' | 'webhook'
NotificationTemplate { key, locale, subject, body }   // регистрируется продуктом

deliver(event, recipients, policy): результат по каналам
```

Core владеет: реестром событий, политикой доставки (`decideExternalDelivery` переезжает
как есть), подписками и настройками пользователя, ретраями, дебаунсом, локалью получателя
(берётся из БД на момент отправки — существующее правило сохраняется).

Продукт владеет: именами событий и шаблонами.

**Изменение схемы:** `notification_type` из `enum` в `text` + реестр типов на стороне
продукта. Это append-only-совместимо и снимает миграцию БД при каждом новом типе.

### 2.6 `platform/billing` — деньги

**Сейчас:** `purchases` **уже полиморфна** (`itemType`/`itemId`) — ближайшая к готовности
Core-сущность. `IPaymentGateway` абстрагирует YooKassa прилично. `subscriptions.type`
полиморфен по замыслу, но enum содержит `ARTIST_TIER`/`LISTENER_PREMIUM`.
Webhook перезапрашивает платёж из API ЮKassa перед действием — безопасно по конструкции.

**Критерий:** A/B — механизм готов, мешают значения enum и отсутствие модели планов.

**Целевой контракт:**
```ts
Plan { id, productId, code, price, currency, interval, features[] }
Subscription { id, userId|orgId, planId, status, currentPeriodEnd }
Purchase { id, userId, itemType, itemId, amount, currency, status }   // уже так
Entitlement { subjectId, capability, source, expiresAt? }             // новое
```

**`Entitlement` — главное добавление.** Сегодня «что человеку доступно» вычисляется из
покупки/подписки каждый раз по месту. Явная сущность прав даёт: один запрос «может ли»,
общий кэш, и главное — работу через API для клиентов, где вычислять по месту негде.

**Что остаётся в домене:** «покупка трека даёт скачать FLAC» — доменное правило,
формулируется как выдача entitlement, а не как знание Core о треках.

**Открытый хвост:** боевая настройка YooKassa (Этап 2) — от платформенной работы не зависит,
делается по отдельной команде.

### 2.7 `platform/search` — поиск

**Сейчас:** `SearchService` в core, но `SearchResults = { artists, releases, tracks }` —
три жёстко названных поля. Генерическое имя при доменной сути.

**Критерий:** B — механизм нейтрален, мешает форма результата.

**Целевой контракт:**
```ts
SearchHit { kind: string, id, title, subtitle?, imageUrl?, url, score }
SearchQuery { q, kinds?: string[], limit, offset, orgId? }
SearchResult { hits: SearchHit[], total, took }

registerSearchable({ kind, index, project })   // продукт регистрирует свои сущности
```

Группировка по `kind` на стороне потребителя вместо трёх фиксированных массивов.

**Что НЕ вводим:** внешний поисковый движок (Meilisearch/Elastic). На 1 ГБ RAM он не
поместится, а Postgres full-text справляется. Контракт спроектирован так, чтобы замена
реализации не задела потребителей.

### 2.8 `platform/analytics` — события и метрики

**Сейчас:** `play_events` — жёстко про прослушивания, но **уже без FK** на `tracks`
(готовый прецедент мягкой связи). `platform_metrics_daily` — фиксированные музыкальные
колонки (`releases_published`, `tracks_ready`, `playlists_total`), каждый новый продукт
потребовал бы `ALTER TABLE`.

**Критерий:** B/C.

**Целевой контракт:**
```ts
Event { id, name, userId?, orgId?, entityType?, entityId?, props: Json, occurredAt }
MetricPoint { day, productId, metricKey, value }        // вместо колонок
```

`play_events` становится частным случаем `Event` (или остаётся отдельной горячей таблицей
с тем же контрактом сверху — решается по нагрузке; буферизованная запись сохраняется).
`platform_metrics_daily` переходит на `(day, metric_key, value)` — иначе второй продукт
упирается в миграцию схемы.

**Что остаётся в домене:** какие именно события продукт шлёт и как считает свои метрики.

### 2.9 `platform/social` и `platform/messaging`

**Критерий:** A — эти сервисы уже нейтральны, аудит не нашёл в них музыки.

Переезжают как есть: `friendship`, `block`, `report` (уже полиморфный `targetId`),
`user-directory`, `chat`/`conversations`/`messages` (E2EE), `user_identity_keys`,
`push_subscriptions`.

Единственная зацепка — `canSeeLikes` в `friendship`: функция социального графа знает
о видимости лайков. Не блокер (чистая функция от `social_visibility` + статуса дружбы,
типы треков не тянет), но при переносе формулируется как общее правило видимости.

**Открытый хвост, не связанный с платформой:** кросс-девайс линковка ключей E2EE
не докатана — приватный ключ живёт только в IndexedDB клиента.

### 2.10 `platform/content` — посты организации

`ArtistPostService` / `artist_posts` → `OrgPost`. **Критерий:** C — анонсы канала и
объявления курса это тот же примитив.

### 2.11 Полиморфные примитивы взаимодействия

`likes` и `follows` сегодня — жёсткие FK: `likes.track_id → tracks.id`,
`follows.artist_profile_id → artist_profiles.id`.

**Критерий:** C — со вторым продуктом появляется второй тип лайкаемого и второй тип
объекта подписки. Это ровно то доказательство, которого требует правило.

```ts
Reaction { userId, targetType, targetId, kind, createdAt }
Follow    { userId, targetType, targetId, createdAt }
```

Паттерн в кодовой базе уже применён (`purchases.item_id`, `reports.target_id` — uuid без FK,
с комментарием-прецедентом).

**Цена, которую надо принять сознательно:** потеря `ON DELETE CASCADE`. При удалении трека
или артиста уборка реакций/подписок становится ручной — либо фоновой задачей, либо явным
шагом в доменном сервисе удаления. Это единственный настоящий минус, и он не отменяется
никакой хитростью.

## 3. Что сознательно остаётся в домене

Перечислено явно, чтобы к этому не возвращались:

| Сущность | Выглядит общей | Почему остаётся |
|---|---|---|
| **Плейлисты** | «Коллекция сущностей с совместным доступом» | Коллаборация, приглашения и порядок плотно завязаны на доменную модель. Даже у VireVideo плейлист будет другим по правилам. Обобщать нечем подтвердить |
| **Смартлинки** | «Link-in-bio для креатора» | Один use-case, внутри `release_id`. Кандидат на будущее, не сейчас |
| **Волна** | «Алгоритмическая лента» | BPM, тональность, Camelot, mood — чистая музыка |
| **Джем** | «Live-сессия с участниками» | Watch-party VireVideo — правдоподобный второй потребитель, но его нет. Пометить, не двигать |
| **`jam-sync`** | Коррекция дрейфа часов — генерический алгоритм | Второго потребителя нет. Пометить |
| **Пресейвы** | — | Специфика музыкальной индустрии |
| **Любимые моменты** | «Маркеры на таймлайне» | Правдоподобно для видео, но реализация про waveform. Пометить |
| **`authorize-track`** | «Проверка владения ресурсом» | Паттерн общий, но обобщается сам собой при введении `can()` в §2.2 — отдельной работы не требует |

Помеченные («пометить, не двигать») фиксируются в коде комментарием в одну строку
в месте определения — не в отдельном реестре, который устареет.

## 4. Admin Framework

Требование заказчика — «explicit configuration over magic», и оно верное. Generic CRUD
с автогенерацией форм по схеме здесь не нужен: админка уже написана, работает и
задизайнена (v1.4.x, единый `ui-kit.tsx` на 25 компонентов).

**Что реально переиспользуемо:**
- примитивы таблиц/панелей/бейджей — переезжают в `packages/ui` (см. `multiplatform.md` §6);
- **Core-разделы админки** — пользователи, роли, организации, биллинг, медиа, аудит-лог,
  настройки — как готовые экраны Core, подключаемые продуктом;
- **доменные разделы** — артисты, треки, релизы — пишет продукт.

Механизм подключения — явная регистрация разделов списком, а не магический автообход
сущностей:
```ts
adminSections = [ ...coreSections, artistsSection, tracksSection, releasesSection ]
```

`/admin` не локализуется — это статус-кво и осознанное решение (backoffice), сохраняется.

## 5. Feature flags и конфигурация

**Сейчас:** флагов нет вообще; валидации env нет (ни zod, ни t3-env); `NEXT_PUBLIC_*`,
CSP и `images.remotePatterns` пекутся в образ на build-time.

**Вводится в Core:**
```ts
isEnabled(flag: string, ctx: { userId?, orgId?, productId }): boolean
```
Источник — БД + кэш, не env. Основание: флаги нужны SDUI (§14 задания — персонализация,
A/B) и нужны для безопасной раскатки самой миграции (см. `migration-plan.md` — переключение
страницы на новый read-сервис прячется за флаг).

**Валидация env через zod на старте процесса** — дешёвая работа с реальной отдачей:
сегодня отсутствующая переменная проявляется рантайм-ошибкой в проде, а это ровно тот класс
багов, который уже один раз ронял прод.

**Build-time запекание** — отдельная задача, полезная сама по себе (белый лейбл упирается
именно в неё: один образ = один бренд).

## 6. Порядок выделения

Ранжировано по отношению «ценность / риск», не по красоте:

| # | Модуль | Почему сейчас | Риск |
|---|---|---|---|
| 1 | `access` (RBAC + аудит) | Чинит состоявшийся дрейф трёх списков ролей | Низкий — чистое добавление |
| 2 | Read-сервисы (не модуль, а разблокировка всего) | Главный блокер `Б1` | Средний — по одному ресурсу |
| 3 | `identity` + Device/Bearer | Без этого API бесполезен клиентам | Средний |
| 4 | `media` (порт хранилища + `MediaAsset`) | Два S3-клиента, порт из одного метода | Средний |
| 5 | `notifications` (enum → text, реестр событий) | Дёшево, снимает миграцию на каждый тип | Низкий |
| 6 | `organizations` | Самая крупная миграция данных | **Высокий** — делать после 1–5 |
| 7 | `analytics`, `search`, `billing` | Контракты, реализация по мере надобности | Низкий |
| 8 | Полиморфные `likes`/`follows` | Только когда появится второй тип сущности | Средний — потеря CASCADE |
