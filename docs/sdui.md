# Server-Driven UI — протокол и границы

**Статус:** предложение (Phase 1) · **Основание:** `architecture-audit.md` §8

SDUI отвечает за **композицию экрана**: какие блоки, в каком порядке, с какой конфигурацией.
Ничего больше. Это сознательно узкая роль — см. §7.

---

## 1. Почему главная страница, и почему только она

Аудит показал: `app/[locale]/page.tsx` **уже является** SDUI-экраном по структуре, просто
описанным в JSX вместо данных. Двенадцать независимых async Server Component блоков,
каждый со своим фетчем, каждый в собственном `<Suspense>` со скелетоном:

```
FeaturedRelease → FlowBlock → PersonalBlock → FeedSection → FriendsActivitySection →
HotTracksSection → FreshReleasesSection → UpcomingSection → ListeningNowSection →
PlaylistsSection → ArtistsSection → DiscoverySection
```

Порядок — это порядок строк в `page.tsx:37-115`. Никакой блок не знает о соседях.
Ни один не делится состоянием с другим.

Иными словами: **вся тяжёлая часть SDUI уже сделана** — декомпозиция экрана на
самодостаточные блоки с независимой загрузкой. Осталось вынести порядок и конфигурацию
в данные.

Остальные экраны — плохие кандидаты, и это разобрано в `architecture-audit.md` §8:
страница релиза/трека (плеер и трек-лист связаны состоянием), формы дашборда
(`track-manager` — 547 строк), джем и чат (SSE-realtime), авторизация, админка.
Их SDUI не касается ни сейчас, ни потом.

---

## 2. Модель: сервер даёт композицию, блок сам берёт данные

Две крайности, обе плохие:

- **Только разметка.** Сервер шлёт список блоков, клиент сам знает, где брать данные →
  клиент снова знает бизнес-правила, и мобильный повторяет логику веба. Не годится.
- **Полностью гидрированный ответ.** Сервер шлёт блоки вместе со всеми данными →
  один жирный запрос, потеря стриминга RSC на вебе (сегодня главная отдаётся по частям
  через Suspense), деградация TTFB на одном небольшом VPS. Не годится.

**Решение — блок объявляет свой источник данных контрактом:**

```
GET /api/v1/screens/home
   ↓
{ blocks: [ { type, id, props, source: { endpoint, params } }, … ] }
   ↓
Web:    RSC-блок вызывает read-сервис в процессе (как сегодня, стриминг сохраняется)
Mobile: рендерер дёргает source.endpoint параллельно, по блоку на запрос
```

Один и тот же дескриптор описывает, **что** показать и **откуда взять**; способ доставки
данных — свойство платформы. Это прямое следствие правила «одна реализация, два входа»
из `architecture.md` §4.

Для мелких блоков предусмотрен `inline` — данные приходят сразу в дескрипторе, чтобы не
плодить запросы ради трёх полей:

```ts
source: { kind: 'inline', data: {...} } | { kind: 'endpoint', endpoint: string, params?: … }
```

## 3. Типизированный протокол

```ts
// packages/sdui — появляется, когда в него переезжает работающий код (architecture.md §2)

interface Screen {
  screen: string;              // 'home'
  version: number;             // версия схемы экрана
  revision: string;            // хеш композиции — для кэша и аналитики
  blocks: Block[];
}

interface BlockBase {
  id: string;                  // стабильный ключ: React key, ключ аналитики, якорь A/B
  type: string;                // ключ реестра рендереров
  source?: DataSource;
}

type DataSource =
  | { kind: 'inline'; data: unknown }
  | { kind: 'endpoint'; endpoint: string; params?: Record<string, string | number> };
```

Блоки — размеченное объединение, `props` строго типизированы под тип:

```ts
type Block =
  | { type: 'featured-release';  id: string; source: DataSource; props: { autoplay?: boolean } }
  | { type: 'flow';              id: string; source: DataSource; props: { chips: string[] } }
  | { type: 'release-grid';      id: string; source: DataSource;
      props: { title: string; limit: number; layout: 'grid' | 'row'; showMore?: boolean } }
  | { type: 'artist-carousel';   id: string; source: DataSource; props: { title: string } }
  | { type: 'track-list';        id: string; source: DataSource;
      props: { title: string; numbered?: boolean } }
  | { type: 'playlist-row';      id: string; source: DataSource; props: { title: string } }
  | { type: 'feed';              id: string; source: DataSource; props: { title: string } }
  | { type: 'friends-activity';  id: string; source: DataSource; props: { title: string } }
  | { type: 'listening-now';     id: string; source: DataSource; props: Record<string, never> }
  | { type: 'banner';            id: string; source: DataSource;
      props: { tone: 'info' | 'promo'; dismissible: boolean } };
```

Источник правды — zod-схемы в `@vire/api-contracts`, типы выводятся через `z.infer`
(как принято в проекте). Отсюда же генерируется JSON Schema для нативных клиентов.

**Правило `props`:** только представление — заголовок, лимит, раскладка, тон.
Ни идентификаторов пользователя, ни правил, ни условий. Всё, что похоже на «если…, то…»,
на клиент не попадает (§4).

## 4. Персонализация решается на сервере целиком

Клиент **никогда** не получает правила — только результат:

```
запрос → actor (кто) + product + client capabilities
       → флаги, A/B-корзина, профиль вкуса, подписки, время суток
       → отбор и порядок блоков
       → готовый список
```

Клиент не знает, что был A/B-тест. Не знает про флаги. Не вычисляет видимость.
Это отличает SDUI от «правил на клиенте» и делает поведение одинаковым на вебе, iOS
и Android без синхронизации версий приложений.

Побочный эффект, ценный сам по себе: порядок секций главной становится **изменяемым
без релиза** — в том числе для мобильного приложения, которое иначе ждало бы ревью в сторе.

---

## 5. Совместимость версий — главный риск SDUI

Веб обновляется мгновенно, мобильное приложение — нет. Через полгода будут работать
клиенты, не знающие половины типов блоков. Без защиты это гарантированный краш или
пустой экран.

Две меры, обе обязательные:

**1. Сервер знает возможности клиента.** Клиент присылает, что умеет рендерить:
```
X-Vire-Client: ios/2.3.0
X-Vire-Blocks: featured-release,release-grid,artist-carousel,track-list
```
Сервер **не отправляет** типы, которых клиент не понимает. Основной механизм.

**2. Клиент молча пропускает незнакомое.** Неизвестный `type` → блок не рендерится,
факт уходит в аналитику. Страховка на случай рассинхронизации.

**Правила эволюции протокола:**

| Изменение | Можно | Как |
|---|---|---|
| Новый тип блока | да | Старые клиенты его не получают (мера 1) |
| Новое необязательное поле `props` | да | Старые игнорируют |
| Новое обязательное поле | нет | Только через новый тип блока |
| Удаление типа | да, отложенно | Сначала перестать отдавать, удалить рендерер после спада доли старых клиентов |
| Смена смысла поля | **никогда** | Новое поле, старое устаревает |

## 6. Реестр рендереров — по одному на платформу

Общий контракт, платформенная реализация. Ровно то, что задано в `multiplatform.md`:
один визуальный UI на все платформы **не** делается.

```ts
// web
const registry = {
  'featured-release': FeaturedRelease,
  'release-grid':     ReleaseGrid,
  'artist-carousel':  ArtistCarousel,
  'track-list':       TrackList,
  …
} satisfies BlockRegistry;
```

Веб-рендерер — тонкий: он сохраняет текущее поведение страницы, включая `<Suspense>`
и скелетоны, потому что блоки остаются теми же компонентами, что сейчас. Меняется только
источник порядка.

```tsx
{screen.blocks.map(block => {
  const Component = registry[block.type];
  if (!Component) return null;              // мера 2
  return (
    <Suspense key={block.id} fallback={skeletonFor(block.type)}>
      <Component {...block.props} source={block.source} />
    </Suspense>
  );
})}
```

iOS/Android получают свои реестры с нативными вью под те же типы.

## 7. Чего SDUI не делает — жёстко

Соответствует ограничению из задания (§14) и расширено по итогам аудита:

| Запрещено | Почему |
|---|---|
| Произвольный JS, `eval`, выражения в схеме | Дыра в безопасности и конец типизации. Мобильные сторы это отдельно не любят |
| Бизнес-логика и правила | Правила живут в `@vire/core`. Иначе они разъедутся между клиентами |
| Состояние приложения | Плеер, очередь, авторизация, черновики форм — вне SDUI |
| Логика плеера | Явно исключено заданием. Плеер — платформенный компонент с общим ядром (`multiplatform.md` §5) |
| Авторизация и её экраны | Безопасность не конфигурируется удалённо |
| Сложные формы целиком | `track-manager` — 547 строк. Форма это состояние и валидация, а не композиция |
| Навигация и роутинг | Остаётся платформенным |
| Стили и произвольный CSS | Только токены и заранее известные варианты. Иначе SDUI превращается в удалённый рендеринг |

Проверка на здравость: **если блок нельзя нарисовать, зная только `type` + `props` +
данные из `source` — он не блок.**

## 8. Безопасность

- Схема ответа валидируется **на сервере перед отправкой** — сломанная композиция не
  доезжает до клиента.
- Клиент валидирует входящий JSON той же zod-схемой; провал → фолбэк на статическую
  композицию, а не пустой экран.
- `endpoint` в `source` — **не произвольный URL**, а значение из закрытого списка
  известных эндпоинтов. Иначе SDUI становится SSRF-примитивом и каналом утечки токена
  на чужой хост.
- Ответ персонализирован → `Cache-Control: private`; общий кэш только для анонимной
  композиции.
- `props` не содержат идентификаторов третьих лиц и ничего, что не должно быть видно
  пользователю: дескриптор экрана виден в DevTools и в перехваченном трафике.

## 9. Тестирование

| Уровень | Что проверяется |
|---|---|
| Схема | Каждый пример композиции парсится zod-схемой; неизвестные поля не ломают разбор |
| Реестр | Для каждого типа из объединения существует рендерер (тест падает при добавлении типа без компонента) |
| Совместимость | Клиент со списком типов N-1 версии не получает новых типов и не падает |
| Композиция | Персонализация детерминирована при фиксированных входах (флаги, корзина A/B, профиль) |
| Снапшот | Композиция главной для гостя / слушателя / артиста стабильна |
| Визуально | Существующие тесты страницы продолжают проходить — блоки те же компоненты |

Отдельно сохраняется инвариант оболочки: `app/__tests__/layout-shell.test.ts` (запрет
`min-h-screen`, запрет `fill: both/forwards` на конечных анимациях). SDUI не должен
дать способ обойти его через `props` — поэтому раскладочные значения только из
перечислений, никогда не свободная строка класса.

## 10. Раскатка

Строго за флагом, с мгновенным откатом:

1. `GET /api/v1/screens/home` отдаёт композицию, **повторяющую текущий порядок один в один**.
2. Главная рендерит через реестр — при выключенном флаге остаётся текущий JSX.
   Оба пути живут рядом.
3. Сверка: одинаковый набор и порядок блоков, одинаковые скелетоны, нет регресса TTFB
   и композитных слоёв (проверка слоёв через CDP `LayerTree` — существующее требование
   к скролл-области).
4. Включение флага для части аудитории, затем на всех.
5. Удаление статической ветки — **только после** того, как мобильный клиент подтвердит
   протокол на практике. До тех пор запасной путь остаётся.

**Откат:** выключить флаг. Никаких миграций БД, никаких необратимых шагов —
поэтому SDUI и стоит делать после фундамента, но раньше мобильного клиента.

## 11. Что появится в репозитории

| Путь | Содержимое |
|---|---|
| `packages/api-contracts/src/sdui.ts` | zod-схемы `Screen`, `Block`, `DataSource` |
| `packages/core/src/platform/sdui/` | сборка композиции: флаги, A/B, персонализация |
| `apps/web/app/api/v1/screens/home/route.ts` | эндпоинт композиции |
| `apps/web/components/sdui/` | реестр и рендерер |
| `apps/web/lib/feature-flags.ts` | флаг раскатки (из `platform/config`) |

Отдельный пакет `packages/sdui` — **только когда** появится второй потребитель рендерера
(мобильный клиент или второй продукт). До тех пор границы держит директория,
по правилу `architecture.md` §2.
