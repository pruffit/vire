Цель аудита — установить фактическое состояние репозитория перед решением о выделении
переиспользуемого Platform Core, введении SDUI и подготовке к нативным клиентам.
Документ фиксирует **что есть**, а не что хотелось бы. Целевая архитектура — `architecture.md`,
путь миграции — `migration-plan.md`.

## 1. Главный вывод

**Проблема проекта — не в недостатке абстракций. Проблема в том, что больше половины
пользовательского пути не проходит через HTTP вообще.**

27 из 53 страниц читают базу напрямую в Server Components, минуя и `packages/core`, и API.
Главная страница, каталог артистов, каталог релизов, лента, страница плейлиста, обзор
дашборда — у всего этого **нет HTTP-эндпоинта**. Не «плохой эндпоинт», а никакого.

Это означает конкретную вещь: мобильному клиенту сегодня нечего вызывать, чтобы показать
хотя бы главный экран. И никакая перестановка пакетов этого не меняет — read-путь придётся
строить заново независимо от того, как называются директории.

При этом слой, который обычно оказывается грязным, здесь чист: `packages/core` не импортирует
ни Next, ни React, ни `@vire/db`; `Result<T,E>` и инъекция эффектов соблюдены не декларативно,
а фактически. Это редкость и это капитал.

**Отсюда приоритет: API-first для чтения — раньше, чем выделение Core.** Выделение Core без
HTTP-поверхности даст красивое дерево директорий и ноль новой возможности.

## 3. Фактическая карта архитектуры

Заявленная в `CLAUDE.md` схема — `Route → Service (core) → Repository (db) → Postgres`.
Фактически путей два, и второй нигде не описан:

```
ЗАПИСЬ (соответствует заявленному):
  Route Handler → Service (packages/core) → Repository (packages/db) → Postgres

ЧТЕНИЕ (не описано, но это основной путь):
  Server Component → функция из packages/db/src/queries/*.ts → Postgres
```

`packages/db/src/queries` — **48 файлов, 7152 строки, ~150 экспортируемых функций,
используемых в 113 файлах `apps/web`**. У этого слоя нет соответствия в core вообще.
Именно там физически живёт бизнес-логика чтения: агрегации, ранжирование, фильтры видимости,
джойны популярности.

Показательный контраст в одной фиче: `followArtist`/`unfollowArtist` идут через `FollowService`
по всем правилам, а `getFollowState`/`getFollowerCount` вызываются из страницы артиста напрямую
из `@vire/db`.

Это не «нарушение» — правило про чтения просто никогда не формулировалось. Но последствие
реальное: **вынести core в переиспользуемый пакет ≠ вынести бизнес-логику**, потому что
половина её не в core.

## 4. Классификация: Core / Domain / Borderline

Применено правило «Abstract after evidence»: в Core попадает только то, что уже сейчас
не знает о музыке, либо знает о ней случайно и дёшево развязывается.

### 4.1 Сервисы (29 файлов)

**CORE-CANDIDATE (10)** — `auth`, `block`, `chat`, `friendship`, `notification`, `purchase`,
`report`, `user-directory`, `external-delivery` (политика доставки уведомлений — чистая
функция без музыки), `jam-code` (генератор кода комнаты).

**DOMAIN (14)** — `release`, `track`, `track-moods`, `wave`, `wave-scoring`, `musical-key`,
`listener-track` (любимые моменты на waveform), `presave`, `authorize-track`,
`external-resolve` (×2), `jam`, `jam-queue`, `jam-mode`.

**BORDERLINE (9)** — разобраны ниже, потому что именно они определяют, где пройдёт граница.

### 4.2 Разбор пограничных случаев

| Сущность | Почему на границе | Решение и обоснование |
|---|---|---|
| `ArtistService` / `artist_profiles` | Это фактически «профиль организации/креатора»: слаг, аватар, bio, тема, ссылки, видео. Каналу VireVideo и школе VireLearn нужен ровно тот же примитив | **В Core** как `OrgProfile`. Доказательство не гипотетическое: `theme_tokens`, `links`, `videos` уже JSONB и уже продуктово-нейтральны |
| `artist_members` | Join-таблица `user_id ↔ artist_profile_id` с колонкой `role` | **В Core** как `organization_members`. Самая обнадёживающая находка аудита — см. §5.1 |
| `ArtistPostService` | «Пост от лица организации» — общий контент-примитив | **В Core** как `OrgPost`, доменные поля (если появятся) — расширением |
| `FollowService` / `follows` | Подписка как примитив генерическая, но код завязан на `artistSlug` и FK на `artist_profiles` | **В Core**, но требует полиморфизации (см. §6, блокер Б2) |
| `PlaylistService` / `playlists` | «Коллекция сущностей с совместным доступом» — генерическая идея, реализация про треки | **Оставить в Domain** до второго use-case. Коллаборация/приглашения — сложная часть — сильно завязана на доменную модель, обобщать сейчас нечем подтвердить |
| `SearchService` | Генерическое имя вводит в заблуждение: `SearchResults = {artists, releases, tracks}` — три жёстко названных поля | **Core-механизм + Domain-типы**: `SearchHit {kind, id, title, subtitle, imageUrl, url}` в Core, регистрация индексируемых сущностей — в продукте |
| `SmartLinkService` | «Link-in-bio для креатора» — общий паттерн, но внутри `releaseId` | **Оставить в Domain.** Один use-case, обобщать преждевременно |
| `feed-ranking`, `discovery-scoring` | Математика (насыщение, квоты на источник против доминирования) переиспользуема; входы музыкальные | **Утилиты насыщения — в Core** (см. §6, находка о трёх параллельных реализациях), скоринг целиком — в Domain |
| `jam-sync` | Коррекция дрейфа часов — генерический алгоритм, применим к watch-party | Пометить как будущий Core, **сейчас оставить**. Второго потребителя нет |

### 4.3 Таблицы (~40)

CORE-CANDIDATE ~14 · DOMAIN ~15 · BORDERLINE ~11.

Готовые к Core без переделки: `users`, `accounts`, `sessions`, `verification_tokens`,
`notifications` (уже полиморфна — `actorId`/`entityId` без FK), `purchases` (уже полиморфна —
`itemType`/`itemId`), `reports` (полиморфный `targetId`), `friendships`, `user_blocks`,
`conversations`, `messages`, `push_subscriptions`, `user_identity_keys`, `artist_members`.

## 5. Что оказалось лучше ожидаемого

### 5.1 Модель членства уже почти изоморфна платформенной

`artist_members` — таблица `user_id ↔ artist_profile_id` + `role`, уникальный индекс на пару.
Дашборд артиста **уже сейчас** работает через `innerJoin(artistMembers)`, а не через прямое
владение профилем.

То есть переход `user → artist_profile` ⟶ `user → membership → organization` — это
переименование и добавление discriminator-колонки, а не проектирование модели с нуля.
Для затеи с Platform Core это самая ценная находка: самая дорогая обычно часть уже сделана.

### 5.2 `packages/core` чист фактически, а не на словах

Проверено grep'ом, а не по декларации:
- импортов `next`, `react`, `next-auth`, `@vire/db` — **ноль**;
- `new Date()` без аргумента в непроверочном коде — **ноль** (везде инъектированный `Clock`);
- `Math.random()` — ноль (в `jam-code` random приходит параметром);
- `fetch` — только за портом `IPageMetaFetcher`;
- Drizzle-типы в сигнатуры core не протекают — репозитории мапят строки в чистые POJO.

Единственный эффект — `node:crypto` в `util/signing.ts`, с объяснением про Edge runtime.

### 5.3 Границы core↔db соблюдены 1:1

21 интерфейс в `core/src/repositories` ↔ 21 реализация в `db/src/repositories`, каждая
`implements`. Репозиториев-сирот нет.

### 5.4 Паттерн полиморфизма в кодовой базе уже есть

`purchases.itemId` и `reports.targetId` — uuid без FK, с явным комментарием-прецедентом.
`play_events.trackId` тоже объявлен без `.references()`. То есть разрыв жёстких FK ради
модульности — уже принятое в проекте решение, просто применённое не везде.

### 5.5 Главная страница структурно уже является SDUI-экраном

`home-sections.tsx` + `page.tsx` — это буквально последовательность из 12 независимых
async Server Component блоков, каждый сам фетчит данные, каждый в своём `<Suspense>`
со скелетоном: `FeaturedRelease → FlowBlock → PersonalBlock → FeedSection →
FriendsActivitySection → HotTracksSection → FreshReleasesSection → UpcomingSection →
ListeningNowSection → PlaylistsSection → ArtistsSection → DiscoverySection`.

Порядок — просто порядок JSX-строк. Превратить в данные — дёшево.

### 5.6 Единый UI-кит уже существует (вопреки первому впечатлению)

`components/admin/ui.tsx` — это `export * from '../ui-kit'`. Админка и дашборд артиста уже
сидят на общем `components/ui-kit.tsx` (25 экспортов, 654 строки). Отдельного дизайн-кита
админки нет — эта работа уже сделана в v1.4.x.

## 6. Блокеры выделения Platform Core

Ранжировано по стоимости бездействия.

### Б1. Read-путь вне HTTP — критический

27/53 страниц читают БД напрямую. Нет эндпоинтов: `GET /v1/artists` (список),
`GET /v1/releases` (список), `GET /v1/feed`, обзор дашборда.

Отдельная деталь: `/v1/artists/[slug]` и `/v1/releases/[releaseId]` **существуют и построены
правильно, через core — но страницы их не используют**, дублируя логику своими прямыми
запросами. То есть в двух местах есть две реализации одного чтения, и «правильная» —
фактически мёртвый код.

*Стоимость бездействия:* мобильный клиент невозможен. *Развязка:* дорого, но это и есть
основная работа.

### Б2. Жёсткие FK у кандидатов в Core-примитивы

- `likes.trackId` → `tracks.id` (NOT NULL)
- `playlist_tracks.trackId` → `tracks.id` (NOT NULL)
- `follows.artist_profile_id` → `artist_profiles.id` (NOT NULL)

«Реакция», «элемент коллекции», «подписка» — общие примитивы, прибитые к музыкальным таблицам.
Паттерн разрыва в кодовой базе есть (см. §5.4). *Цена:* потеря `ON DELETE CASCADE`, нужен
ручной cleanup. Это осознанный размен, а не техническое препятствие.

### Б3. Доменные значения в закрытых enum'ах Core-таблиц

- `notification_type` содержит `JAM_INVITE`, `PLAYLIST_COLLAB_JOIN`
- `subscription_type` содержит `ARTIST_TIER`, `LISTENER_PREMIUM`
- `platform_metrics_daily` — фиксированные колонки `releases_published`, `tracks_ready`,
  `playlists_total`

Каждый новый продукт = миграция БД. Для метрик — `ALTER TABLE` вместо EAV-схемы
`(day, metric_key, value)`.

### Б4. RBAC размазан по 19 файлам

Роль хранится централизованно (`users.role`), но проверки — inline `role === 'ADMIN'` в
каждом route handler. Единой `requireRole()`/`can()` нет.

**Три независимых списка admin-ролей уже разошлись** (`proxy.ts`, `admin/system/route.ts`,
`admin/tracks/*` — `VIEWER` то включён, то нет). Это не гипотетический риск дрейфа, это
состоявшийся дрейф.

Плюс: `/api/**` целиком исключён из matcher в `proxy.ts` — единого гейта авторизации для API
нет, каждый из 109 роутов отвечает за себя сам.

### Б5. Контракты не централизованы

`packages/api-contracts` покрывает ~4 эндпоинта. Реальная валидация — 48 route-level
zod-схем, разбросанных по `app/api/v1/**`. Мобильному клиенту неоткуда импортировать
контракты одним пакетом.

Дополнительно: core-типы используют `Date` в полях. Для JSON это не блокер (`toJSON` даёт ISO),
но как типизированный контракт для клиента они не годятся без явного DTO-маппинга.

### Б6. Аутентификация только cookie-based

Auth.js JWT в httpOnly cookie. Для нативного клиента нужен Bearer-обмен: access/refresh,
привязка устройства. `auth()` используется в 60+ файлах — потребуется общий адаптер.

Хороший задел: HMAC-подписанные сессии для гостей в джем-комнатах (`lib/session-signing.ts`) —
готовый шаблон токена, просто применён к одному домену.

### Б7. Build-time запекание конфигурации — блокер white-label

`NEXT_PUBLIC_*`, CSP и `images.remotePatterns` пекутся в Docker-образ на этапе сборки через
build-args. **Один образ = один бренд.** Смена темы/домена тенанта требует пересборки образа.

Плюс: feature flags отсутствуют полностью, валидации env (zod/t3-env) нет.

### Б8. Бизнес-логика, запертая в `apps/web`

- `lib/player/queue.ts` — 100% чистые функции (Fisher-Yates, shuffle on/off, окно персиста,
  edge-case repeat=all на одном треке). Мобильный клиент либо скопирует, либо переизобретёт
  и разойдётся багами. **Перенести дёшево.**
- `lib/wave-session.ts` — Redis-политика анти-повтора волны (TTL, лимиты).
- `lib/format.ts` — форматтеры централизованы, но не в переносимом пакете.
- Три параллельные реализации «насыщения сигнала» (`discovery-scoring`, `feed-ranking`,
  `wave-scoring`) — разный код, одна идея.

## 7. Безопасность и мультитенантность

| Область | Состояние |
|---|---|
| Rate limiting | Redis fixed-window, переживает несколько инстансов. Fail-open при недоступности Redis — осознанный размен, стоит зафиксировать явно. Покрывает 36/109 роутов |
| Валидация входа | zod в 48/109 роутов |
| Авторизация | Ownership-проверки в core — чисто. Ролевые — размазаны (Б4) |
| CORS | Не настроен вообще. Для нативного клиента не проблема (CORS браузерный), но веб-фронт на другом домене сегодня невозможен |
| CSRF | Не проверено построчно — низкая уверенность, требует отдельного прохода |
| Webhook YooKassa | Подпись тела не проверяется, но платёж перезапрашивается из API ЮKassa перед действием — безопасно по конструкции |
| Секреты | `LINK_SIGNING_SECRET` фоллбечит на `AUTH_SECRET` — переиспользование секрета, средняя серьёзность |
| E2EE | Приватный ключ только в IndexedDB клиента; кросс-девайс линковка (SAS-код) не докатана |
| **Tenant isolation** | **Отсутствует полностью** |
| **Audit logs** | **Отсутствуют полностью** |
| Документация | `docs/security/owasp-top-10.md` устарел в A09 — всё ещё пишет «план: Sentry», хотя Sentry вырезан |

Не проверены на IDOR: `playlists/[id]/collaborators/*`, `chat/*` (проверка участия в
разговоре), `friends/[userId]` DELETE. Требуют прицельного прохода.

## 8. Готовность к SDUI

| Экран | Вердикт | Обоснование |
|---|---|---|
| **Главная** | **Отличный кандидат** | Уже 12 независимых блоков, каждый со своим фетчем и Suspense. Порядок захардкожен в `page.tsx:37-115` |
| Лента, каталоги артистов/релизов | Средний | Блочность есть, но слабее выражена |
| Страница артиста | Средний | Секции менее независимы друг от друга |
| Страница релиза/трека | **Плохой** | Плеер и трек-лист тесно связаны состоянием |
| Плеер | **Плохой** | Состояние, транспорт, синхронизация — не композиция |
| Формы дашборда | **Плохой** | `edit-release-form` 162 строки, `track-manager` 547, `track-edit-form` 410 — сложные формы явно вне SDUI по вашему же ограничению |
| Джем, чат | **Плохой** | SSE-realtime, состояние |
| Авторизация, админка | **Плохой** | По вашему ограничению и по здравому смыслу |

Вывод: SDUI оправдан ровно на одном экране сейчас — главной. И там он оправдан хорошо,
потому что персонализация/порядок блоков — реальная продуктовая потребность, а не
архитектурное упражнение.

## 9. Инфраструктурное ограничение — определяющее

**Прод (на момент аудита): один VPS Timeweb, 1 ГБ RAM, 6 контейнеров.** Postgres уже подрезан
(`shared_buffers=96MB`). Sentry/GlitchTip уже вырезаны, потому что не влезли.
`lockDuration` воркеров поднят из-за риска потери лока под ONNX-инференсом.

Отсюда трезвый вывод, который надо принять до проектирования:

> **Platform Core как отдельно деплоящийся сервис на текущем железе невозможен.**
> Любой дополнительный постоянный процесс — отдельный API-сервис, второй backend,
> поисковый движок — физически не поместится.

Core может быть **набором пакетов, собираемых в тот же образ**. Не сервисом.
Это не ограничивает переиспользование кода, но закрывает вариант «Core как платформа,
к которой подключаются продукты по сети» — до апгрейда VPS.

**CI/CD:** гейты общие и переиспользуемые, но path-фильтрации по изменённым пакетам нет —
каждый прогон гоняет весь монорепо. `deploy.yml` жёстко перечисляет web/worker без
параметризации: третий продукт = копипаста всего блока build-push-deploy.

## 10. Оценка предложенной структуры — прямо

Вы предложили ~16 пакетов и директорию `products/`. **Не рекомендую внедрять сейчас**, и вот
доказательство из вашего же репозитория, а не из общих соображений:

- `packages/ui` создан заранее — за всё время в нём накопилось **2 компонента**, при том
  что реальный UI-кит на 25 экспортов вырос в `apps/web/components/ui-kit.tsx`.
- `packages/api-contracts` создан заранее — в нём **3 файла**, при том что реальных
  контрактов 48, и все они выросли в route handlers.
- `packages/media` — **пуст**.

Три пустых пакета из восьми. Пустой пакет не притягивает код — код растёт там, где его пишут.
Создать ещё 16 пустых директорий значит воспроизвести ту же ошибку в большем масштабе.

**Что предлагаю вместо:** двигать границы по факту извлечения. Пакет появляется в тот момент,
когда в него переезжает работающий код, а не заранее под будущего жильца. `products/` не
нужен, пока продукт один — сегодня он добавит уровень вложенности и сломает пути импортов
без единого выигрыша.

Аналогично про **Product Manifest** (§15 вашего задания) и **white-label** (§16): манифест
уменьшает связность только когда есть два продукта, которые по-разному собирают модули.
С одним продуктом это конфиг, описывающий сам себя. White-label упирается в Б7 (build-time
запекание) — это надо чинить, но как инженерную задачу конфигурации, а не как
мультитенантную архитектуру, которой негде развернуться на тогдашнем 1 ГБ.

**Что поддерживаю без оговорок:** API-first для чтения, централизация контрактов, Bearer-auth,
единый RBAC-гейт, вынос чистой логики плеера, SDUI на главной, экспорт дизайн-токенов.
Всё это оправдано потребностями самого VireMusic — второй продукт для их обоснования
не требуется.

## 11. Порядок работ, вытекающий из аудита

Ранжировано по отношению «ценность / риск», а не по красоте архитектуры:

1. **Единый RBAC-гейт** — чинит состоявшийся дрейф трёх списков ролей. Дёшево, снижает риск
   безопасности сегодня. Не требует ничего от «платформы».
2. **HTTP для read-путей** + подключение уже существующих, но не используемых
   `/v1/artists/[slug]` и `/v1/releases/[releaseId]` к страницам. Это Б1 — главный блокер.
3. **Контракты в `api-contracts`** по мере появления эндпоинтов — заполнять существующий
   пакет, а не создавать новые.
4. **Вынос `player/queue.ts` и форматтеров в core** — дёшево, очевидная общая логика.
5. **Bearer-auth** — без него п.2 бесполезен нативному клиенту.
6. **SDUI на главной** — порядок блоков в данные.
7. **Дизайн-токены в платформо-нейтральный формат.**
8. Полиморфизация `likes`/`follows`/`playlist_tracks` — **только когда появится второй тип
   сущности**, которую надо лайкать. Раньше это чистая потеря referential integrity.

Пункты 1–4 не требуют принимать решение о Platform Core вообще. Они полезны VireMusic
сами по себе и одновременно являются необходимым фундаментом для любой платформенной затеи.
Это и есть проверка на «архитектура ради архитектуры»: работа, которая окупается,
даже если VireVideo никогда не появится.
