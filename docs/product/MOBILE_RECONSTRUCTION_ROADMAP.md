# Дорожная карта реконструкции мобильной Vire

Дата: 2026-08-29 · Коммит: `0aad30d1` · Статус: **предложение, реализация не начата**
Основания: `MOBILE_PARITY_MATRIX.md`, `MOBILE_PRODUCT_ARCHITECTURE.md`,
`MOBILE_PRODUCT_READINESS_AUDIT.md`

---

## Почему порядок именно такой

Задание предлагает структуру `P0 доставка → P1 ядро → P2 паритет → P3 UX → P4 вторичное →
P5 будущее` и разрешает отклониться, если этого требуют доказательства. **Требуют, в одном
месте: UX не может быть третьей фазой.**

Сегодня в приложении ноль `fontFamily`, нет `expo-font`, а `lib/theme.ts` — две строки
реэкспорта токенов `[C]`. Экраны верстаются локальными `StyleSheet` с магическими числами,
из-за чего радиусы и поля разъехались с китом. Если строить плеер, артиста и главную до
дизайн-системы, каждый из этих экранов придётся переверстать, когда она появится. Поэтому
UX-фундамент идёт **вторым**, сразу после доставки, и до единого экрана продукта.

Второе отклонение: «функциональный паритет» не выделен в отдельную фазу. Паритет — не
работа, а мера; он достигается фазами P3–P5 по доменам, а не отдельным заходом.

```
P0 Доставка ──► P1 Фундамент ──► P2 Ядро музыки ──► P3 Артист и каталог
                     │                  │                    │
                     │                  └────────────────────┴──► P4 Главная
                     └──────────────────────────────────────────► P5 Достройка
                                                                        │
                                                                  P6 Отложенное
```

Зависимости, определяющие рёбра графа:

* всё зависит от **P0**: без устанавливаемого APK ни один вывод нельзя проверить живьём;
* все экраны зависят от **P1**: иначе двойная верстка;
* **P4** (главная) зависит от **P3**: половина блоков главной ведёт на артиста;
* **P5** ни от чего сверх P1 не зависит и может идти параллельно, если появятся руки.

**Цель.** Существует APK, который устанавливается на чужой телефон, доходит до боевого
бэкенда и не портит данные пользователя.

**Почему это первая фаза.** Три факта из кода `[C]`: release подписан debug-ключом;
`applicationId` — плейсхолдер `com.anonymous.viremobile`; в `.env` зашит
`http://localhost:3000`, который release-манифест блокирует политикой cleartext. Собрать
сборку, которая у реального человека хотя бы дойдёт до сервера, сегодня невозможно.

**Почему два продуктовых пункта попали в фазу доставки.** Оба срабатывают **в момент
первой установки первым тестировщиком**, а не когда-нибудь потом:

* протухший refresh чистит токены, но на экран входа не уводит `[C]` — тестировщик через
  неделю получает приложение, которое «сломалось» и чинится только переустановкой;
* мобильный `bootstrapE2eeIdentity()` публикует свой ключ на каждом старте и **перетирает
  ключ веба** `[C]` — установка приложения молча ломает веб-чат того же человека. Раздать
  сборку до этого предохранителя — значит повредить данные тестировщиков.

**Объём.**
1. Конфигурация окружения: боевой `API_BASE_URL` по `https`, разделение dev/prod, `.env` вне бандла.
2. Подпись release существующим `vire-upload-keystore.jks`.
3. Постоянный `applicationId`.
4. `versionCode`/`versionName` из `app.json`; `armeabi-v7a` убрать (детерминированно ломает CMake `[C]`).
5. Воспроизводимость: подпись и идентификатор через `app.json`/config-плагин, не ручной правкой Gradle — `android/` вне git `[C]`.
6. Крашрепортинг.
7. Протухшая сессия → `SignIn` (AU5).
8. Предохранитель E2EE: флаг либо явное предупреждение при первом входе в чат (SO4).

**Вне объёма.** Любая продуктовая функция. Любой редизайн. CI-сборка мобилки (P5).
Публикация в стор.

**Критерии приёмки.**
1. `apksigner verify` подтверждает подпись upload-ключом.
2. `expo prebuild --clean` не теряет подпись и идентификатор — проверено фактическим прогоном.
3. APK установлен на **чужой** телефон, выполняет вход и грузит главную с боевого бэкенда `[D]`.
4. Искусственно протухший refresh уводит на экран входа, а не в ошибку на каждом экране.
5. Вход в чат с телефона не меняет `ik_pub` аккаунта — проверено запросом в БД.
6. Падение в release видно в панели крашрепортера.

**Технические риски.** `prebuild --clean` может разойтись с текущим ручным состоянием
`android/` — там уже есть рассинхрон `newArchEnabled` (`app.json` false, `gradle.properties`
true) `[C]`. Проверять **до** остальных пунктов фазы.

**Продуктовые риски.** Ошибка в `applicationId` необратима после первой публикации.

**Тесты.** Юнит: перехват протухшей сессии. Остальное — приёмка сборкой.

**Проверка на устройстве.** Обязательна: установка на аппарат, где приложение не стояло.

**STOP.** Фаза закрыта, когда посторонний человек установил APK по ссылке и вошёл.

## P1 — Фундамент: дизайн-система и единый материал

**Цель.** Существует система, на которой можно собирать экраны так, чтобы они выглядели
одним продуктом, и материал стекла в приложении один.

**Почему сейчас.** См. преамбулу. Дополнительно: сегодня в приложении **две системы
стекла** `[C]` — `VireGlassSurface` (измеренное преломление) только на четырёх кнопках
таб-бара, и плоский `components/glass.tsx` на мини-плеере, шитах, поиске, композере.
Материал, ради которого проделана вся работа, виден на четырёх кнопках, а самая заметная
поверхность продукта сделана из другого вещества.

**Объём.**
1. Типографика: Manrope + JetBrains Mono, бандл через `expo-font`, отдельное семейство на
   каждый вес (Android не синтезирует начертания надёжно), шкала кеглей из кита.
2. Токены: spacing (поля 20, списки 12, шаг 4/8/12/16/22), радиусы (9–12 / 12–16 / 22–28 /
   sheet 30), motion (120/220/280, reduce motion → 0).
3. Компоненты: `Screen`, `Section`, `TrackRow`, `ReleaseCard`, `ArtistCard`, `CoverImage`,
   `Sheet`, `IconButton`, `PillButton`, `Chip`, `Skeleton`, `EmptyState`, `ErrorState`,
   `OfflineBanner`.
4. Миграция мини-плеера и шитов на `VireGlassSurface`; `components/glass.tsx` остаётся
   только внутри фолбэка Android < 13 и режима «стекло выключено».
5. Счётчик бюджета поверхностей + тест-инвариант.
6. Недостающие иконки кита (`share`, `queue`, `lyrics`, `flow`, `bell`, `settings`).
7. Экран настроек с тумблерами «Стеклянный интерфейс» и «Приглушить движение».

**Вне объёма.** Новые продуктовые экраны. Перестройка главной. Артист.

**Критерии приёмки.**
1. Ни один продовый экран не задаёт шрифт, отступ или радиус числом мимо системы (проверка линтом или обзором).
2. Тест падает, если достижимая комбинация экрана, мини-плеера и шита даёт > 6 стеклянных поверхностей. Сегодня такая комбинация существует (поиск + мини-плеер + шит = 7) `[I]`.
3. Manrope и JetBrains Mono видны на устройстве во всех начертаниях шкалы `[D]`.
4. Тумблер «стекло выключено» делает все панели непрозрачными и не роняет приложение.
5. Кириллица корректна во всех начертаниях — **проверить фактически**, лицензии и покрытие пока `[I]`.

**Технические риски.** Вес APK от семи файлов шрифтов. Начертания Manrope без кириллицы в
части весов — риск, который закрывается только проверкой файлов.

**Продуктовые риски.** Смена шрифта и радиусов меняет облик каждого экрана — визуальный
регресс возможен там, где верстка опиралась на метрики Roboto.

**Тесты.** Инвариант бюджета поверхностей. Снапшот шкалы типографики.

**Проверка на устройстве.** Обязательна: типографика и стекло на реальном экране, включая
слабый аппарат 60 Гц — конверт измерен на одном флагмане `[D]`.

**STOP.** Экран настроек и мини-плеер собраны целиком из системы, старый материал из
продового пути ушёл.

## P2 — Ядро музыкального опыта

**Цель.** Vire на телефоне становится музыкальным продуктом: играющее всегда под рукой,
переживает перезапуск, корректно ведёт себя со звонком и честно отчитывается платформе.

**Объём.**
1. **Мини-плеер** заново: обложка, название, play, прогресс нижним rim'ом, свайп вверх —
   фуллскрин, свайп вбок — следующий/предыдущий.
2. **Фуллскрин-плеер** заново: доминирующая обложка, транспорт на стекле, три панели —
   Очередь · Текст · Трек. Третья панель заменяет отдельную страницу трека (решение
   архитектуры §5.3): волна, BPM/тональность, mood-теги, credits, live-счётчик.
3. **Персист плеера** — очередь, индекс, позиция; резюме по первому нажатию play, как на вебе `[C]`.
4. **Отчёт о прослушивании** как подсистема: `POST /api/v1/session` за подписанным
   `sessionId`, учёт фактического времени, флаш в конце проигрывания, контекст `source`,
   локальная очередь для офлайн-прослушиваний.
5. **Аудиофокус**: явная настройка + проверка на входящем звонке.
6. Лайк и шеринг из плеера.
7. Waveform-скраббер на предрассчитанных пиках.

**Вне объёма.** Любимые моменты (P5). Волна (P4 — зависит от главной). Очередь с
переупорядочиванием (просмотр — да, drag — P5).

**Критерии приёмки.**
1. Перезапуск приложения возвращает очередь, трек и позицию; первый play продолжает с места.
2. Одно прослушивание порождает **ровно одно** событие с фактическим `durationPlayedSec`;
   пауза не считается — покрыто тестом.
3. `source` соответствует реальному месту запуска очереди, а не `direct` по умолчанию.
4. Прослушивание в авиарежиме уходит на сервер после восстановления сети.
5. Входящий звонок глушит воспроизведение и корректно возвращает его `[D]`.
6. Текст трека подсвечивается по таймкодам, клик по строке перематывает.
7. Фуллскрин-плеер держится в бюджете поверхностей.

**Технические риски.** Точность учёта времени при переходах фон/форграунд. Дубли событий
при быстром переключении треков — тот же класс гонок, который в сторе уже закрыт
staleness-guard'ом `[C]`.

**Продуктовые риски.** Неверный `durationPlayedSec` **портит рекомендации всей
платформы**: Волна делит его на длительность трека и получает качество дослушивания
(`wave.ts:139,158` `[C]`). Ошибка здесь дороже, чем отсутствие отчёта.

**Тесты.** Персист и восстановление стора. Ровно одно событие на прослушивание. Учёт
паузы. Офлайн-очередь событий. Резюме с сохранённой позиции.

**Проверка на устройстве.** Обязательна: звонок, наушники, Bluetooth, лок-скрин с PIN,
длительная сессия в фоне.

**STOP.** Прослушивание с телефона видно в статистике артиста, а плеер переживает
перезапуск.

## P3 — Артист и контур каталога

**Цель.** Закрыть главную дыру продукта: артист живёт внутри приложения.

**Почему после ядра.** Экран артиста — первое место, где появляется контекстный акцент и
крупная контентная стеклянная плашка. И то и другое требует готовой дизайн-системы (P1),
а транспорт «слушать всё» — готового плеера (P2).

**Объём.**
1. **Экран артиста**: ambient-фон, крупная стеклянная плашка идентичности, тема артиста
   из `theme_tokens`, подписка, play-all каталога, Популярное, Релизы, Анонсы, Похожие, Площадки.
2. Убрать `WebBrowser` из пути к артисту в поиске `[C]`.
3. Имя артиста ссылкой на экране релиза — сегодня не ссылка `[C]`.
4. Экран релиза: credits, liner notes, фит/версия через общий `featuredNames` из `@vire/core`.
5. Медиатека: Любимые треки отдельным экраном, Подписки, лайкнутые плейлисты.
6. Поиск: история и mood-подсказки в пустом состоянии.

**Вне объёма.** Смартлинки-хаб (P5). Видео артиста (P5). Каталоги `/artists`, `/releases` (P5).

**Критерии приёмки.**
1. Ни один путь к артисту не открывает браузер.
2. Подписка работает и переживает возврат на экран.
3. Акцент артиста применяется на его экране и гаснет за его пределами; чипы остаются нейтральными.
4. Play-all каталога запускает очередь с `source: 'artist'`.
5. Экран артиста укладывается в бюджет поверхностей.

**Технические риски.** `theme_tokens` — произвольный JSONB; нужен санитайзер и проверка
контраста, иначе тема артиста может сделать текст нечитаемым.

**Продуктовые риски.** Контраст акцента на тёмном фоне — WCAG AA для публичных
поверхностей заявлен в `docs/PRODUCT.md`.

**Тесты.** Санитайзер темы. Переход из поиска и релиза к артисту. Подписка оптимистично + откат.

**Проверка на устройстве.** Тема артиста на реальном экране; читаемость на солнце.

**STOP.** Путь «поиск → артист → релиз → трек → воспроизведение» пройден целиком внутри
приложения.

## P4 — Главная и discovery

**Цель.** Главная перестаёт быть двумя лентами и становится персональным входом.

**Объём.**
1. Реестр рендереров SDUI; `X-Vire-Blocks` расширяется по мере готовности.
2. **Продолжить слушать** — первый блок вошедшего.
3. **Поток**: кнопка Волны + чипы настроений и жанров; автопродолжение при исчерпании очереди.
4. Для тебя · Ваша лента · Подборки · Скоро выйдет · Открытия для вас · Активность друзей.
5. Экран отсчёта SCHEDULED + пресейв.

**Вне объёма.** Джем. Вечеринка. Каталоги.

**Критерии приёмки.**
1. Порядок блоков задаёт сервер; клиент не содержит своего порядка.
2. Незнакомый тип блока не роняет экран (контракт намеренно открытый `[C]`).
3. Волна, запущенная по чипу, держится внутри выбранного настроения/жанра всю сессию — как на вебе `[C]`.
4. Пустой блок самоскрывается.
5. Прослушивание из Волны уходит с `source: 'wave'`.

**Технические риски.** Стоимость первого экрана растёт с числом блоков — измерять время до
первого содержательного кадра.

**Продуктовые риски.** Перегруженная главная противоречит «инструмент, не витрина» из
`docs/PRODUCT.md`. Порядок и пороги самоскрытия брать с веба, не изобретать.

**Тесты.** Реестр: неизвестный тип. Порог самоскрытия. Seed-фильтр Волны.

**Проверка на устройстве.** Скорость и плавность главной со всеми блоками, включая слабый аппарат.

**STOP.** Вошедший видит персональную главную и запускает Волну в один тап.

## P5 — Достройка продукта

**Цель.** Закрыть остаток паритета, значимого для обычного пользователя.

**Объём** (независимые срезы, порядок по важности):
1. **Пуши до конца**: обработчик форграунда, реакция на тап, общий с вебом контракт
   назначения, холодный старт из уведомления, инбокс уведомлений.
2. **Офлайн как продукт**: детект сети, офлайн-состояние главной, квота и поведение при
   переполнении, уборка битого каталога, скачивание плейлиста целиком.
3. **Профиль**: идентичность, аватар (камера и галерея), статистика, вкус, активность,
   приватность лайков.
4. **Плейлисты**: переименование, описание, приватность, удаление, обложка, порядок, подсказки.
5. **Диплинки** по полной карте + отложенная цель до входа.
6. **i18n**: `packages/i18n` уже содержит ru и en `[C]`; сегодня строки зашиты по-русски.
7. **Правовые страницы** — обязательны для публикации в сторе.
8. Обратная связь, жалобы, шеринг профиля, любимые моменты, каталоги, смартлинки-хаб.
9. **CI-сборка мобилки** и внутренняя раздача.

**Критерии приёмки.** Пуш открывает то, о чём он. Приложение честно ведёт себя без сети.
Профиль показывает пользователя, а не список устройств. Матрица паритета обновлена
фактическим состоянием.

**STOP.** Строки матрицы с важностью 1–2 закрыты или явно перенесены с обоснованием.

## P6 — Отложенное и будущее платформы

Каждый пункт — с условием разморозки, а не «когда-нибудь».

| Направление | Условие |
|---|---|
| **Чат** | Ревью безопасности ключей завершено, привязка устройств через `keys/link/*` реализована, ущерб измерен запросом по `identity_keys` |
| **Джем и вечеринка** | Ядро и социальный слой стабильны; телефон — естественная среда участия в джеме, экран вечеринки остаётся на большом дисплее |
| **Монетизация** | Этап 2 запущен **и** решён вопрос комиссии Google Play за цифровые товары |
| **iOS** | Появился Mac. VireGlass на iOS не поддерживается принципиально — потребуется отдельная визуальная стратегия |
| **Дашборд артиста (просмотр статистики)** | Только чтение; загрузка и редактирование остаются на вебе |
| **Пасхалки** | После P5; часть характера бренда, но не первого релиза |

## Что не делать ни в одной фазе

* **Не возобновлять исследование VireGlass**, не делать HardwareBuffer, не переписывать
  рендерер: конверт измерен `[D]`, ADR-001 написан, продукт в него укладывается.
* **Не переписывать навигацию, состояние и API-слой** — структура подтверждена, дрейфа
  контрактов нет `[C]`.
* **Не менять движок воспроизведения** — RNTP + HLS + foreground-service выстраданы через
  задокументированный краш и его починку.
* **Не тянуть на телефон дашборд и админку.**
* **Не наращивать число тестов ради числа** — недостающая уверенность лежит на устройстве.
* **Не переделывать доступ артистов** — привязка администратором по email работает.
* **Не открывать чат** до ревью ключей.
* **Не начинать iOS.**

## Рекомендуемая первая фаза

**P0.** Не потому, что доставка интереснее продукта, а потому что до неё **ни один
продуктовый вывод нельзя ни подтвердить, ни опровергнуть**: собрать APK, который дойдёт до
бэкенда, сегодня физически невозможно `[C]`, а два предохранителя внутри фазы срабатывают
в момент первой установки первым живым тестировщиком.

P0 — самая маленькая фаза дорожной карты и единственная, которая ничего не строит. Это
осознанно: она превращает репозиторий из «кода, про который мы рассуждаем» в «продукт,
который можно проверить».
