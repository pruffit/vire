## Executive Summary

Внутри `apps/mobile` лежит **работающее музыкальное приложение с настоящим ядром
воспроизведения**, а не каркас. Звук играет через HLS с фоновым сервисом и лок-скрином,
очередь/shuffle/repeat/seek реальны, офлайн-скачивание реально проигрывается с диска,
E2EE-чат реально шифрует, 232 теста зелёные. Это не «UI на моках» — доля мокированного
кода в продовом пути близка к нулю.

Проблема не в качестве написанного, а в **трёх разрывах**:

1. **Разрыв доставки.** Ни один собранный APK сегодня не может работать у реального
   пользователя. Release-сборка подписана debug-ключом, `applicationId` —
   `com.anonymous.viremobile`, а в `.env` зашит `http://localhost:3000`, который
   release-сборка блокирует политикой cleartext. Это не «низкая зрелость пайплайна» —
   это техническая невозможность установить и запустить продукт. Все три пункта
   проверены в коде.
2. **Разрыв продуктового контура.** Артиста в приложении нет: тап по артисту в поиске
   открывает **внешний браузер** на веб-страницу. Для музыкальной площадки, где артист —
   центральная сущность, главный путь выходит за пределы приложения.
3. **Разрыв визуальной системы.** Дизайн-направление (4 связанных канваса) описано
   подробно и последовательно, но реализовано частично: шрифтов кита в приложении **нет
   вообще** (ноль `fontFamily`, нет `expo-font`), радиусы и поля систематически меньше
   китовых, 3 из 8 спроектированных экранов не существуют.

При этом **VireGlass — не проблема, а актив**: он измерен на устройстве, его конверт
известен (до 6 поверхностей), и текущий UI в него укладывается. Перезапускать эту работу
не нужно.

Кратчайший путь до первого релиза не требует переписывания. Он требует: починить доставку,
дать артисту нативный экран, дописать отчёт о прослушивании, обезвредить E2EE между
устройствами и довести типографику.

**Общая готовность к первому релизу — 40 %.**

### 2.1 Родословная направления

Файлы не альтернативы — это **одна линия во времени**, и она читается по содержанию, а не
только по датам:

```
Glass.dc.html            UI Kit.dc.html          Final States.dc.html     design/Main.dc.html
исследование             кит v0.1                8 экранов × состояния    кит финальный
t1 три системы стекла  → акцент = мятный      → применение кита v0.1   → акцента у платформы НЕТ
t2 структура экранов     #4fd1a5 «платформенный» на реальных экранах      акцент только из контекста
t3 на реальных данных    макс. 2–3 стекла                                 макс. 2 BlurView
t4 три закона стекла     нав = 5 кругов                                   нав = 5 кругов
```

### 2.2 Что говорит каждый

**`Glass.dc.html`** — четыре хода исследования, в каждом несколько вариантов. t1: три
системы стекла на общей базе (`#030201` / `#eae7e2`), различаются плотностью, характером
блика и глубиной захода акцента артиста. t2: структурная эволюция — «главная перестаёт быть
ещё одним гридом обложек», плеер получает второй экран, карточка артиста разводится с
профилем слушателя, **таб-бар распадается на отдельные кнопки**. t3: пересборка на
настоящих данных VireMusic — Поток, mood-теги, «Продолжить слушать», «Для тебя», активность
друзей, Джем, личные сообщения. t4: три закона стекла, ставшие ядром кита.

**Три закона (сквозные, повторены во всех последующих файлах):**
1. кнопка с иконкой — **всегда круг под палец**, 48 / 56 / 64 px, **без подписи**; текст
   остаётся только у текстовых кнопок;
2. все панели — **одно и то же** прозрачное стекло: `#12100e @40 %`, blur 30, saturate 175 %,
   преломляющий градиент сверху, specular-нить по верхней кромке;
3. **источник света — контент**: обложки и текст под стеклом подсвечивают его снизу,
   поэтому у панели есть нижний rim-свет, а не только верхний блик.

**`UI Kit.dc.html`** — семь разделов (цвет, стекло, типографика, кнопки, компоненты, иконки,
сетка/радиусы/движение). Ключевое отличие от финального: `accent.platform = #4fd1a5`,
мятный, объявлен фирменным цветом платформы.

**`Final States.dc.html`** — **8 экранов, каждый в 2–5 состояниях**, макет 390×844:

| # | Экран | Состояния в макете |
|---|---|---|
| 01 | Главная | default → загрузка → **офлайн** |
| 02 | Плеер | играет → пауза → буферизация |
| 03 | Поиск | история до ввода → результаты → ничего не найдено |
| 04 | Медиатека | заполнена → пустая |
| 05 | **Артист** | загрузка → не подписан → подписан (нажатие) |
| 06 | **Джем** | лобби → активна → завершена |
| 07 | Сообщения | пусто → диалоги → печатает → вложения → стикеры |
| 08 | Профиль/Настройки | обычный → **стекло выключено** |

**`design/Main.dc.html`** — финальный кит, и он **отменяет мятный акцент**:

> «У платформы нет своего цвета. Веб уже так живёт (`packages/design-tokens` не содержит
> поля accent) — платформенная оболочка нейтральна. Мобилка наследует это буквально.
> Цвет появляется только вместе с контекстом — профилем артиста (`theme_tokens`) или
> играющим сейчас релизом в плеере.»

Правило доведено до деталей: rim панели по умолчанию нейтральный (белый 18 %), цветным
становится только когда панель физически лежит внутри контекста; чипы и фильтры **всегда**
нейтральны даже внутри профиля артиста, потому что они категориальные, а не персональные;
активное состояние вне контекста красится сплошным `foreground #eae7e2`, не цветом.

Там же — инженерная спека под Android: `backdrop-filter` в RN не существует, панель — это
`BlurView` + оверлей-заливка + верхний градиент + нижний rim, обязателен
`dimezisBlurView`, и **максимум 2 одновременных BlurView** (явно: «не 3 — Android дороже
веба»).

## 3. Правила стекла, действующие с этого момента

Дополнение к киту, зафиксированное в этой фазе как обязательное:

1. **Иконка на круглом стекле.** Иконочная кнопка — круг, иконка внутри, подписи нет.
   Реализовано в `LiquidGlassButton`: маска иконки уходит в шейдер, цвет штриха берётся
   там же, активное состояние — плавный переход, а не второе изображение. `[CODE]`
2. **Больший контент — на стеклянных плашках.** Стекло несёт контент: фото, иконки, текст.
   Плашка не декорация, а поверхность под содержимое. Это расширяет кит: там стекло было
   почти только шасси (нав, композер, поиск), здесь оно явно становится носителем
   контента — что делает мини-плеер (обложка + два текста + кнопка на стекле) образцовым
   случаем, а не исключением.
3. Ограничение при этом не смягчается: **стекло не кладётся на плотные списки и не
   кладётся на стекло**, и число одновременных поверхностей держится в измеренном
   конверте (§8).

Правило 2 напрямую влияет на планирование: экран артиста и полноэкранный плеер — главные
кандидаты на крупные контентные стеклянные плашки, и обе поверхности крупные, а **цена
измерена в числе поверхностей, а не в площади** `[DEVICE]` — значит, одна большая плашка
дешевле пяти мелких.

## 11. E2EE-чат

Шифрование **настоящее**, не имитация: `tweetnacl` `nacl.box` (X25519 + XSalsa20-Poly1305),
приватный ключ в SecureStore, на сервер уходят только `ciphertext` + `nonce`, побитовое
соответствие libsodium доказано тестами. `[CODE]` `[TEST]`

Функционально закрыт полный контур: тред, список диалогов, typing, «прочитано», realtime
по SSE, превью последнего сообщения. `[CODE]` `[EMULATOR]` инкременты 13–16.

### Найденная опасность: ключ один на пользователя, а устройств два

Цепочка проверена в коде обеих сторон:

```
apps/web/app/api/v1/keys/route.ts
    POST → upsertIdentityKey(caller.id, ikPub)   ← ОДИН ключ на userId, UPSERT
    GET  → getIdentityKey(userId)                ← отдаёт ровно один

apps/mobile/lib/e2ee/bootstrap.ts
    вызывается из App.tsx НА КАЖДОМ СТАРТЕ с живой сессией
    → getOrCreateIdentity(userId)   ← свой ключ, независимый от веба
    → publishIdentityKey(pub)       ← ПЕРЕЗАПИСЫВАЕТ ключ веба
```

`[CODE]` Веб делает симметрично то же самое из своего `E2eeBootstrap`. Следствие
`[INFERENCE]`, прямо вытекающее из кода: у пользователя, который зашёл и с телефона, и с
браузера, **два устройства перетирают ключ друг друга по очереди**. Новые сообщения
шифруются на того, кто опубликовался последним; второе устройство их не расшифрует, а
старые сообщения не расшифрует первое.

Дедуп в `publishIdentityKey` — по значению ключа **в памяти процесса**, он от этого не
спасает: ключи-то разные.

Инфраструктура для правильного решения на бэкенде **уже есть** — шесть роутов
`keys/link/*` (SAS-привязка устройств) `[CODE]`. Мобилка в них не участвует.

### Классификация для первого релиза: **POST-BETA FEATURE**

Не потому, что чат плох — он как раз хорош, — а потому что он **создаёт риск релиза**:
установка мобильного приложения молча ломает веб-чат того же человека. Технически
впечатляющая часть не должна тянуть релиз вперёд себя. Варианта два, оба дешёвые
относительно привязки устройств: спрятать чат за флагом до реализации `keys/link/*`,
либо явно предупредить пользователя при первом входе в чат с телефона.

| `VireGlassSurface` + `modules/glass-lens` (AGSL) | **только таб-бар** (4 кнопки) | настоящее преломление, Френель, блик, дисперсия, эластичная деформация |
| `components/glass.tsx` (`BlurView` + заливка) | мини-плеер, sheet, поиск, композер чата, транспорт плеера, поиск друзей | плоское стекло: blur + тинт + кромка |

То есть материал v1, ради которого проделана вся работа, сегодня виден **на четырёх
кнопках навигации**. Мини-плеер — самая заметная стеклянная поверхность продукта — остаётся
на плоском стекле. Это не поломка, а неоконченная раскатка.

**Укладывается ли UI в лимиты.** Да, с запасом, но ближе к краю, чем кажется. Каждая
поверхность несёт свой `BlurView` `[CODE]`, поэтому считать надо их:

| Ситуация | Поверхностей | Зона `[DEVICE]` |
|---|---|---|
| Любой экран без мини-плеера | 4 (таб-бар) | зелёная |
| Обычная работа с играющим треком | 4 + 1 = **5** | зелёная |
| Поиск с играющим треком | 4 + 1 + 1 = **6** | зелёная, **на границе** |
| Поиск + открытый sheet «в плейлист» | 4 + 1 + 1 + 1 = **7** | **жёлтая** (101 кадр/с) |
| Полноэкранный плеер | 2 (закрыть + транспорт), таб-бар скрыт | зелёная |

**Есть ли экраны, случайно выбивающиеся из конверта.** Да, один: **поиск с играющим треком
и открытым sheet добавления в плейлист даёт 7 поверхностей** — ровно точка насыщения по
замеру. Это достижимо обычными действиями пользователя, а не искусственно. `[INFERENCE]`
из `[CODE]` (подсчёт монтируемых `BlurView`) + `[DEVICE]` (замер конверта).

Отдельно: китовый ориентир «3 одновременных поверхности» (таб-бар + мини-плеер + sheet)
**считал таб-бар за одну поверхность**. Раздельные круглые кнопки — решение из t2 — сделали
его четырьмя. Реальный минимум приложения не 3, а 5.

**Намеренно ли используется стекло.** Да. Правило «только плавающие слои» соблюдается: в
списках, карточках, строках треков и пузырях чата стекла нет `[CODE]`. Архитектурное
ограничение «стекло не может лежать внутри своей же цели захвата» реализовано аккуратно
через `BlurTargetScope` — и это не косметика, а защита от `SIGSEGV` в RenderThread
(зафиксировано в ADR-001 §2).

## 15. Реальность тестов

**232 теста в 26 файлах, все зелёные, 6.7 с.** `[TEST]` (В `CLAUDE.md` записано 210 —
цифра устарела.)

Покрыто хорошо — вся чистая логика: очередь и переходы плеера, HTTP-клиент с refresh,
E2EE (включая побитовый roundtrip с libsodium), чат (превью/typing/realtime), офлайн-индекс,
поиск, плейлисты, друзья, декодирование токена, LAN-хост, форматтеры, и **тест-паритет имён
пропов JS↔Kotlin для VireGlass** — последний особенно ценен: он закрывает класс ошибки,
из-за которого преломление было молча выключено в проде четыре инкремента подряд. `[CODE]`

Чего нет совсем:

* **ноль тестов уровня компонента и экрана** (`*.test.tsx` — 0 файлов) `[CODE]`;
* ноль тестов навигации и диплинков;
* ноль интеграционных тестов «экран → API → стор»;
* ничто не проверяет реальный звук, фон, лок-скрин, доставку пуша, стекло на GPU.

Честная формулировка: **232 теста доказывают, что логика верна, и ничего не говорят о том,
что приложение работает.** Наращивать их количество бессмысленно; недостающая уверенность
лежит в другой плоскости — на устройстве.

Точечно ценными были бы четыре теста, а не тысяча:
1. `player-store` не теряет очередь при рестарте (после введения персиста);
2. отчёт о прослушивании отправляется ровно один раз на трек;
3. протухший refresh уводит на `SignIn`;
4. payload пуша маршрутизируется в существующий экран.

## 20. Чего строить НЕЛЬЗЯ

* **Не переписывать навигацию, состояние, API-слой.** React Navigation 7 + Zustand +
  общие zod-контракты работают, дрейфа контрактов нет, дублирования логики нет `[CODE]`.
* **Не менять движок воспроизведения.** RNTP + HLS + foreground-service — рабочее ядро,
  выстраданное через задокументированный краш и его починку.
* **Не возобновлять исследование VireGlass, не делать HardwareBuffer, не трогать рендерер.**
  Конверт измерен, ADR написан, продукт в него укладывается.
* **Не переделывать доступ артистов.** Привязка аккаунта к артисту администратором по email
  работает; ручной характер привязки — вопрос масштабирования, а не блокер.
* **Не начинать iOS.** Нет Mac; кроме того, VireGlass на iOS не поддерживается
  принципиально (нет публичного API доступа к фону).
* **Не строить Джем.** Самый дорогой из ненаписанных экранов, к ядру не относится.
* **Не гнаться за паритетом с вебом.** 90 неиспользуемых эндпоинтов — не список задач.
* **Не наращивать число юнит-тестов.** Недостающая уверенность лежит на устройстве.
* **Не redesign'ить визуальную систему.** Она определена и свежая; её надо дореализовать,
  а не переоткрыть.

## 21. Кратчайший путь к первому релизу

Порядок продиктован зависимостями, а не удобством: **сначала то, без чего невозможно
проверить остальное на устройстве.**

```
ФАЗА 5.1  Доставка           → появляется устанавливаемый и достающий до бэкенда APK
    ↓                           (без этого ничего нельзя проверить живьём)
ФАЗА 5.2  Продуктовый контур → артист, прослушивания, сессия, шрифты, E2EE-предохранитель
    ↓
ФАЗА 5.3  Устройство и раздача → первые реальные пользователи
```

### ФАЗА 5.1 — Доставка и конфигурация

**Цель.** Собрать подписанный APK с постоянным идентификатором, который на реальном
телефоне достаёт до боевого бэкенда.

**Работы:** P0-1 … P0-4, P0-10.
Отдельно — решить вопрос **воспроизводимости**: `android/` вне git, поэтому подпись и
идентификатор должны задаваться через `app.json`/config-плагин (или EAS), а не ручной
правкой Gradle, которая исчезнет при следующем `prebuild`.

**Критерии приёмки.**
1. `assembleRelease` даёт APK, подписанный upload-ключом (`apksigner verify`).
2. `applicationId` постоянный, `versionCode` выводится из `app.json`.
3. Установленный на телефон APK успешно выполняет вход и грузит главную с боевого бэкенда.
4. `expo prebuild --clean` не теряет ни подпись, ни идентификатор.
5. Падение в release уходит в крашрепортер и видно в панели.

### ФАЗА 5.2 — Продуктовый контур

**Цель.** Закрыть дыры главного пути музыкальной площадки и снять риск E2EE.

**Работы:** P0-5 (артист), P0-6 (прослушивания), P0-7 (сессия), P0-8 (E2EE-предохранитель),
P0-9 (шрифты).

Экран артиста строится **на существующем**: `/artists/{slug}` + `/artists/{slug}/follow`
уже отдают всё нужное, `ReleaseScreen` даёт образец экрана с обложкой и списком, тема
артиста приходит в `theme_tokens` — и это ровно тот случай, где по киту появляется
**контекстный акцент**, а по правилу §3 — крупная контентная стеклянная плашка.

**Критерии приёмки.**
1. Из поиска и с экрана релиза артист открывается **внутри приложения**; `WebBrowser` из
   этого пути удалён.
2. На экране артиста работает подписка, состояние переживает возврат на экран.
3. Акцент артиста применяется на его экране и гаснет за его пределами; чипы остаются
   нейтральными.
4. Каждое прослушивание порождает ровно один `POST /tracks/{id}/play` — покрыто тестом.
5. Протухший refresh уводит на `SignIn`, а не оставляет ошибку на экране.
6. Вход в чат с телефона не ломает веб-чат того же аккаунта (флаг либо предупреждение).
7. Manrope и JetBrains Mono реально применены; кегли и начертания соответствуют киту.
8. Одновременных стеклянных поверхностей на любом достижимом экране — **не больше 6**
   (проверка включает случай «поиск + мини-плеер + sheet», сегодня дающий 7).

### ФАЗА 5.3 — Проверка на устройстве и раздача

**Цель.** Доказать на живом железе то, что эмулятор доказать не может, и отдать сборку людям.

**Работы:** P0-11 + P1-9.

**Матрица проверки — обязательная, каждая строка `[DEVICE]`:**

| Проверка | Критерий |
|---|---|
| Холодный старт с сессией | главная за разумное время, без вечного спиннера |
| Вход и выход | токены сохраняются и вычищаются, устройство отзывается на сервере |
| Воспроизведение HLS | старт, пауза, next/prev, seek |
| **Фон** | сворачивание не останавливает звук |
| **Лок-скрин** | контролы видны и работают |
| **Лок-скрин с PIN** | звук и контролы переживают блокировку с паролем |
| **Аудиофокус** | входящий звонок глушит и корректно возвращает |
| Офлайн | скачивание, авиарежим, проигрывание с диска |
| Пуш | доезжает при закрытом и при свёрнутом приложении |
| Стекло | таб-бар и мини-плеер держат кадры на всех экранах |
| **Слабый аппарат** | тот же список на не-флагмане 60 Гц |

**Критерии приёмки.** Вся матрица пройдена минимум на двух аппаратах (один — заведомо
слабый); APK доступен по ссылке; крашрепортер получил хотя бы одно событие из полевой
сборки.

## 23. Итог

Внутри `apps/mobile` лежит **настоящее музыкальное приложение**, а не прототип: звук,
очередь, фон, офлайн, шифрование и стекло — реальные, измеренные, покрытые тестами там,
где тесты применимы. Написанное не надо переписывать.

Между этим кодом и первым пользователем стоят три вещи, и ни одна из них не архитектурная:
**сборка, которая доходит до бэкенда**, **артист внутри приложения**, и **проверка на живом
телефоне**. Всё остальное из списка P0 — конфигурация, один эндпоинт, один редирект, один
предохранитель и один шрифт.

Именно поэтому кратчайший путь начинается не с продукта, а с доставки: пока APK не
устанавливается и не видит сервер, ни один продуктовый вывод нельзя ни подтвердить, ни
опровергнуть.
