# Нагрузочное тестирование (§9.5)

Цель — узнать **сколько одновременных слушателей держит сервер** и во что упирается
раньше всего (RAM / CPU / Postgres / очереди). Тестируем Next-приложение (страницы +
API). HLS-сегменты отдаёт CDN/S3 отдельно — в этом тесте не участвуют.

## Инструмент

[k6](https://k6.io) — отдельный бинарь, не npm-пакет.

```bash
winget install k6        # Windows
brew install k6          # macOS
sudo apt install k6      # Linux (через репозиторий k6)
```

Сценарий: [`scripts/loadtest/listener-journey.js`](../../scripts/loadtest/listener-journey.js)
— имитирует путь слушателя (главная → каталог → поиск → артист → релиз → манифест трека → health).

## Запуск

```bash
# локально, дефолт 20 VU на 1 минуту
k6 run scripts/loadtest/listener-journey.js

# по проду, 50 одновременных «слушателей» 2 минуты, с детальными страницами
BASE_URL=https://viremusic.ru VUS=50 DURATION=2m \
  ARTIST_SLUG=<slug> RELEASE_ID=<uuid> TRACK_ID=<uuid> \
  k6 run scripts/loadtest/listener-journey.js
```

Параметры через env: `BASE_URL`, `VUS`, `DURATION`, `ARTIST_SLUG`, `RELEASE_ID`,
`TRACK_ID` (без id-шников детальные шаги пропускаются).

> ⚠️ Гоняй по проду осознанно (это реальная нагрузка на боевой VPS) — лучше в тихое
> время или по стейджингу. Начинай с малого VUS и повышай.

## Как читать результат

k6 печатает `http_req_duration` (p95) и `http_req_failed`. Пороги в сценарии:
p95 < 1.5с и ошибок < 2%. **Повышай `VUS`, пока пороги не начнут падать** — это и есть
потолок. Параллельно держи открытой панель **`/admin/system`**: смотри, что растёт
первым — RAM, CPU load или длина очередей. Это и есть
узкое место, под которое принимать решение (апгрейд VPS / оптимизация / кэш).

## Базовая цифра ёмкости (замер 27.07.2026, прод `viremusic.ru`, VPS 1 vCPU / 1 ГБ)

> ⚠️ **Замер устарел: сделан до апгрейда** (сейчас 2 ядра × 3.3 ГГц / 2 ГБ). Цифры ниже —
> нижняя граница, реальный потолок выше и не измерен. Повторить прогон на новом железе.

Прогон с одной машины (Windows, k6 v2.1.0), профиль по возрастанию, каждая ступень —
20с разгон + 1м плато + 10с спад. Путь слушателя без шага `manifest` (см. оговорку ниже).

| VU | p95 | p90 | медиана | ошибки | вердикт |
|---|---|---|---|---|---|
| 5 | 278 мс | 211 мс | 82 мс | 0 (кроме manifest) | запас |
| 15 | 1.01 с | 615 мс | 248 мс | 0% | порог держится |
| 25 | 2.22 с | 1.43 с | 548 мс | 0% | **порог p95<1.5с пробит** |

**Вывод: потолок — 15–20 одновременных слушателей** при целевом p95 < 1.5с.
Деградация мягкая: на 25 VU растёт латентность, но 5xx нет и сервер не отказывает —
упирается в CPU/RAM, а не в исчерпание соединений. Пропускная способность на плато —
~20 req/s (2.8 итерации пути слушателя в секунду).

> ⚠️ Шаг `manifest` из замера исключён намеренно: `GET /api/v1/tracks/[id]/manifest`
> ограничен 60 запросами в минуту на клиентский ключ (IP), а k6 гонит все VU с одного
> адреса — на 5 VU это уже давало 12% `429`. Это корректная работа rate-limit, а не
> дефект; но ёмкость по манифесту с одной машины не измерить. Для честного замера
> этого шага нужен прогон с нескольких IP (распределённый k6 / облачный запуск).
